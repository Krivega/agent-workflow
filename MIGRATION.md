## Backend задачи при подготовке T6

[ADR-0067](https://github.com/Krivega/agent-workflow/blob/main/docs/design/decisions/inherited/0067-run-reusable-agent-workflow-on-temporal.md)
разрешает после квалификации переход только новых задач. Все начатые задачи сохраняют
исходный backend до завершения; `preview-task`/`apply-task`, обновление TaskNotes, revision
требований и backup/restore не являются переносом исполнения между движками.
Копирование старой задачи под новым ID для её продолжения в Temporal запрещено.

На 2026-11-16 каноническое неизменяемое назначение backend и проверки пишущих входов
реализованы, но в рабочем проекте не включены. Назначения находятся в Git common-dir
`agent-workflow/backend-assignments`; SDK требует явной доверенной регистрации клиента.
Штатный `task-chat start` при действующей политике версии 2 принимает подготовленный вход
Temporal. Квалификация установленного потребителя и включение T6 остаются отдельными шагами.
Новые модельные запуски Harness² запрещены до RPC, процесса и записи. Назначение нельзя вывести только из версии карточки,
наличия Store или Temporal workflow ID.
[Единая карта границ и порядок включения](https://github.com/Krivega/agent-workflow/blob/main/docs/temporal-consumers.md#границы-создания-продолжения-и-записи-перед-t6)
перечисляет обходные пути, подготовительные действия и отсутствующие проверки.

До отдельного разрешения T6 default не меняется. Перед включением проверяются штатный
запуск Temporal и защита от повторного запуска зарегистрированной задачи. Назначение
атомарно закрепляется до первой записи или внешнего эффекта. Неизвестный consumer/backend,
конфликт или недоступное назначение останавливают пишущий путь до сверки.

Возврат default сохраняет назначения уже созданных задач. После сбоя Temporal-задачи нужны
остановка, сверка эффектов и восстановление Temporal. Границы текущего перехода закреплены
в [плане миграции](https://github.com/Krivega/agent-workflow/blob/main/docs/exec-plans/completed/2026-10-27-agent-workflow-temporal-migration.md#переключение-и-восстановление).

## Допуск B1 и ограниченный coder B2

[ADR-0063](https://github.com/Krivega/agent-workflow/blob/main/docs/design/decisions/inherited/0063-admit-local-implementation-with-executor-plan.md)
и [ADR-0064](https://github.com/Krivega/agent-workflow/blob/main/docs/design/decisions/inherited/0064-delegate-coder-in-isolated-copy.md) вводят явные
форматы LocalRun 2 (`format: local-planning` либо `coder`), Execution 3 и WorkflowCheckpoint 2.
Прежний substantial-маршрут без coder сохраняет старую версию; чтение legacy не мигрирует её.
Неизвестный формат, неподходящий discriminator и новый формат без backup отказывают до записи.

Перед первой новой записью штатный `backupSupervision` выполняет freeze/export/verify/thaw
существующего Store и сохраняет receipt. `local_run_format_backup` либо `format_backup`
ссылается на точные байты проверенной копии. Parent locks, coders и execution reservations
пишутся одной транзакцией; старый writer не должен читать их как прежний разрешённый формат.
Managed local planning имеет собственную версию 2 и не подменяет старый planning council.

Откат: прекратить новых coder, подтвердить остановку прежних и согласовать частичный импорт;
затем восстановить весь проверенный backup прежней версией инструмента в отдельный пустой
Store. Не переносить отдельные старые checkpoint/blobs поверх работающего Store и не удалять
новые блокировки для допуска старого writer. Новые и исторические FAIL/NOT RUN сохраняются
в исходных доказательствах. Реальную проверку старого writer выполняют на закреплённой прежней
версии и копии данных; версия схемы сама по себе не заменяет этот опыт.

Состояние общего допуска находится в [каталоге процедур](procedures/README.md).
Подключение не запускает модель, помощников, сеть или публикацию. Для каждой задачи нужны
явные project/task ID и разрешённая карточка; остальные планы остаются без изменений.

## Проверка выпуска в подключённом проекте

В установленном пакете проверка `checkConsumerRelease` отклоняет команды прежнего движка.
Регрессии прежнего процесса проверяют функцию
`await checkConsumerRelease(args, { root, version })` из
`tests/legacyConsumerRelease.mjs`. `root` указывает рабочую копию потребителя,
`version` — версию установленного пакета. Новый процесс сохраняет `runtime_package_version`
в плане подключения, журнале выбора, managed-chat и идентичности Store.

При изменении сохранённой задачи проверяются найденные записи. Старый план, журнал, чат или
Store без совпадающей версии требуют исходного выпуска до первой записи.
Независимое чтение и подготовка новых входов доступны; подготовка с указанным managed-chat
или журналом проверяет их версию. Для продолжения старой задачи используй сохранённую копию
её выпуска и исходные пути.

## Предварительный просмотр

```sh
node --import tsx cli/main.ts preview-task project/workflow.json docs/exec-plans/active/selected.md TASK-ID /absolute/project
```

Команда только читает. Выход — полный план преобразования: версии, descriptor/procedure/rule
hash, исходные и новые байты карточки. Сохрани этот JSON вне проекта и проверь delta до записи.
Все источники и пути проверяются до формирования результата; произвольные shell-команды
из дескриптора не выполняются.

Legacy карточка без TaskNotes или с TaskNotes 1 явно переходит в **TaskNotes 2**. ID задаёт
владелец; для уже принятой карточки они должны совпасть. Неизвестные YAML-поля и ручной текст
сохраняются. При отсутствии заметок добавляется один блок; обычная карточка не превращается
во второй технический журнал. Текущий адаптер читает 1/2, прежний адаптер версии 1 отказывает
карточке 2 до записи. Неизвестные будущие версии не мигрируют автоматически.

## Подключение и отключение

```sh
node --import tsx cli/main.ts apply-task /absolute/connection-plan.json /absolute/external-journal /absolute/project
node --import tsx cli/main.ts disable-task /absolute/external-journal /absolute/project
node --import tsx cli/main.ts rollback-task /absolute/external-journal /absolute/project
```

`apply-task` — явное действие подключения одной задачи. Перед записью снова проверяются
дескриптор, версии/хеши процедур и правил, допустимость delta и фактический текст карточки.
Внешний journal сохраняет неизменяемый `backup.json` до изменения, затем состояние
prepared→enabled. Receipt содержит hash полного плана и историю переходов. Подключение
подтверждает миграцию; READY дополнительно требует реального LOAD и применимых правил роли.

`disable-task` останавливает использование подключения, сохраняя карточку и доказательства.
До команды контроллер прекращает собственную работу и writers; отключение записи в файле
само по себе не останавливает чужой процесс. Для полного обратного преобразования сначала
отключи задачу, затем выполни `rollback-task`: восстановятся точные исходные байты.
При изменённых правилах выключение и откат доступны, повторное включение требует новой сверки.
Резервная копия и receipts не удаляются.

Конфликт ручной правки, изменённый backup/state, несовместимая версия, иной delta, symlink/hardlink
или чужой `.pending` запрещают запись. Одинаковый завершённый результат повторно читается.
При частичной записи восстанавливается тот же план: уже записанная карточка не меняется повторно,
совпадающий pending state завершается. Конфликтующий pending сохраняется для разбора.
После аварийного завершения процесса остающийся writer.lock требует подтверждённой остановки
его владельца и явного разбора; слепого удаления блокировки нет.

## Execution schema 1 → 2

Это отдельная операция адаптера `workflowUpgrade`, а не побочный эффект чтения карточки.
`previewWorkflowUpgrade` проверяет исходный checkpoint, project/task/generation/owner и
подтверждение остановки writers, сохраняет весь source и target. Внешний JSON backup с SHA-256
нужно записать до `applyWorkflowUpgrade`. Применение проверяет backup, первичный stop receipt,
полную исходную revision и checkpoint; запись атомарна через прежний Store CAS.

Меняется только execution schema_version; findings, history, неизвестные поля, решения и IDs
сохраняются. Новый reader отвергает старую schema 1 до записи; прежний reader отвергает schema 2.
Rollback разрешён только из неизменённого результата этого преобразования, восстанавливает
исходный checkpoint и оставляет запись операции в Store. Новое действие, поколение или revision
требует отдельного разбора. После unknown сначала читай исходный operation ID; новый ID не
служит повтором. Эта миграция не выдаёт остановленному старому исполнителю новые права.

## Владелец и проверки

Current-chat Store до первого effect закрепляет путь и физические dev/ino каталогов Store
и evidence в chat-runtime.json версии 2; проверка повторяется перед effects и сохранением.
Пишущие вызовы сериализуются одной блокировкой канонического private parent, включая bootstrap.
Legacy Store без этого binding либо с прежней его версией не мигрирует от одного наличия успешных results: неизвестная
операция могла записать intent в другом каталоге. Чтение сохраняется, автоматическая запись
отклоняется с chat-runtime-binding-required. Старый backup, FAIL, карточка и receipts остаются;
новый изолированный квалификационный прогон не объявляется восстановлением старого.

В REQUIREMENTS допустимы assignment/sources/scope/outcome/criteria/card и обновлённые rules/procedures.
Они снова проверяются действующим fileRunInputs; LOAD и accepted_plan отзываются. Поля owner,
session/run/generation, requested/effective, permissions и прочие поля RunSpec через revision
передавать запрещено. Старые версии процедур не подменяются новым hash без полного чтения.

При явном `task-chat revise` изменённый дескриптор получает новый connection journal:
штатные preview/apply разрешены только для уже подключённой TaskNotes 2 с теми же project/task
и нулевой дельтой карточки. Старые backup/receipts остаются; Store, owner/generation и советники
не заменяются. Отключённая задача автоматически не включается. До нового полного LOAD и
planning допуск отозван. `load` показывает текущие тексты процедур, но не обновляет READY без revise.
Истёкшая lease при новых требованиях сохраняет прежнее требование подтверждённой границы хода;
свежее чтение процедур не выдаёт автоматическое продолжение или права прежнему writer.

Карта потребителей исторического перехода TaskNotes 1 / Execution 1; номера процедур
ниже относятся к исходной миграции, а не к текущему дескриптору:

| Договор | Владелец преобразования | Потребители и обратный путь |
| --- | --- | --- |
| TaskNotes без версии/1 → 2 | `cardMarkdown` и `FileTaskConnection` | `FileProjectCards`, `fileRunInputs`, `FileAuditCards`; CLI preview/apply/disable/rollback; точные исходные байты во внешнем backup |
| Execution 1 → 2 | `workflowUpgrade` | `workflowValidation`, исполнение/советы, SQLite checkpoint; прежний читатель отказывает версии 2, явный rollback восстанавливает весь checkpoint |
| Процедуры bootstrap/implementation/data-roles 1 → 2, task 1 → 3 | Единственные файлы процедур и реестр `workflow.json` | LOAD/READY сверяют версии и hash; старое доказательство сохраняет старые входы, новый сеанс читает новые |

Цель/проектный lifecycle — PLANS и карточка; техническое состояние — Store; процедура — её
единственный файл из [каталога процедур](procedures/README.md); предметные правила —
профильные владельцы подключённого проекта. Общие AGENTS/PLANS
содержат маршруты, а не копии процедур. Старые завершённые планы и чужие задачи не обходятся
массовым преобразованием.

`taskConnection.test.ts`, `workflowUpgrade.integration.test.ts` и прежние card/readiness/audit
тесты проверяют preview, обе версии, реальные записи и rollback, CAS, missing procedures,
ручной конфликт, частичные результаты, отказ доступа и unknown mutation. Живое обнаружение
маршрутов в свежем сеансе и проверка прежнего читателя требуют собственных первичных
доказательств AW10. Их точный locator здесь не закреплён; исторический источник ищется
через [manifest архива](https://github.com/Krivega/agent-workflow/blob/main/docs/evidence/README.md), текущие ограничения — в [разделе качества](https://github.com/Krivega/agent-workflow/blob/main/docs/quality/README.md).

Task 3 подключает принятый DEC-03-A: отмена всей задачи проецируется в отдельный `cancelled`
каталог. Поле `plans.cancelled` необязательно для старых дескрипторов, но без него отменённая
карточка не записывается. Старый reader не распознаёт такой статус. Откат отмены не является
продолжением: новое решение владельца и новый запуск обязательны.

## Минимальное хранение и явная очистка

### Общие входы, инструменты и архив

По [ADR-0058](https://github.com/Krivega/agent-workflow/blob/main/docs/design/decisions/inherited/0058-share-workflow-facts-tools-and-archive.md) новые
check proof/intent и записи совета используют общий пул списков входов. Это явный версионный
формат: читать через `readArtifactFile`, `readChatArtifact` или CLI `read-artifact`,
не через `JSON.parse` физических байтов. `request_reader` в поручении совета указывает команду
чтения полного проверенного JSON. Старые JSON и локальные пулы остаются читаемыми.

Для разрешённого переноса завершённой/остановленной задачи:
`node --import tsx cli/main.ts relocate-files /absolute/request.json`. Запрос содержит `schema_version: 1`,
`root` проекта, `namespace`, `storage: {root, grant}` и `relocation`:
`{operation_id, expected_revision, expected_generation, expected_owner, files}`.
`files` — точная карта относительных имён в namespace: `{hash, kind: archive|tool}`.
Инструменты должны находиться под `native-tools/`. Неправильная идентичность, активный lease,
effects, неизвестный check, изменённые данные и попытка перенести рабочее управление запрещены.

Архив находится рядом с namespace в `archives/<SHA-256 namespace>/`, общий кэш — в
`tool-cache/<SHA-256 состава набора>/`. Содержимое сначала копируется, синхронизируется и
сверяется; затем атомарно публикуются индекс и короткие обычные файлы-указатели. Повтор того же
запроса завершает прерванный перенос. Старые логические locator/hash остаются действительны
через reader; обычный `cat` указателя исходные байты не возвращает.
Каталоги кэша нельзя удалять как временные файлы задачи. Новый потребитель использует
существующий проверенный набор, сохраняя относительные пути шаблонов и зависимостей.

`resolve-tool` принимает `schema_version`, `root`, `namespace`, `locator` и возвращает путь,
SHA-256 и kind проверенного инструмента. Запуск старого архивного исходника требует явного
восстановления окружения; указатели не являются исполняемыми файлами.

Для полного восстановления в новый пустой каталог:
`node --import tsx cli/main.ts materialize-files /absolute/restore-request.json` с `schema_version: 1`,
`root`, `namespace`, `destination`, `storage: {root, grant}`. Требуются manage, остановленный
либо released/frozen Store и отсутствие незавершённых effects. Материализация держит
транзакцию Store, проверяет байты и возвращает manifest восстановленных файлов; индекс внешних
адресов не копируется. Для отката прежнего reader остановить writers и восстановить исходные
файлы в прежних логических местах из проверенного materialization и после полной сверки
убрать прежний `.workflow-files.json`. Абсолютные пути внутри
исторических доказательств не переписываются. Store-only backup не заменяет копию всей задачи.

### Минимизация Store

[ADR-0057](https://github.com/Krivega/agent-workflow/blob/main/docs/design/decisions/inherited/0057-normalize-workflow-facts-and-events.md) заменяет
обязательное хранение прошлых тел актуальным состоянием, квитанциями повторов и доказательствами
приёмки. Новые journal/managed записи используют минимальный формат. Старое чтение не пишет.
`AWRETAIN1` — checkpoint Store, `AWRETAIN2` — самодостаточный управляемый файл.

При первом штатном сохранении legacy managed-файла `saveManaged` сначала сохраняет
`<file>.originals/<SHA-256>/original`, все достижимые `shared-json/` и `manifest.json`.
Копия проверяется до замены рабочего файла; повреждение копии/источника прерывает преобразование.
Исходные файлы не удаляются. Повторное сохранение нового формата не создаёт новых копий прошлого.
Для восстановления остановить writer, сверить SHA-256 всех записей manifest и открыть `original`
через прежний reader в этом каталоге: рядом уже лежит необходимый `shared-json/`.
Возврат рабочего файла и pool выполняется только при остановленных writers.

Новый транспорт не дописывает старый сырой RPC-журнал: его исходные байты и артефакты сохраняются.
Текущая диагностика находится в `<journal>.diagnostics.json` (128 записей / 256 КиБ),
квитанции операций — в `<journal>.deliveries/`. Восстановление читает оба поколения;
коллизия или неизвестность запрещают retry. Квитанции нужны для продолжения, их нельзя очищать
вместе с диагностикой. Прежняя версия инструмента не распознаёт новые квитанции: откат с незавершённой
доставкой требует сверки нативной истории, слепое повторение недопустимо.

Для явно разрешённой очистки остановленного namespace:
`node --import tsx cli/main.ts retain-store /absolute/retention-request.json`.
Запрос содержит `schema_version: 1`, `root` workspace, `storage: {root, grant}` и `retention`:
`operation_id`, `expected_revision`, `expected_generation`, `expected_owner`, абсолютный `backup`
вне Store. Требуются manage, точная идентичность и истёкший lease либо release. Сначала проверяется
копия по SHA-256, затем под эксклюзивной транзакцией меняется состояние; после commit удаляются
недостижимые blobs и старые checkpoint событий. Повтор с тем же ID безопасен; изменённый запрос
отклоняется. Проверенные evidence и незавершённые effects сохраняются.

Если принятый план содержит старый совет, сначала сохранить его точные байты вне namespace,
подготовить минимальный сертификат с `retained_source` исходной ссылки и добавить `planning`:
`{previous, current, original}`. `current` имеет тот же locator и новый hash; `original` —
абсолютный путь проверенной копии с прежним hash. Обслуживание сверяет сохраняемый смысл и
атомарно меняет ссылку LocalRun. Управляемый request должен получить ту же новую ссылку.

Восстановление: остановить writers, проверить backup manifest/hash, вызвать
`restoreRetentionBackup` в новый пустой каталог и восстановить исходный план из `original`.
Не копировать отдельные старые blobs поверх нового работающего Store. Подробная история после
очистки доступна только из внешней копии. Новая схема не сокращает gates и не подтверждает
повторную содержательную приёмку прежней задачи.

## Совместимость внутреннего архива истории

[ADR-0056](https://github.com/Krivega/agent-workflow/blob/main/docs/design/decisions/inherited/0056-separate-workflow-history-from-current-state.md)
вводит `AWARCHIVE1` и явную запись `archive_version: 1`. Старое чтение ничего не изменяет.
Первое штатное сохранение владельца переносит полные события и исторические ответы в blobs;
оно дороже следующих записей и требует прежних CAS, поколения и действующего lease.
Перед обновлением используемого Store выполните существующий backup/restore процесс и сохраните
прежнюю версию инструмента. Исторические, завершённые и чужие Store массово не обходятся.
Откат — остановить writers и восстановить согласованную резервную копию прежней версией.
Старый reader отказывает новой оболочке; обратного молчаливого преобразования нет.

Обычные журналы возвращают рабочий индекс. Полные payload доступны через `{ archive: true }`,
отдельное событие — через `readEvent(hash)`; CLI `--full` и `read-artifact` старого артефакта
раскрывают доступную legacy историю. Новая квитанция CLI прошлых тел не содержит.
Архив результата переносится в каталог результата, а backup/finalization включает все его корни
и зависимости. Это внутреннее хранение, отдельные полномочия финализации и cleanup не меняются.
