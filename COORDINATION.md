# Координация AW7

Договор принадлежит [спецификации](docs/quality/agent-workflow-contracts.md#координация-и-relay).
[Процедура coordination](procedures/coordination.md) загружается до первого поручения
в версии дескриптора подключённого проекта. Условия подключения — в [каталоге процедур](procedures/README.md);
границы квалификации — в [разделе качества](https://github.com/Krivega/agent-workflow/blob/main/docs/quality/README.md).

## Состояние и полномочия

`beginCoordination` сохраняет неизменяемое назначение готового AW4 orchestrator: отдельное
разрешение каждого child, владельца, canonical workspace, пути, зависимости, критерий и
эффективный профиль. Общие договоры закреплены за одним executor интеграции. Права координатора
не включают техническую приёмку вместо исполнителя или запись в карточки дочерних задач.

`TaskCoordinationJournal` хранит `coordination.schema_version: 1` рядом с `local_run` и
`workflow`, сохраняет соседние поля и дописывает события через CAS/generation AW3. Чтение
восстанавливает состояние через исходные переходы; неизвестная версия не получает права записи.
Только исходный готовый координатор управляет этим журналом. Смена владельца — отдельный relay,
а не `RESUME` с другим run ID. Отмену coordination фиксируют до отмены готовности AW4.

После подтверждённого [relay](RELAY.md) версия 2 оборачивает исходный журнал, сохраняет его
историю и добавляет нового готового владельца и последующие события. Перенос требует того же
project/workspace/identity и поколения +1. Старый владелец не может дописать этот журнал.
Идентификатор каждой новой операции включает generation, run ID и номер события в текущем
журнале. Обнуление списка событий wrapper после relay не пересекается со старыми receipt
в том же SQLite. Существующие операции и исходные журналы не переписываются; повтор
сохранённого события остаётся идемпотентным. Это проверено через два последовательных переноса.

`FileCoordinationInputs` принимает явный перечень разрешённых рабочих деревьев. Проверяются
realpath, symlink/hardlink и существующие предки нового пути. Имя `src/a.ts` в двух различных
canonical roots не означает общий файл. Пересечение двух областей записи либо области child
с общим договором отклоняется; read-only области могут пересекаться. Разрешение на read-only
поручение не повышается до записи.

Пересечение определяется по полным путям workspace + path, включая вложенные рабочие каталоги:
`/repo` + `nested/file.ts` и `/repo/nested` + `file.ts` принадлежат одному файлу.

## Внешние действия

Контроллер сначала сохраняет `RESERVE`, затем вызывает разрешённый транспорт. Для ограниченных
читающих поручений используются существующие `DataRoutes`/`AppServerSessions`: отдельные
reservation/create/LOAD/send и первичные receipts AW5. `BIND` сверяет реальный session ID,
project/root, модель, effort, режим записи и отсутствие fork. Unknown создания восстанавливается
из первичной identity или сохранённого reading, а не повторным dispatch. Сам факт `RESERVE`
не создаёт чат; продуктовые чаты не запускаются автоматически. Процедура требует отдельного
подтверждения полномочий для каждого внешнего запуска.

События `OBSERVE` содержат session ID и монотонный cursor. Один event ID с другим содержимым
отклоняется; одинаковый cursor с противоречащим результатом также отклоняется. Более старый
cursor не откатывает наблюдение. Повтор завершения сохраняет принятый результат, не запускает
повторную работу. `observationWait` использует настраиваемый интервал (рекомендация 180–240 s),
возвращает максимум 60 s на вызов и ноль при доставленном событии.

Внешнее чтение может пересечься с отменой; перед записью проверяется неизменность журнала.
FAIL/stalled оставляют child открытым. UNAVAILABLE приостанавливает координацию без захвата
чужого владельца. CANCEL запрещает новые поручения и принятие результатов. Неизвестный dispatch
остаётся stopping до первичного подтверждения остановки; поздний BIND сохраняет identity для
остановки, поздний completion не становится приёмкой. STOPPED относится только к своему child
и требует receipt. Журнал сам не убивает процессы и не получает права на чужие PID.

Завершённый или принятый результат не заменяет остановку: каждый запущенный child остаётся
stopping до STOPPED. Исходные результаты и уже полученные stop receipts сохраняются при повторной
отмене. Старые журналы CANCEL без таких подтверждений восстанавливаются как cancelling;
события не переписываются, владелец дописывает недостающие STOPPED после проверки остановки.

## Приёмка и интеграция

`ACCEPT` требует точных scope/criterion, PASS проверки ребёнка и полного применимого перечня
входов. Перед принятием проверяются реальные файлы. Принятые этапы закрываются ссылками;
повторное выполнение не требуется при неизменных существенных входах.

`INTEGRATE` принимает только назначенного executor, все принятые child results, отдельный PASS
изменённых связей и PASS общего validate на одном перечне входов. Существенные входы каждого
ребёнка повторно проверяются в его рабочем дереве. Доказательства — реальные файлы с SHA-256;
контроллер отвечает за полноту manifest и правдивость результата команды. Политика переходов
не интерпретирует произвольный текст журнала как доказательство успешного теста.

Проверки: `coordination.test.ts`, `coordinationPersistence.integration.test.ts`; общий профиль
`yarn test`, затем `yarn validate`. Живой стенд использует два ограниченных
читающих сеанса, один внешний контроллер интеграции и настоящие SQLite/App Server. Проверки
отказов с искусственными событиями отдельно от живых результатов. Relay и остановка реального
пишущего предшественника проверяются в AW8.
