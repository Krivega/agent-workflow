Владелец договоров — [ADR-0047](https://github.com/Krivega/agent-workflow/blob/main/docs/design/decisions/inherited/0047-isolate-agent-workflow-in-tools.md)

Область проверки — [профиль инструмента](https://github.com/Krivega/agent-workflow/blob/main/docs/testing/profiles/agent-workflow.md).
Явное подключение и текущая граница допуска описаны в [каталоге процедур](procedures/README.md)

## Сборка контроллера

`beginExecution`/`advanceExecution` принимают `WorkflowJournal` и `WorkflowInputs`.
`TaskWorkflowJournal` сохраняет `workflow.schema_version: 1` в checkpoint AW3, сохраняя
`local_run` и остальные соседние поля. В AW6 вложенная схема `execution.schema_version` повышена до 2; оболочка workflow и SQLite сохраняют версию. Старые версии execution отклоняются до записи; явный перенос относится к AW10. При чтении и записи проверяется вложенная схема выполнения.
Переход связан с готовым AW4 executor: task/run/project/generation, writer и отсутствие pending
projection проверяются до действия и при записи того же checkpoint. Отмена AW4 запрещает done. Конфликт версии или
поколения запрещает запись; повтор уже сохранённого события возвращает прежний результат.
Сравнение JSON учитывает значения и порядок массивов, но не порядок ключей объектов.

`FileWorkflowInputs` снимает SHA-256 фактических байтов файлов. Перечень содержит явные файлы,
полностью просматриваемые каталоги и правило их обнаружения. Владелец подтверждает полноту
существенных входов: требования, влияющие зависимости, проверки, конфигурация и среда должны
быть представлены файлами. Автоматического вывода полноты по импортам нет. Добавление/удаление
обнаруживаемого файла меняет набор; недоступный вход даёт unknown. HEAD сам по себе не входит
в сравнение применимости. Внешние файлы evidence доступны только внутри отдельно заданного root.

## Четыре маршрута данных

`directEvidence` читает известный ID и exact revision либо head прямо из Evidence Store.
`DataRoutes` обслуживает unknown-source/explorer, large-source/raw-data-reader и
unknown-evidence/evidence-explorer. Brief строится из разрешённых полей, всегда с
`fork_turns: none`; поля истории родителя не копируются. Reader получает диапазоны, selection,
classification, completeness и continuation; evidence-explorer — task_id и budget.

Контроллер сохраняет reservation до создания сеанса, identity до LOAD и намерение отправки
до модельного хода. Сохранённый delivery ID включается в запрос. Потерянный ответ `turn/start`
восстанавливается только по единственному совпадающему ходу в первичной истории. Отсутствие
совпадения оставляет unknown и запрещает повтор отправки. Неизвестный исход оставляет состояние для восстановления и запрещает
повторное создание под прежним ID. `recover` принимает восстановленный identity и первичные
receipts; при невозможности восстановить identity новый `start` получает новый ID и явную
ссылку `restart` на прежний запуск/checkpoint. Исходный отказ остаётся в хранилище.

`poll` возвращает running без перезапуска. `followUp` возобновляет тот же identity; перед
отправкой и приёмом ответа источники сверяются. Смена revision требует доказательства новой
выборки; старый continuation reader нельзя переносить автоматически. Неполный ответ сохраняет
coverage и continuation, не становится полным PASS всей задачи.

`AppServerSessions` использует только управляемые read-only сеансы с подтверждённым model/effort,
выключенной сетью и без fork. Транспорт получает явный binary/args/cwd и сохраняет первичные
request/response/events. Запросы внешнего подтверждения отклоняются; потеря канала даёт unknown.
В LOAD передаются только locator/hash каждого выбранного файла; вложенные поля истории
или готовое содержимое не копируются. LOAD проверяется по полному содержимому и хешам в успешном выводе инструмента, а не по заявлению
модели. Receipts сохраняются по хешу содержимого. Пустой сеанс без первого хода может не иметь
восстанавливаемого rollout; этот случай различается с транспортной неопределённостью.

Для советников [текущего чата](CURRENT-CHAT.md#советники-текущего-чата) используется отдельный
управляемый create/thread/start с подтверждённым read-only, без сети и родительской истории.
Наблюдение выполняется через transcript и thread/read без resume. LOAD фиксируется через
load/observeLoad; точное поручение связывает project/identity/parent_run, assignment, фазу,
роль, target и LOAD. Независимая identity, понятное имя и эффективные права проверяются отдельно.
Первый LOAD хранит receipt создания с `operation=thread/start` и пустыми turns. Его ссылка
в `LoadReceipt.origin` связывается с первым ходом нативной истории и сохраняется при новых LOAD;
`native` указывает на текущую загрузку. Ответ от resume без доказательства создания не допускается.

Процессный контроллер передаёт отключение hooks/apps/plugins/memories/multi_agent и MCP в
аргументах своего отдельного App Server. Он не меняет пользовательский config. Проверенный
клиент и фактические профили фиксируются в evidence; недоступная конфигурация не подменяется.
Публичная основа протокола — [документация App Server](https://learn.chatgpt.com/docs/app-server).
При расхождении проверяется экспорт схемы установленного клиента.

## Советы и завершение

[Процедура council](procedures/council.md) загружается до первого reviewer в точной версии
из дескриптора подключённого проекта. Назначение adviser требует подтверждённой загрузки.
Историческое подключение AW4 без council не даёт допуска нового советника.

Selection содержит все роли из `council.profiles` подключённого проекта, явный true/false/null trigger, причину, версии требований и существенные входы каждой роли.
Старый selection без новых ролей требует явного обновления по
[договору применимости](docs/quality/agent-workflow-contracts.md#применимость-совета).
Пропущенный trigger недопустим; смена scope или входов роли открывает её оценку заново. Unknown,
отсутствующий reviewer, running, частичный ответ, NOT RUN и FAIL блокируют допуск; mandatory
роль не может ответить N/A. Применимость устанавливает ответственный контроллер по фактическим
изменениям и источникам, а не автоматически по имени файла. Новые требования возвращают
затронутые роли к planning. Acceptance получает точный scope/base/diff и manifest.

XState задаёт planning → implementing → review → done. M1 допускается при совпадении identity,
точного delta, ссылок и применимости принятого материала к текущему target/manifest.
Файлы доказательств M1 сверяются при записи, ссылки входят в Result; новая семантика требует planning.
Review сохраняет измеренный реальный baseline и результаты проверок. Fixture-only baseline
отклоняется. Для кода обязательный gate validate нельзя убрать при создании выполнения.

Finding сохраняет первоначальные поля, FAIL и историю исправлений. Один correction ID даёт
один раунд независимо от числа голосов и HEAD. Закрытие требует выполненного условия, evidence
и PASS ответственного reviewer. Повторная приёмка идёт тому же adviser по новому delta;
работающий reviewer не пересоздаётся. Назначения сохраняются между исправлениями. Замена
требует отдельного REPLACE_REVIEWER с первичным подтверждением утраты identity и checkpoint. Ранее принятые дочерние результаты переиспользуются
с исходными scope/criterion/evidence и manifest. Существенные входы проверяются на каждом
последующем переходе; отдельный INVALIDATE_CHILD снимает применимость до новой проверки.
Новое замечание в дочернем scope, включая неблокирующее, также отзывает прежний результат.
Закрытие замечания не восстанавливает его автоматически: нужен повторный REUSE с проверкой.

Result записывается только после обязательных проверок, приёмки и решений человека, без
открытого blocker или непринятого compromise. Он сохраняет baseline/check/council links и
точный принятый дочерний scope. Новая приёмка или изменение дочерних результатов сбрасывают
прежний Result; DONE повторно проверяет также отдельные файлы дочерних доказательств. DONE требует уже сохранённого Result; перед сохранением перехода
проверяются актуальные входы и доступность связанных доказательств. Вызов библиотеки сам по себе
не даёт полномочий на модельные сеансы, запись внешних данных или публикацию.
