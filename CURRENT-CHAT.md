# Текущий чат Codex

Режим реализует [ADR-0048](https://github.com/Krivega/agent-workflow/blob/main/docs/design/decisions/inherited/0048-drive-agent-workflow-from-codex-chat.md).
Он обслуживает одну явно выбранную задачу; текущий агент остаётся исполнителем.
Процедуры и [descriptor](project/workflow.json) сохраняют владение процессом.

## Запуск через Temporal

В проекте с действующей политикой назначения версии 2 `task-chat start` принимает готовый
вход SDK версии 12 и регистрацию Worker. Команду запускают из корня рабочей копии.

```sh
yarn --silent agent-workflow task-chat start --temporal-input input12.json --temporal-registration /absolute/private/registration.json
```

Вход содержит строгий `SubstantialPlan` с хешем, отдельные запросы планирования и приёмки,
профиль исполнителя, исходную проверку и ранее выданный `startAdmission`.
[Порядок подготовки Input12](docs/temporal-sdk.md#подготовка-input12-для-task-chat-start) использует
`prepareTaskStartAdmission` и первичную запись поручения. Запросы и допуск адресуются
по SHA-256 и размеру в хранилище зарегистрированного Worker. Состав ролей берётся из
дескриптора Temporal, применимость задаётся отдельно в обеих фазах.

Внешний приватный файл регистрации содержит `schemaVersion: 1`, `address`, `namespace`,
`taskQueue` и `registration`. В `registration` указываются точный дескриптор `project`,
`hostId`, `owner`, `generation`, канонические `workspaceRoot` и `artifactRoot`, `commands`
и `taskBackend: "required"`. Проверка допуска читает первичный журнал текущего чата Codex.

Перед созданием назначения команда проверяет подготовленные входы и первичный допуск.
При успешном ответе выводит `status: "accepted"`, `backend: "temporal"` и `workflowId`.
Назначение закрепляет адрес Temporal, namespace и очередь. Повтор с тем же входом и
назначением использует тот же Workflow ID. При неизвестном исходе сохраняй запрос,
регистрацию и идентификатор. Подробности исполнения описаны в [договоре SDK](docs/temporal-sdk.md#исполнение-и-независимое-завершение-b1).

## Штатный вход без JSON

До включения политики Temporal действует этот вход. Запускай `agent-workflow task-chat` из
корня подключённого проекта. Примеры ниже используют
команду Yarn для установленного пакета. Пользователь ставит задачу
в чате; предметную карточку и предложение готовит агент. Поддержаны компактная карточка
(`Цель`, `Границы`, `Критерии`) и полный ExecPlan (`Результат и не-цели`, `Критерии приёмки`).
Технические запросы, ID и хеши инструмент формирует сам. Агент составляет
[карту применимости совета](docs/current-chat/council.md#карта-применимости-совета); пользователь не готовит JSON или команды.
В записи критерия `- [ ] ID: описание` именем программной проверки служит ID; полное описание
остаётся в карточке и RunSpec. Без явного префикса сохраняется прежнее имя проверки.
`--human` по-прежнему использует точный текст критерия и сохраняет прежние человеческие gate.
Это позволяет исполнять подробные критерии без пробелов и пунктуации в техническом ID.

```sh
yarn --silent agent-workflow task-chat start --state /absolute/external/run --card docs/exec-plans/active/task.md --plan proposal.md --council-selection roles.json
yarn --silent agent-workflow task-chat load --state /absolute/external/run
yarn --silent agent-workflow task-chat start --state /absolute/external/run
yarn --silent agent-workflow task-chat continue --state /absolute/external/run
yarn --silent agent-workflow task-chat revise --state /absolute/external/run --plan proposal-v2.md --affected criterion-id --council-selection roles-v2.json
```

`start` создаёт подключение выбранной карточки, отдельный Store и сохраняемые параметры.
`LOAD_REQUIRED` означает: вызывать `load`, пока он не перестанет выдавать файлы, затем повторить
исходное действие. Каждый вызов читает только ещё не подтверждённые файлы текущего marker.
Вывод LOAD сохраняй целиком в успешном нативном CommandExecution; достаточный лимит вывода
особенно нужен для большого файла правил. Внутреннее чтение и ответ команды до появления
этого события не дают READY. Новый turn/сжатие, revision и точный состав правил получают новый marker.
Изменение правил не принимает прежний обрезанный LOAD; новый marker требует полного свежего чтения.

`load --load-bytes 96000` увеличивает партию без дополнительных модельных переходов.
По умолчанию бюджет — 24000 байт UTF-8; допустимо 1000–512000. Бюджет включает JSON-экранирование,
метаданные и завершающий перевод строки, в том числе у первой строки. Размер части уменьшается
до выполнения бюджета; если не помещаются даже метаданные с одним символом, команда отказывает
с `chat-load-budget-too-small`, не подтверждая чтение. Большие файлы выдаются последовательными частями до 8000 символов с `offset` и
`length`, по одной части на вызов. LOAD подтверждает файл только после всех частей: совпадают
порядок, длина, точный текст и полный hash текущего источника. Старый полный вывод совместим. До вызова обеспечь достаточный лимит нативного вывода
и внешней обёртки: усечённый вывод не подтверждает LOAD. Увеличивай партию, только когда
можешь прочитать весь вывод; команда по-прежнему выдаёт отдельную строку для каждого файла.

После LOAD `start` сам создаёт независимые read-only сеансы, устанавливает имена, подтверждает
профили и первичный LOAD, отправляет и дожидается поручений, принимает planning и открывает
execution. Роли и ссылки выводятся при создании; повтор использует сохранённые сеансы.
`--binary` задаёт установленный Codex CLI, если `codex` отсутствует в PATH.
Новый `start` и `revise` требуют `--council-selection` с оценкой каждой роли; молчаливого
запуска всех ролей нет. Прежний явный `--skip-role role:предметное-основание` совместим:
он исключает указанные роли, остальные получают общий набор входов. Эти варианты не смешиваются.
Причина исключения сохраняется и не заменяет предметную оценку применимости.
В существующем запуске `start`, `continue` и `load` разрешают повторить прежнюю неизменную
карту или прежние исключения. Другой состав или путь карты требует `revise`; изменение байтов
прежней карты также блокирует продолжение с этой картой до пересмотра.
Перед советом служебный `prepare-chat` сохраняет principal в WAIT и привязку управления;
READY и реализация этим не разрешаются. Поэтому даже первоначальный FAIL planning допускает
штатный `revise`, сохраняя прежних советников и заключения.

`--source file` добавляет стабильное требование в RunSpec; `--target file` — изменяемый исходник
в manifest выполнения. Повторяемый `--human` задаёт точный текст критерия, требующего решения
человека. `validate` всегда остаётся обязательной программной проверкой. Ни роль, ни команда
не дают дополнительных прав реализации, публикации, установки или передачи другому чату.

`continue` читает актуальный Store, проверяет прежнего owner и pending effects, подтверждает
новый профиль/LOAD и выполняет существующий RESUME, включая восстановление истёкшего lease.
При действующем сроке каждый успешный `continue` продлевает его до 30 минут от вызова,
включая повтор неизменного RESUME без дублирования истории. Повтор проверяет текущий профиль,
owner, CAS и pending effects; сохранённый READY не заменяет эти проверки. При долгой работе
вызывай `continue` до истечения срока, например перед следующим этапом или после сжатия.
Автоматический ход без нового человеческого сообщения использует последний уже принятый
источник RESUME в том же активном чате. Он сохраняется как `previous_source_turn` и проверяется
по первичной истории: новый содержательный человеческий текст отзывает такой повтор,
paused/cancelled и новые REQUIREMENTS его не принимают. Свежий профиль/LOAD, завершение
прежнего хода, Store/CAS и известные исходы операций остаются обязательными.
При автоматическом продолжении без сжатия LOAD может повторно использовать принятые
первичные чтения: ссылки и хеши CommandExecution, тот же thread/workspace/профиль и текущие
байты каждого правила сверяются заново. Старые чтения до `compacted`, изменённые источники
и непригодные receipts не используются. Уведомление о завершении `SubAgentActivity` после
границы хода сохраняется в истории и не является поздней операцией записи; поздние starts,
команды, изменения файлов и MCP-операции по-прежнему блокируют продолжение.
Поздняя терминальная квитанция собственной фоновой команды допустима только при первичных
`started_at_ms` до границы хода и согласованном `completed_at_ms`, том же thread/turn/workspace,
уникальных command/process ID и точном совпадении команды и process ID с исходным нативным
code-mode вызовом и его результатом запуска. Порядок результатов связывается с отдельными
прямыми последовательными `text(await tools.exec_command(...))` и `text(await tools.write_stdin(...))`;
синтаксис разбирается установленным TypeScript, аргументы должны быть буквальными значениями.
Параллельная или иная неоднозначная форма не считается доказанной автоматически. Квитанция становится
источником continuation; исходная граница и история сохраняются. Все наблюдённые фоновые сеансы
требуют терминального результата. Новые поздние запуски, FileChange/MCP writers, неизвестные
квитанции, подмена, повтор и незавершённые операции по-прежнему блокируют продолжение.

При приёмке исходные ID, scope и condition замечания сохраняются. Неблокирующее подтверждение
его устранения от владельца с PASS остаётся в полной истории ответа; оно не заменяет определение
уже доказанно закрытого замечания. Само закрытие по-прежнему требует исходного condition,
истории исправления и текущего PASS владельца с точным evidence. Новый blocker, иной владелец,
FAIL и незакрытое условие этим правилом не исключаются.
Перед правкой связанной карточки в новом ходе сначала восстанови владельца через `continue`;
изменённые стабильные входы не обходят проверку прежнего scope. Пауза требует явного `continue`,
`start` и `revise` её не снимают.
`revise` сохраняет REQUIREMENTS с первичным человеческим источником, новой revision и REPLAN;
применимость ролей оценивается заново через `--council-selection` либо явный `--skip-role`.
Человеческие проверки неизменившихся критериев сохраняются; новые добавляются через `--human`.
После нового LOAD повторный `start` получает заключения затронутых прежних советников с сохранением origin
и истории; неизменные полные PASS сохраняются. Предыдущие требования и план сохраняй отдельными файлами; новую редакцию передавай
новым путём. Неизвестный исход create/send остаётся конкретным отказом без слепого повторения.
Если стабильный источник уже изменён и срок прежнего владельца истёк, `revise` проверяет
новый человеческий REQUIREMENTS, прежнюю завершённую границу, профиль, полный LOAD и исходы
операций до восстановления срока. REQUIREMENTS/REPLAN и RESUME сохраняются одним checkpoint;
до нового planning состояние остаётся WAIT. Обычный `continue` с изменённым источником
по-прежнему отклоняется; права, owner/generation и правила неизвестных эффектов не меняются.
Подготовленную редакцию planning до отправки нового LOAD/поручения можно заменить только при
точном совпадении сохранённого завершённого answer turn прежнего советника с его write-ahead
progress, при load_pending=false и проверенном доказательстве ответа. Начатая или неизвестная
доставка блокирует замену. Прежний PASS не принимается за новую редакцию.
Нативный `interrupted`/`failed` сохраняется отдельным доказательством; следующий вызов делает
одну новую попытку заключения в том же сеансе. Неизвестное состояние к такому повтору не допускается.

Параметры и намерения находятся во внешнем `--state`, принятый planning — в
`tmp/agent-workflow/chat-*/planning-*.json`. Store остаётся владельцем технического состояния.
Краткий результат содержит ссылку/hash полного доказательства и путь `request.json` для
совместимых низкоуровневых операций. Ранее созданные вручную запуски автоматически не
перепривязываются; прежние команды и адресные договоры сохраняются.

## Сообщения и полномочия

Агент понимает естественный текст и передаёт проверяемую операцию; инструмент не угадывает
полномочия по ключевому слову. Каждая операция содержит исходное сообщение/источник, task ID,
thread/turn, ожидаемые revision и generation, неизменный operation ID и проверяемый payload.

| Сообщение | Операция и условия | Отказ / отсутствие эффекта |
| --- | --- | --- |
| «Начни задачу через agent-workflow» | Выбор одной карточки, preview/apply; сохранить цель, границы и критерии | Неоднозначный выбор требует вопроса; информационный вопрос не подключает задачу |
| «Приступай» | Реализация только после принятого planning, действующего LOAD/READY и разрешения scope | Подключение и разрешение сами по себе не дают READY |
| «Учти …» | Новая revision требований; сохранить старые FAIL; отозвать только затронутые проверки через существующий REPLAN | Нельзя скрыть изменение под прежней приёмкой |
| «Статус» | Прочитать карточку, checkpoint, обязательные условия и ближайшее действие | Никаких create/resume/write при чтении |
| «Приостанови» | Сохранить paused и WAIT LocalRun; прекращение собственных writers подтвердить отдельно | Lease и отсутствие вывода не подтверждают остановку |
| Прерывание хоста | При следующем ходе сверить незавершённые операции и отметить interrupted | Не трактовать как отмену или успешную паузу |
| «Продолжай» | Та же session identity; новый подтверждённый turn/profile/LOAD, сверка входов и pending operations | Чужой сеанс или неизвестный эффект блокирует продолжение |
| «Отмени» | Отдельный cancelled, причина и невыполненный scope; проверенный stop receipt | Поздний ответ не возобновляет отменённое; возврат требует нового решения и запуска |
| «Да» / решение | Точный question ID, revision требований и разрешённая операция | Ответ старому/другому вопросу отвергается |

Разрешения задаются поручением, а не моделью, навыком или профилем хоста. Профиль фиксирует
наблюдаемую модель, effort и права; разрешённые RunAction задаются отдельно и не расширяются
при продолжении. Read-only поручение не создаёт подключение и не меняет код. Внешние действия,
координация и передача требуют соответствующего разрешения; сохраняется уже выданное.

## Выполнение и свидетельства

Planning готовится в чтении до READY и принимается существующим council; принятое evidence
переиспользуется execution. Результаты ролей проходят существующие проверки identity, scope,
профиля и источников. Арбитр, аудитор и координатор не заменяются самостоятельной проверкой.
Если обязательная роль недоступна, успешный Result запрещён.

Фактический процесс проверки сохраняет команду, exit code, полный журнал и manifest до/после;
изменение входов отзывает применимость даже при exit 0. Полноту manifest подтверждает владелец.
Проверка и текст роли — разные свидетельства. Execution владеет REVIEW/ACCEPT/CORRECT/RESULT/DONE;
LocalRun — READY/WAIT/CANCEL; projectLocalCard — проекцией и конфликтами revision. Новый маршрут
не дублирует эти машины. DONE без закрытых обязательных условий и успешной проекции не сообщается.

## Проверка договора CH2

- Обычный случай: явная новая задача выбирает одну карточку, сохраняет её identity и разрешённый
  scope; подтверждённый профиль и полный LOAD допускают только разрешённые действия.
- Пограничный: повтор «продолжай» после сбоя использует прежний operation ID; неизвестный эффект,
  disabled, чужой turn или изменённая revision оставляют зависимую операцию открытой.
- Неприменимый: «Как устроен agent-workflow?» и «проведи анализ, код пока не меняй» не создают
  карточку, подключение, пишущего исполнителя или модельный ход самому себе.

Это проверка согласованности договора; живые доказательства и границы квалификации принадлежат
плану CH3–CH8.

Подробности ниже выбираются по действию. Прямая ссылка не заменяет обязательное чтение
процедур и правил с подтверждённым LOAD. Полномочия и границы квалификации сохраняются.
