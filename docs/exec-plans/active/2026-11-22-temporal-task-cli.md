# CLI agent-workflow от справки до результата задачи

- **ID:** `PLAN-20261122-TEMPORAL-TASK-CLI`
- **Статус:** `active`
- **Приоритет:** `P1` по [критериям](../../PLANS.md#приоритеты), воспроизведена ошибочная диагностика до старта
- **Владелец:** сопровождающий CLI agent-workflow
- **Начат / обновлён:** 2026-11-22
- **Следующий пересмотр:** 2026-11-25

## Результат и границы

Из справки владелец узнаёт, как подготовить и запустить задачу Temporal. До старта видит
последствия выбранной команды. После ответа `accepted` по возвращённому `workflowId`
может узнать состояние и прочитать итог через CLI в контексте зарегистрированного проекта.
При отказе владелец и вызывающий скрипт понимают, можно ли исправить ввод или нужно
сверить исход уже отправленной операции.

## Порядок реализации и первая поставка

1. Первым выпустить исправление P1 (этап 1, CHECK-01–02). Ошибка ввода до старта
   получает точную подсказку, потеря ответа после отправки сохраняет неизвестный исход.
2. Затем вести параллельно этап 2 CLI (чтение по ID), этапы 1–3
   [предпросмотра](2026-11-22-temporal-start-preview.md) и этап 1
   [шаблонов](2026-11-22-project-task-templates-and-routes.md) (проектирование договора).
   Чтение по ID опирается на существующую задачу Temporal.
3. Этап 3 CLI подключить к сводке, как только доступны проверенные данные предпросмотра
   и их привязка к старту. Приёмка поставки объединяет этот путь с чтением по ID.

Для разработки рекомендован `gpt-6.2-sol/medium` на справку и диагностику,
`gpt-6.2-sol/high` на состояние, итог и последствия старта. Для независимой проверки
границы отказа и сквозного сценария — `gpt-6.2-astra/high`. Это профили работы над CLI.
Справка, просмотр и чтение задачи выполняются без вызовов модели.

**Сквозная приёмка первой поставки.** Владелец обычной карточки без шаблона находит
команду через справку, видит фактический план, проверки критериев, пробелы и последствия,
запускает тот же вход и получает `workflowId`. По нему читает фазу, причину ожидания,
а после завершения — итог и подтверждающие материалы. Проверить также ошибочный ввод
и неизвестный исход старта. Состав поставки — CHECK-01–07 этого плана и
CHECK-01–05, CHECK-08–09 предпросмотра. Версии правил, отчёт о токенах и проектные
маршруты выходят отдельными приращениями.

## Исходное состояние

- [Общая справка](../../../cli/runAgentWorkflow.ts) пропускает `task-chat`.
  В рабочей копии вызов `task-chat --help` дал код 1 и `task-chat-action-required`.
- Вызов `task-chat start --temporal-input` без значения завершился при
  [разборе аргументов](../../../cli/taskChatCommand.ts). Диагностика вернула
  `status: unknown` и предложила искать квитанцию. Назначение на этом шаге ещё не создаётся.
- [Клиент запуска](../../../src/client/localTask.ts) возвращает идентификатор.
  [Процесс задачи](../../../src/workflows/taskExecution.ts) предоставляет запрос
  `localTaskStatus`; [клиент SDK](../../../src/client/taskExecution.ts) умеет читать
  данные о решениях человека. Для завершённой задачи нужен сохранённый итог выполнения.

## Этапы и критерии приёмки

### 1. Исправить справку и диагностику независимо от остальных этапов

- [ ] CHECK-01: Вызовы `agent-workflow --help` и `agent-workflow task-chat --help` через
  штатную точку входа завершаются с кодом 0 без регистрации и обращения к серверу.
  Первая справка ведёт к командам задачи, вторая показывает синтаксис Temporal и область
  применимости прежних команд с `--state`. Примеры проверяются через тот же разбор аргументов.
- [ ] CHECK-02: Неполный `start` даёт ненулевой код, статус `refused`, точную причину
  и синтаксис с обоими обязательными параметрами. При потере ответа после отправки старта
  без подтверждения исхода CLI сохраняет `unknown` и указывает, как проверить исходный
  запуск. Тесты различают эти случаи по границе фактического действия. Сохранить совместимость
  полей ответа, включая `reason` и `next_action`.

### 2. Дать команды чтения по workflowId

- [ ] CHECK-03: Ответ `accepted` сохраняет прежние поля и показывает точную команду чтения
  состояния по выданному ID. Через CLI видны текущая фаза, причина ожидания или остановки
  и доступное владельцу следующее действие. Проверить выполнение и ожидание решения человека.
- [ ] CHECK-04: По тому же ID после завершения доступны итог, причина неуспеха при её наличии
  и ссылки на подтверждающие материалы. Проверить успешное завершение, отмену и запрос итога
  во время исполнения. Различать неизвестный ID в доступном namespace и недоступный сервер.
  При продолжении Temporal читать актуальный запуск в рамках исходного `workflowId`.
- [ ] CHECK-05: Повторное чтение статуса и итога не меняет задачу и не вызывает модель.
  Использовать доверенную регистрацию и существующие проверки проекта. Чужой ID или
  неподходящая регистрация не раскрывают материалы задачи и содержимое приватной регистрации.

### 3. Показать последствия старта в предпросмотре

- [ ] CHECK-06: В [существующей сводке подготовленного запуска](2026-11-22-temporal-start-preview.md)
  видно, что делает сам просмотр, что выполняет команда старта и что позднее может выполнить
  Worker. Для одного подготовленного входа показать резервирование назначения, обращение
  к Temporal, условия вызова моделей, область записи исполнителя, перенос результата
  и запускаемые проектные проверки. Условные действия снабдить условием, например успешной
  исходной проверкой перед записью. Чтение сводки не резервирует назначение и не расходует допуск.
- [ ] CHECK-07: Предпросмотр и старт используют один закреплённый вход. В испытании с успешным
  стартом и в испытании с отказом исходной проверки сопоставить показанные последствия с
  наблюдавшимися действиями. Изменившиеся значимые данные обнаруживаются до первого эффекта.
  За подготовку и привязку сводки отвечает связанный план, за описание последствий в CLI — этот.

## Проверки и риски

Проверить справку, коды возврата и JSON через [интеграционные тесты CLI](../../../tests/cli.integration.test.ts);
отказы и границы эффектов — через [тесты команд чата](../../../tests/taskChatCommand.test.ts).
Состояния и итог проверить через штатный CLI на стенде Temporal с зарегистрированным проектом,
включая закрытый запуск. Обновить [инструкцию текущего чата](../../../CURRENT-CHAT.md).
Для изменений кода выполнить полный `yarn validate` с четырьмя показателями покрытия 100%.
Раздельно зафиксировать результаты имитации потери ответа и стендового чтения.

Главные риски — предложить повтор при неподтверждённом старте, принять недоступность сервера
за отсутствие задачи или показать запланированное действие как уже выполненное.
