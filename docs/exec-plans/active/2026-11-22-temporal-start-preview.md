## Результат и границы

Перед стартом владелец видит в текущем чате карточку, рабочую копию, область записи,
исполнителя, роли приёмки и обязательные проверки. Сводка строится по подготовленному
входу версии 12 и регистрации проекта. Просмотр доступен локально и не расходует
разовый допуск. Для старта по тому же поручению достаточно уже выданного разрешения.

Первым поставляется предпросмотр штатного запуска из текущего чата. Затем владелец получает
сведения о происхождении правил приёмки и отчёт о фактическом расходе токенов. Рабочее
переключение T6 и введение жёстких лимитов расходов остаются за пределами плана.

Для задач с шаблоном сведения о его версии, уточнениях карточки и передачах между ролями
добавит [план проектных шаблонов и маршрутов](2026-11-22-project-task-templates-and-routes.md).

Какие действия старта показать в этой сводке и как сверить их с исполнением, описывает
[план доработки CLI](../verifying/2026-11-22-temporal-task-cli.md).

### Ответственность по этапам

В начале предпросмотра вывести число критериев без назначенной проверки и перечислить их
с формулировками из карточки. Ниже для каждого этапа показать участника, его задачу и
критерии, к которым она относится. Для программной проверки указать команду и кто её
запускает, для ревью — роль и предмет заключения, для решения человека — кто его принимает.

Сверять назначения с полным списком критериев карточки. Использовать ID, если он задан,
иначе сохранять исходную формулировку. Один критерий может иметь несколько проверяющих.
Участие в планировании и поручение написать код сами по себе не подтверждают назначение
проверки результата. Учитывать только явные связи в подготовленном задании. При отсутствии
связи показать «Проверяющий не назначен», в том числе когда в плане есть общая команда
`validate` или применимая роль без поручения проверить данный критерий.

### Как будет проверен каждый критерий

Для каждого критерия вывести рядом три сведения из карточки и подготовленного задания.
Если проверяющих несколько, для каждого указать его доказательство и условие успеха.

| Критерий карточки (пример) | Кто проверяет и на каком этапе | Какое доказательство потребуется | Что считается успехом |
| --- | --- | --- | --- |
| Повторный запрос возвращает прежний запуск | Архитектор при приёмке | Квитанции первого и повторного запросов | Обе квитанции содержат один и тот же `workflowId` |

До исполнения эти поля описывают предстоящую проверку. Если часть сведений отсутствует,
сохранить известные поля и вынести в начало сводки критерий с точным пробелом:
«Проверяющий не назначен», «Доказательство не указано» или «Условие успеха не задано».

## Зависимости и граница первой поставки

После исправления справки и диагностики (этап 1 [CLI](../verifying/2026-11-22-temporal-task-cli.md))
этапы 1–3 этого плана идут параллельно с чтением состояния по `workflowId` и проектированием
[шаблонов](2026-11-22-project-task-templates-and-routes.md). Для обычной карточки достаточно
нынешнего подготовленного входа. Сначала выделить данные и привязку к старту, затем
подключить этап 3 CLI с описанием последствий. Сверку неизменности входа использовать общую.

Первая поставка включает CHECK-01–05 и CHECK-08–09: видны рабочая копия, роли, проверки,
доказательства, условия успеха и пробелы по критериям. В общем сценарии CLI владелец
находит команду, проверяет сводку с последствиями, запускает тот же вход и читает итог по ID.

Этапы 4–5 — отдельная ветка, совместимая с разработкой шаблонов. Сначала проверить версию
реально выполненной команды (CHECK-06). Данные о расходе можно собирать параллельно;
разбивку по этапам и повторам (CHECK-07) удобно вывести после появления команды результата.
Обе проверки остаются критериями завершения всего плана.

Для разработки сводки, привязки и отчётов рекомендован `gpt-6.2-sol/high`, для
независимой сверки показанных и фактических действий — `gpt-6.2-astra/high`.
Обычный предпросмотр выполняется локально без модели.

## Сводка для продолжения

Предпросмотр и привязка к старту реализованы. `task-chat preview` читает подготовленный
вход, проверяет допуск и возвращает сводку с `previewDigest`. Старт с этим хешем
сверяет значимые данные перед резервированием назначения. В план версии 2 добавлены
необязательные явные назначения проверок `criterion_checks`.
Профильные тесты покрывают детерминированность, пробелы, команды стадий и реальные
квитанции проверок при успехе и отказе исходной проверки. Сквозная приёмка первой
поставки остаётся в [плане CLI](../verifying/2026-11-22-temporal-task-cli.md).

## Этапы

1. Проследить источники отображаемых полей от CLI до клиента запуска. Переиспользовать
   чтение приватных файлов и применимые проверки. Зафиксировать состав сводки и способ
   связать её с проверенными входом и регистрацией, включая фактические команды проверок.
2. Добавить режим чтения в `task-chat` и вывод сводки в текущем чате перед штатным стартом.
   Связать каждый критерий с поручениями по этапам, ожидаемыми доказательствами и условиями
   успеха. Вынести пробелы в начало сводки.
   Перед первым эффектом сверять привязку показанной сводки. При изменении значимых данных
   вернуть причину и сформировать актуальный просмотр. Сохранить действующий прямой запуск.
3. Обновить инструкцию текущего чата и проверить обычный запуск, отказ и повторный просмотр
   через пользовательский вход. Доказательства записать рядом с критериями.

4. Проследить, откуда берутся обязательные проверки и какие версии их определений исполняются.
   Начать со сквозного примера, где кандидат ослабляет скрипт под прежним именем
   `yarn validate`. Использовать имеющиеся привязки к версиям, дополнить отчёт приёмки
   недостающими сведениями. Проверить различимость доверенных правил и правки кандидата.
5. Сопоставить доступные сведения о расходе модели с этапом и попыткой. Добавить в итог
   поручения разбивку по планированию, исполнению и независимой приёмке. Показать повторы
   отдельно и проверить сумму на задаче с повторной попыткой.

## Критерии приёмки

- [x] CHECK-01: На примере двух рабочих копий одного проекта владелец однозначно различает
  целевой путь. Карточка, область записи, исполнитель, применимые роли и команды проверок
  совпадают с данными, которые использует старт.
- [x] CHECK-02: Два просмотра одного входа дают одинаковую сводку при отключённом Temporal.
  Файлы допуска и назначения сохраняют исходное состояние. Обращений к серверу, Worker и модели нет.
- [ ] CHECK-03: Подмена входа или значимой части регистрации после просмотра обнаруживается
  до резервирования. Старт с исходными данными проходит штатную проверку допуска.
  Существующие вызовы CLI и SDK сохраняют свои результаты.
- [x] CHECK-04: Некорректная или чужая регистрация даёт диагностический отказ.
  Успешный вывод и ошибки не раскрывают полный приватный файл, исходное сообщение владельца
  или содержимое квитанций.
- [ ] CHECK-05: Инструкция показывает сводку на одном примере. Прошли профильные тесты
  [команды чата](../../../tests/taskChatCommand.test.ts) и [CLI](../../../tests/cli.integration.test.ts),
  проверки документации и полный `yarn validate` с 100% по четырём показателям покрытия.
- [ ] CHECK-06: В примере с изменённым `yarn validate` по результату приёмки видны источник
  и версия доверенных правил, изменение скрипта кандидатом и версия, фактически запущенная
  на проверяемом дереве. Если исполнился ослабленный скрипт, его успех не засчитывается
  как прохождение исходной проверки.
- [ ] CHECK-07: Для задачи с повторной попыткой отчёт показывает расход по каждому из трёх
  этапов и вклад повтора. Итог совпадает с суммой показаний по уникальным попыткам, в том
  числе после повторного чтения результата. При отсутствии показаний отчёт указывает пробел
  и обозначает известную сумму как частичную.

- [x] CHECK-08: На примере карточки с тремя критериями предпросмотр показывает, кто реализует
  изменение, какую проверку первого критерия запускает хост и какая роль проверяет его при
  приёмке. Для второго указан принимающий решение человек. Третий поручен только исполнителю:
  в начале сводки указан один критерий без проверяющего, его ID и текст. После явного назначения
  проверки третьего критерия повторный просмотр показывает ноль критериев без проверяющего.
- [x] CHECK-09: В предпросмотре для каждого критерия видны проверяющий, требуемое
  доказательство и наблюдаемый признак успеха. В примере с повторным запросом поочерёдно
  убрать из задания требование к квитанциям и условие совпадения идентификаторов.
  В каждом случае сводка называет конкретный пробел и сохраняет остальные сведения.

## Риски и доказательства

Главный риск — расхождение показанного плана с исполнением, особенно при замене регистрации
между просмотром и стартом. Проверять этот случай через штатную команду с наблюдением
за первым побочным эффектом. Недоступность Worker и готовность внешней среды по локальному
просмотру определить нельзя. В сводке указывать только фактически проверенные сведения.

Стендовое подтверждение привязки и полный допуск ожидают прогона с локальным сервером.
