# Проверки agent-workflow

## Обязательная граница

Самостоятельный полный допуск — `yarn validate`. Он проверяет типы, сборку, архитектурные
границы и весь существующий набор тестов: core/ports/application/adapters/CLI и src/Temporal.
Каждый показатель покрытия lines/statements/functions/branches равен 100%. Сужение до src
или Temporal-тестов не доказывает полный инструмент.

Изменение начинается с адресной регрессии у владельца договора. Затем выполняются затронутые
type/build/architecture checks и полный validate. Таймауты, assertions, изоляция, обработка
ошибок и пороги сохраняются.

[Матрица](traceability.md) связывает требования TC-WF с профильными проверками и исходной квалификацией.

## Различие доказательств

Pure/unit/fixture tests доказывают только проверенные правила. Настоящий SDK подтверждает
реальные Workflow/Activities и свои filesystem effects в объявленном scope. Native Codex,
Writer, параллельные владельцы, operational restore, активные grants и T6 требуют собственных
первичных доказательств и независимой приёмки. `prepared` и `answered` не являются DONE.

Сервисный SDK/Temporal/PostgreSQL тест не входит в разрешение выполнить локальный unit/build.
До его запуска должны быть конкретные request/input hashes, числовые caps, общий deadline,
план STOP/cleanup и действительный пользовательский источник. Разовый grant не переносится
на исправленный запрос. Ошибочный запуск сохраняется; повтор без нового допуска запрещён.

## Проверка документации

Проверяй текст командами `yarn lint:docs` и `yarn lint:docs:references`, а журнал решений —
командой `yarn lint:adr`. Ссылки на первичные доказательства ведут на сохранённый снимок
или неизменяемый источник.

`yarn lint:docs:references` проверяет текущие локальные ссылки, якоря и имена команд Yarn
по `package.json`. Исторические источники и явно обозначенные команды другого проекта
учитываются отдельно; внешние URL и абсолютные evidence-locators не проверяются по сети.
Проверка входит в статическую цепочку общего допуска и не исполняет команды из документов.

Неизменяемые источники `decisions/inherited`, `decisions/sources`, `tests/fixtures/qualification`
и тела завершённых/отменённых планов относятся к истории; текущие указатели и входящие
ссылки на них проверяются. В текущем документе старый блок команд можно явно ограничить
парой `<!-- documentation-check: historical:start -->` и
`<!-- documentation-check: historical:end -->`; ссылки внутри блока остаются проверяемыми.
Фраза «команда проекта-потребителя G» выделяет команды только своей строки и требует
ясного указания проекта выполнения. Наличие исключения показывается в отчёте проверки.

## Время выполнения и кеш

`yarn validate` запускает три независимые статические цепочки: типы тестового проекта,
сборка, архитектура и ESLint идут последовательно; форматирование и документация — рядом.
Сборка проверяет отдельный NodeNext-договор `src`, поэтому внутри полного допуска его
предварительный повтор через `typecheck --noEmit` не нужен. Отдельный `yarn typecheck`
по-прежнему проверяет оба договора без записи сборки.
После успешной статики запускается весь `test:coverage`. Он получает ресурсы отдельно;
затем две цепочки выполняют прежние Node/profile/consumer/self/contract/package проверки.
Отказ останавливает зависимую цепочку и последующие этапы; соседние цепочки завершаются,
а общий код выхода остаётся ненулевым. Для диагностики есть `yarn validate --serial`;
`yarn validate:static` проверяет только статику и не является полным допуском.
Каждая команда печатает время и результат.

ESLint разделён на два последовательных прохода. Типовые и неизвестные правила выполняются
каждый раз; кешируются только базовые правила и известные правила TypeScript без типов.
Файлы с директивами ESLint целиком проверяются без кеша, включая неиспользуемые отключения.
Исходные параметры правил и нулевой порог предупреждений сохраняются. Кеш по содержимому
учитывает версию Node, реализацию разделения, lock-файл и найденные настройки
ESLint/TypeScript/Prettier/EditorConfig, включая родительские EditorConfig.
Для сравнения есть исходный `yarn lint:all` без кеша.

Prettier использует кеш по содержимому; версия, параметры и настройки учитываются самим
Prettier. `yarn format:check:all` выполняет исходный проход без кеша.
Кеши находятся в `node_modules/.cache/`; общий запуск также передаёт дочерним Node-процессам
встроенный кеш компиляции, сохраняя явно заданный `NODE_COMPILE_CACHE`.
Удаление кешей не меняет состав проверок.
ADR, Markdown, архитектурные связи и результаты тестов не кешируются.

Общий Vitest выбирает до пяти рабочих процессов с учётом доступных ядер и памяти
(одно ядро в резерве, не менее 2 ГиБ на процесс). При двух и более процессах планировщик
резервирует один для наборов без внешних инструментов. Один и тот же предел действует
при составлении очереди и при запуске файлов в обоих проектах Vitest.
При ограниченной памяти или для воспроизведения последовательного запуска можно задать
`VITEST_MAX_WORKERS` или `--maxWorkers` для Vitest. Значение 1 выполняет файлы по очереди.
ARM64-процессы сохраняют защиту `--no-sparkplug`.

Под покрытием на macOS с памятью от 16 ГиБ проект Vitest `unit` размещает временные
файлы в отдельном томе в памяти на 2 ГиБ. Vitest отключает том после завершения
проверки. При недоступности тома используется системный временный каталог.
Интеграционные тесты, отчёты покрытия и JUnit используют прежние каталоги.
