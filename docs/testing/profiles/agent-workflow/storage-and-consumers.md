# Хранение, поставка и установленные потребители

Проверки архивов, резервных копий, восстановления и закреплённого пакета у потребителей. Самопроверки стендов отделены от установки и запуска служб.

[Выбор проверки](../agent-workflow.md) · [Обязательная граница](../../strategy.md#обязательная-граница).

Команды выполняются из корня самостоятельного `agent-workflow`. Сервисные, установочные и
native-варианты требуют собственного применимого разрешения; наличие команды не даёт допуска.
Исторические результаты и точные версии ниже относятся только к своим входам и попыткам,
не подтверждают текущую поставку и не заменяют открытые критерии миграции. Пометка
«историческая команда G» сохраняет прежнее имя команды игры, а не команду этого репозитория.

## Подготовка хранения и потребителей Temporal

`yarn package-closure --check MANIFEST.json` читает закреплённый tarball
до установки. Проверяются достижимые imports, объявленные зависимости и literal assets;
дополнительные входы потребителя связаны с hash исходника внутри архива. Подменённые hashes,
ссылки, выход за архив и отсутствующие файлы дают отказ. Вычисляемые пути и внешние входы
остаются unknown, `qualification=false`; содержимое установленных зависимостей не проверяется.
`--plan` выдаёт шаблон без запуска пакета. Девять Node-тестов проверяют эти границы и отсутствие
исполнения кода архива; они входят в `validate` самостоятельного пакета.

`yarn build && yarn test:legacy-archive`, `yarn build && yarn test:retention` и `yarn build && yarn test:backup` проверяют
читаемую историю, целостность копий, повреждение/неполноту и отчёт хранения без удаления.
Store открывается read-only; исходные ID/hash, FAIL/findings/Result и неизвестные тела
сохраняются. `legacyArchive.test.ts` проверяет прямые и транзитивные архивные зависимости,
отказ при неполноте до создания назначения и положительный export → stage → read. Файловой копии версии 2 недостаточно для утверждения полного восстановления
PostgreSQL/Temporal. `yarn test:postgres-restore:self` проверяет готовый ограниченный стенд без служб;
`node tests/temporal/t4-postgres-recovery.mjs --run CONFIG.json` требует отдельного прямого разрешения и использует
только новый синтетический cluster, без Docker/Temporal/моделей. Подробности —
[хранение и восстановление](../../../temporal-storage-recovery.md).

`t4-pg-temporal-recovery.mjs --show-restore-plan CONFIG.json NEW_ROOT` проверяет сохранённый
coherent recovery set и закреплённую конфигурацию; выдаёт review-only argv, schema/readback
и ссылки на artifacts/workspaces/build. Общая физическая БД восстанавливается одной группой
команд. `--self-test` проверяет файловой backup → план, подмену, неизвестную топологию,
конфликт БД и небезопасное назначение. Сервисы не запускаются, реальный комплект и
эксплуатационные RPO/RTO этим не квалифицируются.

`yarn test:pinned-consumers:unit` проверяет установочный стенд без установки.
Поставка обязательно содержит compiled contract, package.json и yarn.lock; отсутствующие
или подменённые directory/nested spelling имена отвергаются до установки. Типы tar
по-прежнему отдельно проверяет static closure; проверка списка имён не заменяет её.
`yarn build && node tests/temporal/pinned-consumers.mjs --run NEW_EVIDENCE_DIRECTORY` пакует закреплённый локальный tarball,
проверяет SHA/состав, offline frozen install без hooks в отдельные game-config/neutral копии,
реальный запрет исходного repo/сети и cleanup. Прогон требует прямого допуска к установке.
Game-config не содержит приложения и не запускает game validate, поэтому preparation smoke
не закрывает TEMP-14/T5. [Карта](../../../temporal-consumers.md),
[инструкция](../../../temporal-installation.md) и
[методика сравнения](../../../temporal-comparison.md) фиксируют
оставшиеся зависимости и нулевой бюджет сравнительной серии. Самостоятельный validate
дополнительно выполняет Node self-tests стенда; standalone проверяет новые архивные CLI
и PG self-test, не запуская PG.

`yarn test:installed-full-consumers:unit` проверяет отдельный полный стенд
отдельными Node self-tests; входит в package validate и standalone. Команда
`yarn test:installed-full-consumers --plan REQUEST.json` описывает действия без установки;
`--run REQUEST.json` требует нового прямого допуска к трём offline/frozen/ignore-scripts
установкам и временному SDK-комплекту до 60 минут. Один pinned tarball используется обоими
проектами; runtime/Workers не читают исходные checkout или verification-копии. Отдельный
доверенный checker выполняет настоящие игровые проверки над точными candidate bytes.
Его исходный срез — `a79757f3` с четырьмя закреплёнными исправлениями проверочного проекта:
`tests/temporal/finalization.test.ts` убирает ровно шесть лишних
`await` у синхронного `fixture()`; `tests/boundaries.integration.test.ts`
добавляет ровно одну пропущенную копию `scripts/vitestToolDependencies.mjs` во вложенный
стенд. Ещё два исправления переносят существующую оптимизацию `TransportJournal` и две
связанные регрессии: одинаковый диагностический снимок не записывается повторно только после
сверки идентичности и точных байтов файла. Создание и каждая попытка доставки сохраняют
свои первичные записи; схема, пределы журнала, исходные assertions и тайм-аут 5000 мс прежние.
Source/test payloads закреплены отдельно от изменяемых основных файлов. Проверяющий сверяет
точный состав двух путей, размеры и исходные/итоговые SHA обоих payloads до любой записи;
неизвестные байты дают отказ. Base и все четыре overlay сохраняются в отчёте,
`compatibility-overlay.json` и source snapshot до его инвентаризации. Это не pristine-срез
`a79757f3`; игровой owner, команды, assertions и пороги не изменяются. Node-тесты стенда
проверяют точные преобразования и отказ при подмене входа или payload. Прежний FAIL с
тайм-аутом журнала остаётся историческим результатом; новая подготовка сама по себе не
доказывает успешного полного установленного SDK-прогона.
После offline-установки checker выполняет существующий `yarn build`
под запретом сети и исходных checkout. Он создаёт локальные dist-цели self exports, нужные
архитектурной проверке smoke-потребителя. Сборка, её stdout/stderr и подтверждённая остановка
записываются в checker-preparation.json, отчёт и source snapshot до его фиксации. Это
дополнительная команда сборки, не установка; ошибка/unknown запрещают дальнейшие этапы.
Учёт процессов разделяет активную принадлежность и историю: полный проверенный снимок
подтверждает отсутствие прежнего PID или всей группы до снятия принадлежности. Повторное
использование уже освобождённого номера не даёт права сигналить чужой процесс или относить
его TCP-listener к старому запуску. История и подтверждения снятия сохраняются; смена
идентичности без наблюдённого отсутствия, неполный снимок и ошибки наблюдения дают unknown.
Эти границы проверяются без служб на подставных снимках и часах; старый actual UNKNOWN
остаётся отдельным первичным исходом. Host support закрепляется отдельно от runtime tar.
Узкий запрос с дополнительным `consumer: "neutral"` выбирает только neutral: один
SDK-сценарий, одну offline-установку, ноль игровых проверок и внутренний предел10мин.
`--plan REQUEST.json` описывает этот scope до запуска; старые шесть полей запроса и
`--plan` без файла сохраняют полный маршрут60мин. Частичный отчёт имеет neutral-only/
partialScope и qualificationfalse; он не засчитывает full game/neutral или T5.
Отдельный cleanup guard требует ровно одного завершённого neutral,1install, полного
экспорта и всех известных stop; unknown/ошибки сохраняют временный root. Для всех
режимов проверяются порядок обязательных receipts, before/approved SHA, точные
registered executable/argv, sourceError=null, code0, отсутствие timeout и knownstop.

Material механического SDK-сценария перечисляет все обязательные project.checks:
для game это validate, для neutral — baseline и validate. Baseline выполняется до
изменения и после точного исправления; checker принимает для него только закреплённые
before/approved bytes, а для validate — только approved. Сохраняются проверки base64,
SHA, текущего source snapshot и owner. Подтверждения ожидаются для исходного baseline
и двух этапов всех обязательных checks: game — три, neutral — пять. Фактический builder
проверяется отдельно без запуска SDK; подготовка не подменяет установленный прогон.
Два игровых validate сохраняют действующий предел 20 минут и четыре метрики 100%; превышение
сохраняется как FAIL/unknown. Восстановление завершённого RESULT новым Worker/client и replay
не доказывают восстановление активного writer. Модели и authority этого стенда имитированы;
полный T5 и сравнение остаются открытыми до отдельных доказательств.

`yarn test:pg-temporal-recovery:self` проверяет recovery-set и test-only
PGTemporal runner без служб: pin до любого exec, private socket/endpoint ownership,
ограниченную остановку и сохранение root при FAIL/unknown. Входит в standalone.
`node tests/temporal/t4-pg-temporal-recovery.mjs --extract-archive CONFIG ARCHIVE NEW_DESTINATION` и `--run CONFIG`
требуют нового прямого допуска. Один новый PGTemporal source и новый target используют
закреплённые Server/SQL-tool и прежние ID/history/result, без моделей и существующих задач.
Тестовый pending/query не квалифицирует живого T3 writer, действующие grants, production ACL
или промышленный RPO/RTO; signature/files-verified не означает готовое восстановление.
Необязательный `resumePending: true` выбирает отдельную синтетическую ветку: после
восстановления и query прежнего состояния runner один раз отправляет Signal и проверяет
COMPLETED на прежних WorkflowID/runID, неизменный исходный prefix истории, ровно один Signal
и одно завершение. Activities и модели отсутствуют. По умолчанию сохраняется query-only
ветка; unknown при отправке запрещает повтор и оставляет root/proof для разбора.

## Минимальное хранение рабочего состояния

`sharedProofs.test.ts` проверяет реальный процесс и один список входов для before/after/check,
нескольких проверок, intent и поручения совета; также малые списки, полный CLI reader,
legacy pool, независимость полей и повреждение/подмену границы пула. `nativeCouncil.test.ts`
читает новый формат через явный reader, сохраняя прежние отрицательные проверки bindings.
`taskFileMaintenance.test.ts` проверяет архив и общий кэш двух namespace, исходные логические
хеши, запуск инструмента, запрет исполнения архивного указателя, CAS/manage/lease/effects,
неизвестные checks, прерывания copy/index/replace, повреждение, символьные ссылки, пути,
повтор и независимую материализацию. Полный перенос R2 и исходные хеши проверяются отдельно
на остановленной задаче; это не новая содержательная приёмка и не измерение токенов модели.

`retention.test.ts` проверяет отпечатки повторов и конфликтов без прежних тел, продолжение,
значимые FAIL и использованные turns, явные legacy markers, Unicode и независимость изменяемых
объектов при разделении неизменяемых manifests. `retentionMaintenance.integration.test.ts`
проверяет полномочия/CAS/owner/lease, точную внешнюю копию и восстановление, аварии до/после commit
и во время удаления, повтор очистки, сохранность effects/evidence и перепривязку принятого плана.
Новые записи не создают полного архива. R2 измеряется отдельно от времени модели и её токенов.

`council.test.ts` проверяет сохранение `review_turns` после двух PASS, сокращения истории и
`revisePlanning`: старый ответ снова не принимается. `managedOriginal.test.ts` проверяет точные
legacy plain/archive байты и все зависимости до минимизации, повтор без второй копии, повреждение,
отсутствие blob и конкурентную замену. Повторное минимальное сохранение читает только 10 байт
заголовка вместо прежнего файла; обычное сохранение проверяет метаданные без чтения содержимого.
Прежняя защита от ссылки проверяется `chatDiscovery.test.ts`.
`chatOutput.test.ts` и `chatRuntime.test.ts` проверяют
короткие квитанции вместо полных снимков: 20 результатов с большим старым телом дают менее 20 КиБ
квитанций; FAIL/blockers видимы, исходный check proof неизменен, Council продолжается,
`--full` раскрывает доступный legacy архив без записи лишнего экспорта и проверяет его целостность.

## Совместимость прежнего архива

Новый Temporal-пакет имеет отдельный файловый контур `tests/temporal/backup.test.ts`:
все границы persistence/artifacts/receipts/workspaces/build, оригинальные FAIL, closed tombstones,
owner/generation/unknown, пустые каталоги, бинарные файлы и права; отсутствие исходников при
восстановлении; защита от повреждения manifest/blobs, подмены hash, неполноты, выхода пути,
повторов, links/специальных файлов, смены исходников и ENOSPC. Итог восстановления — staged,
требующий сверки; `.restore-incomplete` запрещает использовать частичный результат.
`yarn build && yarn test:backup` проверяет собранный CLI; собственный standalone
повторяет его без доступа к исходному репозиторию. Persistence — синтетическая сигнатура,
а не настоящая база PostgreSQL. Ни тесты, ни упаковка байтов не подтверждают её согласованность,
восстановление Temporal, полноту регистрации рабочих копий, RPO/RTO или промышленный допуск.

`archiveJson.test.ts` проверяет точное полное чтение и компактный индекс, literal/UTF-16,
исторические FAIL, идентификаторы ответов, неизменяемые blobs и отсутствие чтения старых тел
при добавлении события. Проверены чтение отдельного события через IPC, CAS/полномочия,
повреждения, backup/restore, перенос результата в независимый каталог и буквальные JSON.
`storageRecovery.integration.test.ts` повторяет настоящий SIGKILL на четырёх границах и для
архивных blobs. Legacy-регрессии явно читают прежнюю полную историю; новые workflow/chat/runtime
регрессии проверяют продолжение и повторы после удаления тел. Правила —
[договор архива](../../../quality/agent-workflow-contracts.md#кандидаты-хранения-и-восстановление).
