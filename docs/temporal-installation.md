## Что устанавливается

Поставка сохраняет публичные экспорты из `dist` с декларациями типов, CLI с его исходными
зависимостями, версионные инструкции и нейтральный пример. В разделе `docs/` разрешены руководства текущего чата, договор API, договоры процедур
и руководство SDK. Внутренние планы, ADR, протоколы и отчёты разработки остаются в репозитории.
Карты исходников, тесты, Python-стенд,
проверочные примеры потребителей и пересмотры сравнительных критериев остаются в checkout.
Из `src` поставляются только перечисленные в `package.json` файлы, достижимые из CLI;
добавление импорта требует проверки и при необходимости расширения этого списка.

`tests/packageSupply.test.mjs` проверяет настоящий архив: состав и относительные зависимости,
публичные экспорты, хеши процедур, справку CLI и загрузку SDK из распакованной копии.
Зависимости берутся из существующей локальной среды; установки и службы не запускаются.
Это проверка файлов поставки, а не установленная квалификация с запретом доступа к исходникам.
TypeScript закреплён среди runtime-зависимостей: его использует разбор первичных команд CLI.

После упаковки и до установки выполните `yarn package-closure --plan`
из корня репозитория, заполните manifest точными path/SHA-256/bytes архива и проверьте его
через `--check MANIFEST.json`. Для npm-архива добавьте в манифест поле `npmIntegrity`
со значением `integrity` из `npm pack --json`. Проверка сверяет SHA-512 архива.
lock-файл создаётся у npm-потребителя. Дополнительные входы и assets требуют привязки к исходнику
внутри архива. Отсутствующий import даёт отказ, unknown сохраняется явно; статический отчёт
не заменяет проверку установленного пакета. Архивный код при этой проверке не исполняется.

Целевая поставка `@krivega/agent-workflow` идёт через npm-реестр. Локальный архив служит входом
для проверки до публикации и для изолированных стендов. Потребитель закрепляет версию и lock-файл. Исторические проверки в этом руководстве относятся к своим архивам.
Состав публичных exports определяется метаданными проверяемого архива; на срезе 2026-11-16
это 22 входа, включая `./consumer-release`, `./task-execution` и `./task-backend`.
Установочные результаты 21 входа относятся к прежнему срезу без `./consumer-release`
и не принимают нынешнюю поставку. SDK starts/controls требуют явного `bindTaskBackendClient`
с регистрацией потребителя до обращения к серверу. Smoke
перечисляет входы из метаданных, без фиксированного числа. Прежний installed preparation PASS
19 входов остаётся доказательством своего снимка. Собственные `package.json`/`yarn.lock` фиксируют зависимости. Перед упаковкой сборка и полный
пакетный допуск должны соответствовать принимаемому исходному снимку.

Предварительные условия: поддерживаемый Node из package engines, установленный Yarn 1.22.22,
готовый `dist` и заполненный локальный Yarn cache. Стенд использует macOS `sandbox-exec`.
На другой ОС он явно отказывает; отсутствие системного запрета не считается успешной изоляцией.
Новая установка Node/Yarn, заполнение cache из сети и глобальная установка не входят в команду.

Из корня репозитория:

```sh
node --test tests/temporal/pinned-consumers.test.mjs
node tests/temporal/pinned-consumers.mjs --run tmp/pinned-consumers-preparation-NEW
```

Вторая команда устанавливает пакеты и требует своего действующего допуска; первая проверяет
сам стенд. Этот preparation-маршрут создаёт собственный tarball и не исполняет текущий
neutral-only request; для него отдельно закреплён уже подготовленный v6.

Каталог evidence должен быть новым: повтор не перезаписывает старый исход. Упаковка вызывает
`yarn pack --filename <temporary-root>/runtime.tgz` для существующего `dist`; lifecycle hooks
prepack/postpack/prepare запрещены проверкой. Команда сама не выполняет build или полную
квалификацию. Список tarball проверяется на наличие сборки и отсутствие `src`/`node_modules`.

## Два отдельных потребителя

Стенд создаёт один временный корень вне исходного репозитория и отдельные `game`/`neutral`:

- `game` получает фактический `project/temporal.json`, объявленные им правила и ролевые профили,
  отдельную карточку installation в его `cardRoot`; check ID `validate` зарегистрирован как
  `yarn validate`. Это минимальная копия входов проектного адаптера, а не копия приложения игры.
- `neutral` получает `examples/temporal-consumers/neutral`: свои правила, reviewer,
  `work-items` и syntax. Существующий `examples/neutral` не изменяется.
- Оба имеют `dependencies: {"@krivega/agent-workflow":"file:../runtime.tgz"}`.
  Yarn lock содержит точный локальный tarball/его SHA-1 и исходный закреплённый граф зависимостей.
  Входной lock не может содержать file/link/portal/workspace resolutions; новые source-ссылки
  не допускаются. SHA-256 tarball независимо проверяется перед smoke.

В каждом потребителе выполняется только:

```sh
yarn install --frozen-lockfile --offline --non-interactive --ignore-scripts
node smoke.mjs
```

Обе команды работают под системным запретом чтения **всего исходного репозитория** и сети.
Отдельное чтение его `package.json` обязано получить `Operation not permitted` до установки.
Проверяется неизменность lockfile и tarball, отсутствие symlink установленного runtime,
разрешение всех публичных exports внутри установленного пакета. Smoke использует публичные
`/contracts` и `/activities`, сверяет project v1, вызывает `prepareProject`, читает и проверяет
hash/размер каждого входа manifest. Чужой owner и отсутствующая карточка обязаны дать отказ.

Зарегистрированные команды не исполняются. Служба Temporal, Workers, модели, writer, Git,
рабочие карточки и старые Stores не запускаются и не изменяются. Полный установочный маршрут
с настоящим TaskWorkflow, командами, приёмкой, остановкой и восстановлением остаётся T5.

## Доказательства и восстановление

В переданном каталоге evidence сохраняются:

- `runtime.tgz`, `package-files.json`, итоговый `report.json` с версией, SHA-256,
  статусом, путём временного корня, `cleaned` и явным `qualification:false`;
- для каждого потребителя package/project/pin/lock, журнал установки, smoke result и
  неизменяемые manifests подготовки.

При ошибке сохраняется `failed` с причиной, исходный отказ не превращается в PASS.
Временные `game`/`neutral`, их `node_modules` и общий tarball удаляются в `finally`;
evidence сохраняется в новом ignored tmp каталоге. Если процесс убит до `finally`,
сначала определить его исход и отсутствие активных процессов, затем удалить только принадлежащий
этому запуску `aw-pinned-consumers-*`; рабочие данные и системный cache не очищаются.

Стенд не проверяет, что уже собранный `dist` соответствует текущему `src`: перед итоговым T5
нужны закреплённый source/build manifest и отдельный полный пакетный допуск. Он также
не проверяет доступность Temporal, совместимость Workers или резервных копий.

## Подключение и обновление внешнего проекта

### Выбор схемы для T7

| Где применяется | Как подключить | Кто управляет обновлением |
| --- | --- | --- |
| Отдельный репозиторий | Установить точную версию `@krivega/agent-workflow` из npm в `devDependencies`. Добавить lock-файл, выполнить `init` и `doctor` из корня. | Команда проекта принимает изменение версии и lock-файла после `doctor` и своих проверок. Это рекомендуемая схема по умолчанию. |
| Монорепозиторий с общими правилами | Установить одну версию в корень. В корневом дескрипторе указать правила и команды проверки нужных компонентов. | Одно обновление охватывает весь репозиторий. Эта схема удобна, когда команды готовы обновляться вместе. |
| Несколько самостоятельных репозиториев | Подключить каждый как отдельный проект. Общие навыки, процедуры и базовые профили приходят с пакетом. | Для массового обновления можно открывать однотипные запросы на изменение версии в каждом репозитории. Каждый проект проверяет и принимает выпуск отдельно. |
| Закрытая сеть | Получать ту же закреплённую версию из внутреннего npm-зеркала. Для автономной установки подготовить архив, его контрольную сумму и кэш всех зависимостей для целевой платформы. | Владелец зеркала или комплекта отвечает за доставку выпуска и зависимостей. Проект сохраняет свой lock-файл и порядок приёмки. |

Язык приложения может быть любым. Для действующего CLI нужны поддерживаемая пакетом
версия Node.js и `package.json` в корне проекта. Например, для Python достаточно
приватного `package.json` с именем проекта и скриптом `"test": "python3 -m unittest discover"`.
В Go-проекте аналогичный скрипт может вызывать `go test ./...`. Основная сборка и тесты
остаются у привычных инструментов проекта. В среде, где запускают CLI, устанавливают
и зависимости разработки. Рабочий сервер Temporal и Worker подключаются отдельно.

Обновление готовится как **новый** tarball/version/hash и новый каталог потребителя. Вне рабочего
исполнения сверяются схема, exports, lock, полные проверки и replay историй. Неизвестная схема,
неполный backup или несовместимый replay запрещают обновление. Успешная установка без replay
не доказывает безопасное обновление Worker; его версии и восстановление относятся к T4/T5.

Каждый проект задаёт собственный дескриптор v1 и доверенную локальную регистрацию:
project/workspace IDs, относительные rules/cardRoot/role profiles, check IDs и команды
`executable`/`args`. В descriptor нет shell-кода, секретов или машинного абсолютного пути.
Репозиторий выбирает расположение файлов, менеджер пакетов и команды проверки.

Откат установки выбирает прежний проверенный tarball и его lock в отдельной копии. Откат Worker
разрешён только при доказанной совместимости истории и внешних эффектов. Задача, начатая в
Temporal, остаётся в Temporal: старый SQLite Store не заменяет её актуальную историю.

```sh
npm exec -- agent-workflow doctor
```

`package.json`, импортах SDK, проектной обёртке и ссылках навыка на
`@krivega/agent-workflow`. Пересоздайте соответствующую запись lock-файла штатной
установкой и выполните `doctor`. Команда CLI по-прежнему называется `agent-workflow`.

Вместо `<версия>` подставьте принятый номер выпуска. Команды запускаются из корня
проекта с установленными зависимостями. Для нового подключения `init` использует
имя из `package.json` и существующую команду `validate` или `test`. Он создаёт
тонкий вход `.agents/skills/agent-workflow/SKILL.md`, дескриптор
`tools/agent-workflow/project/temporal.json`, каталог карточек, правила и начальный
проектный профиль на основе пакета. Профиль можно редактировать в Git. Повторный
вызов сохраняет существующие файлы. При существующем дескрипторе проверяются его
собственные пути и команды. `doctor` читает подключение, проверяет привязку CLI,
процедуры, правила, роли и навык. Эти команды не регистрируют Worker и не запускают задачи.

## Перед включением T6

После полного T5 и отдельного решения о включении сверить [карту потребителей](temporal-consumers.md),
закрепить один backend для project/task до первого эффекта, исключить повтор старого поручения
под другим taskId. Неизвестный backend или неизвестный прежний writer запрещают новый start.
Прежний CLI продолжает только ранее начатые задачи в совместимой среде. Source копий инструмента
не нужен установленным потребителям; чтение старой истории не выдаёт права исполнения.

При сбое остановить новые действия, сверить первичные эффекты и восстановить тот же backend.
Постоянные службы, фон, публикация, внешнее подключение и удаление старого runtime не разрешены
этой инструкцией. Переключение и удаление прежнего штатного runtime относятся к T6,
оформление самостоятельной поставки — к T7. После T5 оба этапа можно вести параллельно.

## Отдельный полный устанавливаемый стенд

`tests/temporal/installed-full-consumers.mjs` принимает запрос `schemaVersion:2`.
Полный game/neutral закрепляет текущие файлы игры отдельным снимком и использует установленный
runtime; исходники инструмента в checker не переносятся и не собираются.
Прежний `pinned-consumers.mjs` и его `qualification:false` сохраняют свою область.

Исторический full-маршрут был привязан к commit `a79757f3…`, накладывал overlays на
`tools/agent-workflow/tests` и `tools/agent-workflow/adapters` и вызывал
`agent-workflow:temporal:build`. Эти действия исключены из нового маршрута после выделения.
Старый запрос без `schemaVersion:2` или с `base` отклоняется; его исходные байты,
использованные разрешения и результаты не переписываются. Новый профиль сам по себе
не является новой установочной приёмкой. Наличие `./consumer-release` также не означает PASS.

Ранний FAIL до exec/install/SDK из-за дробного timeout и последующие отказы checker остаются
первичными отказами. Их журналы и копии не перезаписываются. Позднее выполненный комплект v5

Отдельные SDK basic/CAN и standalone уже имеют PASS на своих закреплённых снимках.
Standalone работал с запретом обоих исходников, сохранил первичные tmp и подтвердил остановку.

Подготовка снимка только читает рабочую копию игры и печатает JSON. Сохраните вывод вне
исходной игры и вычислите его SHA-256 и размер для запроса. Просмотр плана также не
устанавливает пакеты и не запускает службы:

```sh
node tests/temporal/installed-full-consumers.mjs --snapshot /absolute/game-checkout > /absolute/game-source-snapshot.json
yarn test:installed-full-consumers --plan
yarn test:installed-full-consumers --plan /absolute/full-consumers-request.json
yarn test:installed-full-consumers --plan /absolute/neutral-request.json
```

Manifest снимка имеет `schemaVersion:1`, `kind:"installed-game-source/1"`, канонический
`root`, текущий `head` и отсортированный список `files` с относительным путём, SHA-256,
размером и mode каждого файла. Снимок учитывает текущие файлы Git, включая незакоммиченные
изменения и неигнорируемые новые файлы; один HEAD их не закрепляет. Перед копированием
проверяются ref самого manifest и совпадение фактических входов. Изменённый источник
даёт отказ до установки. Корень задаётся в `gameSource.root`; переменная окружения
`AGENT_WORKFLOW_CONSUMER_ROOT` не заменяет этот договор полного режима.

Проверочная копия получает только закреплённый Git HEAD через независимый shallow clone
по `file://`, затем точные текущие файлы из manifest. Предки Git не входят в этот снимок;
проверка, требующая их, должна явно завершиться отказом, без автоматической подгрузки истории.

Имя команды определено в `package.json` этого репозитория. `--plan REQUEST` проверяет
только форму запроса, не создаёт evidence и не проверяет фактические байты archive/CLI
или снимка игры. Без запроса выводится полный план версии 2. Проверки байтов и полномочий
выполняются отдельно до запуска.

В полном режиме игра проверяет M1: в отдельной копии намеренно удаляется учёт результатов дел из реального
`apps/player/src/application/story/playerStoryProfileScores.ts`; затем точный принятый материал
восстанавливает исходные байты. Потребители перечислены в `examples/temporal-consumers/full/spec.mjs`:
PlayerStoryFlow, playerStoryHost, playerNativeGameRuntime и существующие тесты проекции/библиотеки.
Исходное приложение не изменяется. Нейтральный проект механически восстанавливает суммирование,
проверяет пустой, положительный и смешанный набор через собственный `node:test`.

В полном режиме два независимых driver и disposable checker игры используют **один tarball
с одним SHA-256**. Для публичного npm-архива без `yarn.lock` источником графа
служит закреплённый lockfile снимка игры. Стенд сверяет имя, версию, URL реестра, SHA-1 и
SHA-512 из lockfile, SHA-256 архива и опись поставляемых файлов с учётом режимов.
Оба driver используют копии этого графа с локальной ссылкой на проверенный архив.
Checker использует реестровую запись игры без изменений. Для npm-архива без собственного lockfile доступен
совместный сценарий игры и neutral. Отдельный сценарий neutral требует архив с lockfile.

Для прежнего vendor-архива граф driver задаёт собственный lockfile пакета. В копии игры
стенд обновляет vendor-архив, его pin, опись и запись runtime в игровом lockfile.
В обоих вариантах driver используют `@temporalio/testing@1.25.0` для SDK.
Дополнительная прямая зависимость допускается только на уже существующий узел игрового
lockfile с точным selector и той же точной версией: новые пакеты, версии и разрешения
зависимостей не добавляются, остальные записи lockfile не меняются. Например, TypeScript
`6.0.3` может стать прямой runtime-зависимостью, если `typescript@6.0.3` уже закреплён
игрой. Несовпадение даёт ранний отказ. Исходная игра и её индекс сохраняются.
Всего остаются три offline/frozen/ignore-scripts установки.
После единственной установки выполняется команда проекта-потребителя G `yarn agent-workflow:consumer:check` под
запретом чтения исходных checkout и сети: проверяется установленное подключение, сборки
исходников инструмента нет.

Runtime/Workers/driver находятся под OS-запретом чтения исходных checkout и **обеих** полных
verification-копий. Публичные exports реально импортируются с проверкой realpath внутри
установленного пакета; Workflows и artifact-store читаются из
поставленного `dist`, исходный `src` не подмешивается. Проверка пакета остаётся зависимой от этих
явных поставляемых путей, хотя новых публичных exports этот стенд не требует.

Доверенный checker — отдельный процесс за пределами ограничения runtime. Он получает по
закрытому Unix socket только enum baseline/validate и exact bytes/hash единственного заранее
разрешённого owner. Произвольных путей и команд в запросе нет; иные байты отвергаются до записи.
Checker накладывает принятые байты в собственную полную копию приложения. Baseline игры выполняет
существующий playerStoryLibraryProgress.test.ts; **candidate и integrated** проходят полную проверку —
команда проекта-потребителя G `yarn validate:brief`, включая действующие игровые проверки и прежние пороги покрытия.
Полный собственный допуск инструмента выполняется отдельно на том же закреплённом срезе.
Взаимосвязь результата с
owner hash, точная команда, полный журнал, исход и подтверждённый stop сохраняются отдельно.
Дочерние baseline/validate-команды обоих проектов выполняются под OS-запретом чтения
исходных checkout. Наблюдатель процессов остаётся снаружи; команды используют тот же
ограниченный переходник `ps`, что и driver, без расширения допустимых запросов.
Checker читает собственный снимок игры и установленную поставку; runtime/Workers/driver
не получают доступа к этим checker-входам. Его `/bin/ps`-наблюдатель допускает лишь два прежних фиксированных
формата: macOS запрещает setuid `ps` внутри Seatbelt. Runtime не получает произвольного чтения.

Настоящий SDK выполняет preparation → отдельный planning → M1 → baseline/candidate/integration
→ реальные проверки → acceptance → RESULT/DONE. Обе роли представлены детерминированным
RPC-double: по четыре simulated turns на проект, **модельных стартов 0**. LOAD читает настоящие
байты частей с hash; это не доказательство понимания моделью или native independent acceptance.
Стенд проверяет чтение прежнего завершённого результата новым Worker/клиентом без нового хода
и replay пяти историй проекта. Это подтверждено для игры и neutral в полном прогоне
`41fe8d8d…` и отдельно для v5 игры и узкого v6 neutral.
Это восстановление завершённого результата, а не потерянного активного writer или закрытого
persistence. Эта граница отмечена в отчёте.

Полный запуск требует **нового отдельного разрешения** на три установки, два последовательных временных
Temporal CLI v1.9.1 и два последовательных checker/observer процесса. Прежние бюджеты закрыты.
Подготовленный интерфейс:

```sh
node tests/temporal/installed-full-consumers.mjs --run /absolute/full-consumers-request.json
```

Полный запрос содержит `schemaVersion:2`, `archive`, `archiveSha256`, новый `evidence`,
`temporalBinary`, `temporalBinarySha256` и `gameSource:{root,snapshot:{path,sha256,bytes}}`;
шаблон — `examples/temporal-consumers/full/request.example.json`.
Для neutral-only вместо `gameSource` задаётся `consumer:"neutral"`; снимок игры в этом режиме
не допускается. Поле `base` и неизвестные поля отвергаются. Нулевые hashes, примерный размер
и пути шаблона нужно заменить проверенными значениями до отдельного допуска. Это абсолютные
существующие локальные tarball/CLI и новый каталог доказательств. До любого запуска CLI
проверяются SHA, настоящий путь, обычный
исполняемый файл и единственная жёсткая ссылка; symlink и hardlink отвергаются. Приватная копия
проверяется повторно перед `--version` и запуском SDK. Версия и setup входят в общий срок. CLI копируется,
из сети не загружается. Ожидается 36–45 минут на два игровых validate и 3–8 минут на остальное;
общий предел 60 минут, предел каждой игровой команды сохраняет 20 минут. Последовательные проекты,
до двух штатных test workers, ориентировочно 3–6 ГиБ памяти; фактический пик ещё не измерен.
Действующий runtime отвергает timeoutMs более 1 200 000 в `activities/localTask.ts`;
последний root занял 1055 с, холодная копия может превысить 20 минут. В таком случае сохраняется
FAIL/unknown с первичными журналами, без увеличения предела или автоматического повтора.
При отказе нет автоматического повтора или уменьшения набора проверок.

В evidence сохраняются package pin, исходный game snapshot, квитанции обновления подключения
только в копии checker, exact check receipts с полными
журналами, отдельными root full.log/LCOV/JUnit каждого нового прогона, before/after inventories
исходников, driver и checker, RESULT либо failure, artifacts, host/task records, SQLite и истории.
После закрытия Worker/CLI отдельно проверяется отказ соединения с его listener; unknown stop
не даёт очищать корень. Ошибка и
`qualification:false` не заменяются успехом. Службы закрываются общим ограниченным по времени
маршрутом с проверкой наблюдавшихся потомков, групп и listeners; код 0 главного процесса сам
по себе не подтверждает остановку. Только полный PASS с экспортированными доказательствами
и подтверждёнными остановками допускает удаление копии. Любой FAIL, unknown,
незавершённый check receipt или живая группа сохраняют
временный корень и failed/cleanupBlocked вместо успешной очистки;
при аварийном убийстве до `finally` принадлежность и stop проверяются до ручной очистки.
Само наличие исполнимого стенда не закрывает TEMP-14/T5, не выделяет comparison-бюджет и не
разрешает T6, фон, публикацию или удаление старого runtime.
