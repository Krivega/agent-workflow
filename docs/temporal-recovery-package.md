# Архив завершённого H06/3 и автономная проверка восстановления

`tests/comparisonH06RecoveryPackage.ts` собирает архив завершённого Legacy H06/3 в новом
каталоге и проверяет его восстановление без модели и сервисов. Это доказательство сохранения
конкретных файлов и состояния SQLite. Оно не подтверждает восстановление Temporal/PostgreSQL,
RPO/RTO сервера, повторный запуск исполнителей или перенос полномочий.

Для рабочего PostgreSQL/Temporal recovery используется другой, связанный комплект со snapshot,
native dumps, artifacts, receipts, projections, build и workspaces. Его test-only команда
`t4-pg-temporal-recovery.mjs --show-restore-plan CONFIG.json NEW_ROOT` проверяет сохранённые
ссылки и выдаёт конкретный план БД/конфигурации/readback без запуска служб. Порядок подготовки,
ограничения конфигурации и оставшийся сервисный допуск описаны в
[инструкции восстановления](temporal-storage-recovery.md#проверяемый-сервисный-план-сохранённого-комплекта).
Файловой H06-копии, включая PASS с 2416 восстановленными и 938 неизменными исходными файлами,
для такого backend-доказательства недостаточно; эксплуатационные RPO/RTO остаются `UNKNOWN`.

Для подготовки свежего синтетического окна служит `--show-fresh-plan`: существующие
закреплённые binaries, нулевые старты при подготовке, отдельный сервисный допуск и экспорт
первичных namespace/Run readback и настоящего delete-history timer из native dump. Полное
внешнее окно проверяется до target Server; неизвестный срок запрещает старт. Подробности —
в [порядке подготовки свежего окна](temporal-storage-recovery.md#подготовка-нового-ограниченного-окна-с-первичным-retention).
Отдельный прогон 2026-11-08 дал
[ограниченный PASS свежего синтетического восстановления](temporal-storage-recovery.md#свежая-синтетическая-сервисная-проба-2026-11-08).
Он не закрывает `UNKNOWN` прежнего архива, физическую сверку writer/полномочий T3
и эксплуатационные RPO/RTO. Разовый допуск израсходован; новый запуск требует своего допуска.

## Вход и запуск

Из корня репозитория подготовь JSON с абсолютными путями:

```json
{
  "kind": "comparison-h06-recovery-package/1",
  "summary": {
    "path": "/absolute/completed-h06/live-result-summary.json",
    "sha256": "<SHA-256 точных байтов сводки>"
  },
  "destination": "/absolute/new-recovery-package"
}
```

```sh
yarn comparison:h06:recovery --plan /absolute/request.json
yarn comparison:h06:recovery --run /absolute/request.json
```

`--plan` только читает входы. Он требует завершённый `PASS` профиля
`h06-autonomous-recovery/3`, подтверждённую остановку трёх Writer, отсутствие принадлежащих
попытке процессов по квитанции очистки, шесть завершённых фаз и отсутствие WAL/SHM/journal.
Результат содержит `mayRun=false`: архивирование не разрешает новую попытку.

`--run` создаёт только новый каталог вне исходных доказательств и рабочей копии. Повторный
запуск с занятым назначением отклоняется. Исходная сводка, результаты и первичные ссылки
проверяются по хешам; прежнее разрешение не расходуется повторно.

## Состав и проверка

До открытия SQLite инструмент снимает полный файловый перечень исходного пакета и рабочей
копии. Затем копирует их в собственный каталог, проверяет равенство байтов и открывает только
свои копии. Символические и жёсткие ссылки отклоняются. После восстановления повторно
проверяются исходные перечни.

| Компонент архива | Содержимое                                                                                      |
| ---------------- | ----------------------------------------------------------------------------------------------- |
| `legacy`         | Полный исходный пакет: SQLite, blobs, результаты, квитанции, копии Writer и сохранённый runtime |
| `workspaces`     | Полная рабочая копия, включая дескрипторы и Git                                                 |
| `artifacts`      | Байты достижимых внешних файлов и неизменяемые префиксы нативных журналов                       |
| `receipts`       | Перечни исходных файлов и явная карта разрешённых и отсутствующих ссылок                        |
| `build`          | Экспорт Store через штатный адаптер, только если сохранённое состояние уже заморожено           |

Ссылки собираются из сохранённых JSON, строк с JSON и декодированного состояния Store.
Файловая ссылка содержит путь и хеш, `ArtifactRef` — `sha256` и `bytes`. Диагностические
отпечатки RPC с полями `hash`, `bytes`, `direction` сохраняются как данные журнала;
они не объявляют отдельный файл для восстановления.
Сохранённая версия runtime выбирается по точному хешу, даже если нынешний файл репозитория
уже изменился. Для нативного журнала проверяется хеш каждой требуемой строки; на журнал
сохраняется один префикс до последней требуемой строки. Остальная переписка не расширяет
область поиска зависимостей. Отдельно сохраняется точный байтовый префикс из пары
`transcript`/`nativePrefix` квитанции `h06-delegated-retained-host-continuation/1`; его длина
и SHA-256 проверяются независимо от позднейших дописанных строк. Внешние файлы восстанавливаются
по карте исходного пути и
хеша внутри изолированного архива; исходные абсолютные пути и inode не перезаписываются.

Архив создаётся через `createBackup`, упаковывается в `recovery.tgz`, распаковывается в новый
каталог, проверяется через `verifyBackup` и восстанавливается через `stageRestore`.
Сравниваются все исходные файлы, рабочая копия и декодированные данные SQLite. В отчёте
сохраняются SHA-256 архива и manifest, первичная сводка, кандидат и его ресурсы, перечень
runtime, редакция Store, поколение владельца и три Coder.

## Замороженный и завершённый Store

Штатные `exportStore`/`restoreStore` требуют `state.frozen=true`. Для уже замороженного
источника экспорт выполняется на дополнительной собственной копии и проверяется
восстановление через эти адаптеры.

Завершённый H06/3 может иметь `frozen=false`: завершение Writer не меняет этот признак.
В таком случае инструмент сохраняет и восстанавливает точные байты закрытой SQLite через
штатный файловый архив, проверяет целостность SQLite и равенство состояния. Он не меняет
владельца, часы, поколение, редакцию или признак заморозки ради экспорта. Отчёт указывает
`method=closed-file-backup-restore` и `frozenStoreAdapter=NOT_APPLICABLE_UNFROZEN`.

## Значение результата

- `PASS` означает успешное автономное восстановление файлов и Store и полную найденную
  область ссылок.
- `PARTIAL` сохраняет успешное восстановление файлов/Store, но перечисляет каждую
  отсутствующую или изменившуюся внешнюю ссылку в `missingReferences` и `closure.json`.
- Ошибка целостности, незавершённый источник или изменение исходных файлов прерывают проверку.

В обоих успешных вариантах остаются `executionImport=false`, `requiresReconciliation=true`,
`mayRun=false`, `qualification=false`. Поля `temporalPostgresql`, `serverRpo` и `serverRto`
остаются `UNKNOWN`. Подключение к серверу и возобновление живого исполнения требуют отдельной
проверки и своих полномочий согласно
[ADR-0067](design/decisions/inherited/0067-run-reusable-agent-workflow-on-temporal.md).
