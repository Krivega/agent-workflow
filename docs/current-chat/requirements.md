# Требования и повторная экспертиза текущего чата

Подробный договор для соответствующего действия. Обычный рабочий цикл —
в [инструкции для сравнительных проверок](../../CURRENT-CHAT.md#сравнительный-запуск-из-исходников).

## Ранняя карта требований и адресные повторы

Перед полным прогоном исправь отказы дешёвых статических проверок и проверь наиболее
рискованный сценарий применимого профиля. Для UI сначала нужны малое окно, крупный текст,
ошибка ввода, фокус и прокрутка; затем полная обязательная матрица на стабильных входах.
Собери замечания одной редакции до `revise`. Изменение только записи результата в документации
после PASS проверяется по текстовому уровню обвязки и не требует повторять неизменный код.

Для нового пакета используй штатную последовательность:

```sh
node --import tsx cli/main.ts freeze-checks check-map.json
node --import tsx cli/main.ts preflight-checks-chat agent-request.json
node --import tsx cli/main.ts checks-chat agent-request.json
node --import tsx cli/main.ts package-checks package-request.json
node --import tsx cli/main.ts council-run-chat council-request.json
```

`freeze-checks` принимает карту ниже: schema_version/root/evidence_root/card/checks и
необязательные `probes: ChatCheckRequest[]`, `native: {id, engine, project, driver}`.
Результаты должны находиться вне репозитория. Команда фиксирует все tracked и nonignored
untracked файлы Git, включая новые/удалённые исходники, и объединяет объявленные зависимости
в один manifest проверок. Игнорируемые, внешние и транзитивные зависимости объяви явно:
Git не доказывает их полноту. Квитанция `details` адресует неизменяемый план по SHA-256.
Внешние Godot-проекты перечисляются до запуска; после изменения их состава подготовь новый план.
Кэш `.godot` результат импорта и в исходники не входит.

До подготовки плана проверяются ID и допустимость каждой команды. Для критерия `validate`
исполняемый файл и все аргументы должны совпасть с одной записью `validation_commands` проекта. Подготовка плана и новый запуск совета требуют минимум
1 ГиБ доступного места в проекте и evidence_root; ошибка `workflow-disk-space-low` содержит
путь и доступные байты. Это нижний порог, не оценка размера будущих снимков: для большой
серии отдельно проверь требуемое место. Проверка не удаляет данные и не выдаёт права очистки.
Совпадающий manifest сверяется один раз внутри вызова проверки плана; перед следующей
операцией входы и окружение проверяются заново. Постоянного кэша актуальности нет.

В обычный agent-request с допуском текущего владельца добавь `check_plan: {locator, hash}`.
`preflight-checks-chat` проверяет owner/native LOAD/writer, восстановление неизвестных операций,
актуальность входов и окружения, затем выполняет только startup-пробы. `scope: startup-only`
не означает готовность всей задачи. `checks-chat` проходит те же пробы, выполняет карту и
возвращает ссылку на пакет. Lease продлевается существующим механизмом; до запуска каждого
процесса входы и окружение сверяются заново. Ошибка или потерянная доставка блокирует
последующие проверки. Повтор того же запроса продолжает по исходным ID/квитанциям без
повторного исполнения подтверждённых операций; FAIL и unknown автоматически не повторяются.
Для изменённых исходников подготовь новый план с новыми ID.

Профиль `workflow-v1` передаётся реальному процессу и хешируется: из окружения удаляются
только метаданные вызова `npm_config_argv`, `npm_lifecycle_event`, `npm_lifecycle_script`,
`CODEX_TOOL_CALL_ID`; PWD/INIT_CWD равны root.
Остальные переменные значимы. Значения переменных не записываются в квитанцию.
Всегда запускай через указанный способ Yarn; смена значимого окружения запрещает reuse.
Для отдельных вызовов подготовки и исполнения используй один устойчивый вход:
`yarn --silent node --import tsx cli/main.ts freeze-checks|preflight-checks-chat|checks-chat <file>`.
Запуск через Yarn-script создаёт временный каталог `yarn--…` в PATH и `_` каждого процесса;
такая смена остаётся значимой. Указанный вход сохраняет проверку PATH и исполняемого файла.
Native-пробы проверяют версию заданного движка, последовательный headless импорт
(`import/use_multiple_threads=false`) и фактический запуск выбранного графического драйвера.
`SCRIPT ERROR`/`ERROR:` в полном журнале не допускают PASS даже при exit=0.
Драйверы не устанавливаются и не выбираются автоматически. Startup не доказывает качество UI.

Для добавления материалов используй `package-checks` с schema_version/root/evidence_root,
`check_plan`, `proofs` (все refs из предыдущего пакета, включая probes) и `artifacts: [path]`.
Упаковщик проверяет точные proof/log и окружение исходного плана, а не собственное окружение.
Пакет содержит `source_inputs`, `acceptance_inputs`, `checks`, `proofs`. В ReviewTarget перенеси
`inputs: source_inputs`, `evidence_inputs: acceptance_inputs`; baseline/checks сохраняют
исходный manifest. Новый пакет включает все исходные refs с теми же хешами. Оба manifest
проверяются на актуальность; binding, сравнение target, дизайн и арбитраж учитывают пакет.
Без evidence_inputs действует прежний единый manifest. См. [ADR-0059](https://github.com/Krivega/agent-workflow/blob/main/docs/design/decisions/inherited/0059-separate-check-inputs-and-evidence-packages.md).

`council-run-chat` принимает обычный agent-request и `council_file` внутри evidence_root,
первоначальный `council` и необязательный `binary` (по умолчанию codex). Начальный совет
сохраняется один раз; при продолжении council можно опустить. Изменившийся target/selection
требует явного обновления checkpoint: несовпадающий исходный запрос отклоняется.
Ответы сохраняются последовательно по мере готовности; сбой одной роли сохраняет остальные.
Команда использует прежний управляемый runner с независимыми сессиями, LOAD, origin и
восстановлением неизвестной доставки. Она не создаёт нового владельца задачи.

До первой дорогой приёмки подготовь `preflight-chat plan.json`. Обязательные поля:
`schema_version: 1`, `root`, `evidence_root`, `card`, `checks`. Каждый элемент checks:
`{criterion, implementation: [path], verification: [path], check}`. Поле check имеет договор
`check-chat`: id, criterion, command, discovery, attested_by, необязательный reuse.
В discovery включи карточку, реализацию, тесты, ресурсы, конфигурацию и транзитивные зависимости
проверки. Полноту подтверждает владелец через attested_by; инструмент не выводит её из импортов.
Все критерии карточки, включая продолжения строк, и обязательный validate должны иметь строку
карты. Команда проверяет наличие файлов и соответствие manifest, но не запускает команды.
`ready: true` означает полноту карты, а не правильность кода, PASS или решение человека.

Перед запуском acceptance добавь `acceptance_inputs` — полный manifest фактического пакета
совета — и `check.reuse` для каждого выполненного критерия. Preflight проверит актуальность
PASS, точные proof JSON и полные журналы в этом пакете. Отсутствующий журнал даёт
`missing-evidence` до запуска модели; изменённый пакет отклоняется. Источники проверки и
созданные ею доказательства остаются разными manifest, без циклического включения журнала
в собственные исходные входы. Готовность пакета не заменяет заключение совета и решение человека.

При повторном `check-chat` передай новый id и `reuse: {locator, hash}` прежнего proof JSON.
Повтор использует только целый PASS с тем же criterion, командой, полным manifest и отпечатком
содержимого и выбранного пути исполняемого файла (включая цель symlink), рабочего каталога,
Node, ОС и окружения. Относительный PATH и пустые
элементы PATH разрешаются от cwd команды; при отсутствующем PATH используется POSIX-поиск
`/usr/bin:/bin`. Невозможность прочитать выбранный executable означает неизвестный отпечаток,
а не пригодный для reuse hash. Отпечаток окружения сохраняется только как хеш.
Зависимости оболочки/ресурсы/транзитивные инструменты входят в discovery. Изменение входов
или среды запускает новую проверку; повреждённая ссылка и неизвестный исход блокируют её.
Без reuse действует прежний запуск. Старые proofs без отпечатка читаются, но не используются
для такой оптимизации. Результат reuse содержит исходный operation_id и reused_from;
новый PASS не создаётся. Reuse получает ту же блокировку критерия, что и новый запуск,
и повторно сверяет входы и среду после чтения proof. Чужая или неизвестная блокировка
не обходится; собственная резервная блокировка снимается без запуска процесса.
Полный validate остаётся обязательным по правилам проекта.

Разные критерии карточки должны иметь разные ID. Повторяющиеся ID отклоняются при
создании gates и завершении проекции; один PASS не закрывает два разных требования.

`repeat-council request.json` готовит повтор для прежних советников: schema_version/root/
evidence_root, council, target, roles и необязательный selection. Команда не запускает сеансы
и не принимает заключения. Без нового selection сохраняется прежняя консервативная проверка
всего target. С явным selection незатронутый PASS сохраняется только при том же scope,
требованиях и полном наборе входов роли. Изменённая роль включается в roles; FAIL и прежние
bindings остаются в history. Текущие входы применимых ролей проверяются перед переходами
execution; новое заключение проходит обычный council-chat и native binding.
Компактное поручение ссылается на массивы sources/requirements/reads полного request_file:
советник читает их из файла, а не копирует ссылочные объекты в источники ответа.

После реализации используй `refresh-council request.json` с полями `schema_version: 1`,
`root`, `evidence_root`, `council`, `target`. Команда проверяет актуальность полного target,
пересчитывает входы каждой применимой роли по её прежнему discovery и обновляет хеши требований.
В фазе acceptance команда сохраняет только полный PASS (`coverage: complete`) при прежних scope,
требованиях и полном manifest роли; изменённые роли, FAIL, NOT RUN и частичный PASS возвращаются
на проверку. Исходный FAIL и origin сохраняются. Повтор неизменной проверки получает новый ход
ответа и маркер доставки в той же сессии; неизвестная доставка восстанавливается по прежнему
маркеру. Не подставляй общий target в каждый role manifest. Неизвестная применимость, неполнота
и входы вне target блокируют обновление. Новые обязанности или зависимости за пределами discovery
требуют пересмотра явной карты ролей через существующий revise/repeat, а не автоматического N/A.
Результат возвращается ссылкой `details` на полный артефакт, как у `repeat-council`.
Это подготовка нового совета: команда не меняет Store, не запускает модель и не выдаёт READY.

Материалы UI/UX проверяются по текущему пакету даже при прежних исходниках роли.
Изменение или удаление использованного design.artifact переоткрывает дизайнера при
refresh/revise; repeat не переносит такой PASS в незатронутые роли. Прямой переход также
отклоняет устаревший материал. Добавление постороннего доказательства сохраняет полный PASS,
если все использованные артефакты остались в пакете с прежними хешами. История и binding
прежнего ответа сохраняются.

Управляемый запуск совета принимает готовый ответ сразу, пока другие роли ещё работают.
Сохранения общего совета последовательны; ошибка роли не отменяет уже принятые ответы других.
После `native-load-compacted` исполнитель сохраняет прежнюю попытку и один раз автоматически
повторяет полный LOAD и проверку в той же сессии, с новым маркером доставки. Повторная ошибка
остаётся блокером. Неизвестная доставка сохраняет прежний маршрут восстановления без слепого
повтора; другие роли повторно не запускаются.
Если последний ответ уже сохранён, повторный вызов восстанавливает завершённый снимок
прогресса без запуска транспорта и советников.

Для наблюдения за запущенным управляемым советом используй `wait-council request.json`:

Штатный маршрут без подготовки JSON:

```sh
node --import tsx cli/main.ts task-chat wait --state /absolute/external/run
node --import tsx cli/main.ts task-chat wait --state /absolute/external/run --after cursor-from-previous-snapshot --timeout-ms 60000
node --import tsx cli/main.ts task-chat wait --state /absolute/external/run --until settled --timeout-ms 60000
```

Он использует тот же файловый cursor и не читает нативную историю, не захватывает writer
и не запускает советников. Запускай producer один раз. Для терминального результата процесса
ожидай 30–60 секунд; короткий опрос оправдан только ожидаемым быстрым результатом.
Не перечитывай прежний полный вывод или историю ради неизменного статуса.
Прежний `wait-council` с JSON остаётся совместимым:

```json
{
  "schema_version": 1,
  "root": "/workspace/project",
  "evidence_root": "/external/task-state",
  "after": "cursor-from-previous-snapshot",
  "timeout_ms": 60000
}
```

Первый вызов без `after` возвращает текущий снимок. Следующий ждёт изменения cursor через
файловые события; `timeout_ms` — целое от 0 до 60000, по умолчанию 60000, 0 означает чтение
без ожидания. Источник — `evidence_root/council/progress.json`: run, фаза, scope, хеш target,
состояния ролей, их сеансы, ходы, вердикты и ошибки. Ответ содержит `changed`, `timed_out`,
`snapshot`; неизменное состояние сохраняет cursor. Завершённый или ошибочный запуск возвращается
сразу. Отсутствующий либо повреждённый снимок даёт ошибку, а не пустой успех.

`--until settled` (в JSON — `"until": "settled"`) ожидает `completed`/`failed` либо заданный
предел: промежуточные состояния ролей не возвращают управление модели. Прежний режим
`changed` сохраняет поведение cursor. Если предел достигнут при `running`, settled возвращает
`timed_out: true` даже при изменившемся cursor. Подписка предшествует первой сверке; периодическая
сверка файла внутри вызова восстанавливает потерянное уведомление. Смена run/фазы/scope/target
во время ожидания даёт `council-wait-target-changed`; результат другой операции не принимается.
Библиотечное ожидание поддерживает AbortSignal и не принимает позднее уведомление после отмены.
Предел остаётся 60 секунд; это не обещание фонового пробуждения завершённого хода.

Снимок роли содержит предметное `reason` из действующей карты применимости и `review_basis`:
прежние verdict/coverage/scope и состояние требований/manifest относительно прежней проверки.
Эти факты показывают основание повтора и сохранения PASS; решение о reuse остаётся у council.
Отсутствующая прежняя область выводится как null, неизвестная полнота — как unknown.
Ожидание native turn восстанавливает потерянный `turn/completed` по `thread/read` в том же
вызове. Неизвестная история/исход и закрытый транспорт возвращают отказ; новый turn не создаётся.
Терминальное состояние само по себе не доказывает PASS: вызывающий код проверяет первичный ответ.

Managed planning и runtime council сохраняют привязку ожидания к operation/session/turn,
run, owner/generation, редакциям требований и управления, ходу и первичному источнику.
Внутри native ожидания проверяются актуальные полномочия и lease; перед применением первичного
ответа проверка повторяется. Смена владельца, требований, отмена или поздний ответ дают отказ.
Сохранённое ожидание можно сверить в новом разрешённом ходе того же владельца без нового
create/send; старое поколение не принимается. Квитанция применения и история review_turns
сохраняют однократность. Локальные регрессии этого пути не заменяют квалификацию app-owned задачи.

Читающее ожидание `task-chat wait` не обращается к App Server и не захватывает writer.
Запусти совет один раз; при необходимости наблюдения ожидай 30–60 секунд с последним cursor,
не перезапускай совет ради опроса. Неизменный тайм-аут не означает новый прогресс.
`accepted` означает сохранённый ответ, включая FAIL/NOT RUN; `completed` — завершённый сбор,
а не всеобщий PASS или готовность задачи. Штатные проверки допуска остаются обязательными.
