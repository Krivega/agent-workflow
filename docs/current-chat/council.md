# Вызов и применимость совета текущего чата

Подробный договор для соответствующего действия. Обычный рабочий цикл —
в [основном руководстве](../../CURRENT-CHAT.md#штатный-вход-без-json).

## Советники текущего чата

Живая проверка отдельного read-only маршрута
фиксирует проверенный клиент, первичные доказательства и границы результата.

Советника создаёт текущий агент через `AppServerSessions.create` в отдельном persistent
`thread/start` с явными `sandbox=read-only`, `approvalPolicy=never`, моделью и effort роли.
До LOAD проверь `confirmSession(session, profile, true)`: свежая identity, пустая история,
отсутствие fork, фактический read-only и отключённая сеть. Неизвестный профиль означает NOT RUN.
Первый `load/observeLoad` получает исходный объект созданного сеанса: его receipt с
`operation=thread/start` вкладывается в LOAD как `creation`. Сохрани первый LOAD и в
`role_run.loaded.native`, и в `role_run.loaded.origin`. Приёмщик проверяет хеши обоих receipts,
пустые turns при создании, identity/project/workspace/profile и первый ход нативной истории.
Нельзя подставить receipt от resume с исключёнными turns или LOAD после посторонних ходов.
При повторе новый LOAD заменяет только `native`; `origin` и session ID сохраняются, в том числе
между planning и acceptance. Точная ссылка `origin` входит в review brief и binding.
Старые записи без доказательства создания остаются историей; их нельзя дополнять задним числом.

В managed-маршруте полный запрос совета сохраняется как неизменяемый `request-<SHA-256>.json`.
Поручение содержит `request_reader`: чтение через `read-artifact` и соседний `.role.ref.json`
проверяет исходный SHA и раскрывает полные inputs именно роли, requirements/sources/reads.
Общие target.inputs и target.evidence_inputs остаются адресными ссылками со счётчиками;
соседний `.ref.json` по-прежнему раскрывает весь оригинал. Полный снимок и его проверки
не сокращаются. Физический файл может содержать
версионные ссылки по хешу; обычный `JSON.parse` этого файла не является reader.
`councilReviewBrief(request, request_file)` передаёт точную ссылку, identity/parent/роль,
assignment, target и LOAD; длинные наборы inputs адресуются полями этого файла. Нативный
приёмщик сверяет весь файл с ожидаемым запросом, а `target_ref` ответа — с точной ссылкой.
Полный target восстанавливается только после этой проверки; модель не назначает его заново.
Для `ui-ux-designer` ответ также содержит обязательные `design.ui` и `design.ux` по
[профилю дизайнера](../../roles/ui-ux-designer.md#формат-и-обязательные-доказательства). Поручение
учитывает `phase`: planning проверяет предложение, acceptance — фактический результат.
Снимки и протоколы готовит исполнитель, включает в `target.inputs` и сохраняет доступными
для чтения. Советник реально просматривает материалы без изменения своих прав; недоступное
направление остаётся NOT RUN. Ссылки проверяются по байтам вместе с остальными входами;
binding покрывает весь ответ, включая раздельные выводы и наблюдения дизайнера.
Прежний полный формат поручения и ответа сохраняется. Подмена/исчезновение файла, чужая ссылка
или одновременные target и target_ref запрещают приём; входы проверок остаются полными.

Явный `-32602/input_too_large` восстанавливается только по одному коррелированному запросу
`turn/start` и ответу в первичном старом журнале RPC либо короткой квитанции нового транспорта,
после проверки отсутствия принятого delivery
в нативной истории. Отказ сохраняется отдельным receipt; повтор идёт тому же сеансу с новым
номером попытки. Тайм-аут, потерянный/неоднозначный ответ и другие ошибки остаются unknown.

Текущий principal остаётся исполнителем; его права и историю не меняют.
Это явный маршрут по [ADR-0049](https://github.com/Krivega/agent-workflow/blob/main/docs/design/decisions/inherited/0049-run-council-in-independent-read-only-sessions.md),
а не запасная подмена штатного подагента. Наследующий danger-full-access spawn_agent не подходит.

До LOAD установи `councilAdviserName(role)` через `thread/name/set`. Основной чат сообщает роль
и ссылку на сеанс. LOAD и повторные поручения направляй тому же ID через App Server.
Создание и отправка требуют сохранения intent/receipt; неизвестный исход восстанавливай по
нативному журналу, без слепого повторного создания или отправки.

`council-chat` получает council/role/role_run/role_turn. `roles` содержит первичный источник
полномочий пользователя, разрешённые отдельные session IDs, native project ID советника,
наблюдённый binary/args и `peer_observations[id]`: root/transcript/anchor.
Путь transcript должен точно совпадать с path из нативного thread/read.
Наблюдатель проверяет самостоятельный источник в transcript и thread/read, собственную
session_id, отсутствие parent/fork, точный проект, workspace и имя роли. Логический проект
процесса отличается от native project ID. `role_run.spec.parent_run_id` должен совпадать
с текущим запуском principal; project/identity/parent_run входят в точный нативный review brief
вместе с фазой, ролью, assignment, target, версиями входов и LOAD.

Проверки model/effort/read-only/network и полного scope/coverage сохраняются. Контекст прав
обязан относиться к role_turn: поздний безопасный ход не подтверждает прежний ответ.
Для managed-профиля проверяются файловые и сетевые ограничения; неизвестный или пишущий
профиль не становится read-only по тексту поручения. Наблюдение никогда не вызывает resume.

Первое поручение советнику содержит только LOAD: прочитать полные тексты выбранных процедур и
правил, вывести инструментом строки JSON path/sha256/content и подтвердить чтение. После его
завершения сохрани `AppServerSessions.observeLoad(session, query, loadTurn)` в
`role_run.loaded.native`: метод только читает завершённый ход и проверяет полные тексты.
Для управляемого отдельного сеанса `AppServerSessions.load` выполняет тот же LOAD через транспорт.
Поручение начинается с `councilReviewBrief(councilReviewRequest(...))`: запрос формирует
[`core/council.ts`](../../core/council.ts), а текст сообщения —
[`adapters/codex/councilReviewBrief.ts`](../../adapters/codex/councilReviewBrief.ts).
Оно содержит точные версии профилей, остальные входы, фазу и target.
Приёмка заново читает нативную историю того же сеанса: успешный полный LOAD должен предшествовать
`role_turn`, его userMessage — содержать точное поручение, а снимок ответа — совпадать с poll.
Результат получает receipt и binding транспорта, а не ссылку или binding, заявленные моделью.
Старый ответ нельзя зачесть повторно или перепривязать обновлением локального spec/LOAD.
Перед completed и повтором проекции заново проверяются профили обоих советов.

Замороженные источники могут включать карточку, индексы и связанные ссылки. При повторе
завершения проверка учитывает только существующий сохранённый план проекции: каждый файл
pending должен совпадать с before либо after, а confirmed — только с after. Хеш before
обязан совпадать с исходной квитанцией; для сравнения используется прежний вид manifest,
квитанции checks/baseline не переписываются. Новые и посторонние изменения, неверная база,
нечитаемый файл и symlink остаются блокерами. Это действует для источников исполнителя,
обоих наборов target и текущих входов ролей, включая повтор после частичной записи файлов.

Исправление форматирования после confirmed — отдельная правка текущих индексов по обычным
полномочиям, с текстовой проверкой обоих файлов. Сохрани исходные FAIL, intent и receipt;
не переписывай их и не формируй другой payload с прежним operation_id. Повтор confirmed
возвращает прежнюю квитанцию и не применяет исправленный prepare. Ручная правка не меняет
исторический результат проверки; повтор завершения по изменённым входам остаётся заблокированным.

Повтор идёт к прежнему
reviewer; замена требует отдельного recovery. Арбитраж/аудит передаются существующему supervision,
а human-gates требуют текущего связанного решения. Наличие маршрута не доказывает живой аудит.

Для `SUPERVISE/audit` применяется отдельный [договор аудитора](../../SUPERVISION.md#время-и-аудит):
`roles.audit_parent` — явно выбранный читающий вспомогательный родитель native auditor,
`peer_observations` содержит первичные наблюдения обоих. Он только запускает роль и не получает
владение основной задачей. Arbitration продолжает требовать родителя principal.
Клиент V2 принимает follow-up через штатный инструмент подагентов этого родителя; прямой ввод
в дочерний thread не используется. Технический LOAD и единственный содержательный локатор
снимка разделены; отсутствие роли, независимой истории или эффективного профиля даёт NOT RUN.

Старые ответы без новой привязки project/identity/parent_run читаются как история. Новый допуск
требует отдельного сеанса и нового review; исходные FAIL/receipts сохраняются.

`coordination-chat` доступен только текущему явно разрешённому orchestrator с coordinate и
подтверждённым LOAD. Он использует прежний coordinator/journal, разрешённые coordination_roots,
seed либо событие. Для пишущих детей `roles.peer_observations` задаёт выбранные журналы/anchors;
инспектор сверяет первичные метаданные и native thread/read без resume и изменения sandbox.
Неизвестные network/profile, другая identity/project и неподтверждённое родство блокируют ветвь.
Запуск вспомогательных ролей остаётся прежней отдельной операцией с intent/receipt; этот мост
не создаёт скрытого второго исполнителя и не расширяет полномочия поручения.

## Карта применимости совета

Перед новым запуском и редакцией главный агент анализирует требования, фактический diff и
потребителей по [triggers](../quality/agent-workflow-contracts.md#применимость-совета).
Пути помогают найти код, но сами по себе не доказывают неприменимость роли. Неизвестное
разрешается узким applicability-only запросом соответствующему специалисту до полного совета.
Советник не снимает с себя уже назначенную обязательную проверку: ошибку выбора или нехватку
входов сообщает как NOT RUN с основанием пересмотреть карту.

`--council-selection` принимает путь относительно проекта к JSON с `schema_version: 1`
и объектом `roles`. Его ключи должны точно совпасть с ID из `council.profiles` подключённого
проекта. При продолжении сверяй сохранённые состав и пути. Общий каталог задаёт
`council.catalog`. Каждая запись имеет одну из двух форм:

```json
{
  "trigger": true,
  "reason": "Конкретное изменение и обязанность этой роли",
  "requirements": ["review/role-proposal.md"],
  "inputs": { "files": ["path/to/consumer.ts"], "directories": ["path/to/dependencies"] }
}
```

```json
{ "trigger": false, "reason": "Почему требования и потребители этой роли не затронуты" }
```

`requirements` содержит хотя бы один предметный источник: полное предложение этой роли,
критерии и применимые договоры. Отдельный краткий файл по роли полезен для независимых
повторов; он сохраняет весь относящийся к роли смысл общего плана, включая зависимости.
Изменение общего плана требует заново сопоставить его с этими файлами, а не просто оставить
старую карту. Общий план остаётся контекстом поручения, версия карты — входом текущей задачи.
Все пути относительны проекту; `files` и `directories` обязательны и могут быть пустыми.
Каталоги раскрываются заново: появление зависимости отзывает прежнюю проверку.

Для предметной выборки перечисляй настоящие потребители и их договоры. Не выбирай корневые
`scripts`, весь прототип или `node_modules` только ради удобства перечисления: они связывают
роль с посторонними изменениями. Игнорируемые и внешние зависимости, действительно нужные
роли, перечисляй явно. Полный снимок общих проверок остаётся в target; role inputs его
не дублируют. Старые серии снимков сохраняй в истории, в текущий пакет включай нужные
доказательства и проверяемые ссылки на используемые прежние материалы.

Общие правила проекта и каждый `--source` входят в требования всех выбранных ролей.
Локальное требование указывай в `roles.<role>.requirements`, изменяемый код — в `inputs`;
профили ролей добавляются автоматически. Каждый явный `--target` должен входить хотя бы
в одну применимую область. Неизвестная/пропущенная роль, `trigger: null`, пустое основание,
лишние поля, непокрытый target или недоступный источник блокируют запуск.

Перед созданием selection составь в плане таблицу «роль → требование → вход → причина →
зависимость». Архитектору нужны изменяемые границы и договоры; специалисту по данным — кодеки,
хранение и отказы записи; методисту — учебные значения и тексты; дизайнеру — представления,
геометрия, ввод и кадры; DevOps — сборка, проверяющий скрипт и целостность доказательств.
Это основания поиска, а не закрытые списки. Проследи фактических потребителей и зависимости.
Общий массив файлов в каждой строке или одинаковые широкие каталоги требуют предметного
обоснования. Общий target остаётся адресно доступным. Неполноту сообщай как NOT RUN;
для уменьшения входа нельзя удалять необходимую зависимость.

Инструмент сохраняет отдельную неизменную запись выбора каждой применимой роли во внешнем
каталоге состояния и включает её хеш в требования. На допуске карта сверяется с текущими
источниками, сохранёнными записями и полными manifest ролей. Для новой редакции
проверяются её assignment и revision; незатронутый ответ сохраняет исходный native binding,
а не перепривязывается к новому ответу. Изменение основания, требований, профиля, discovery
или существенных файлов вызывает новую проверку соответствующей роли; смена общего scope
возвращает все выбранные роли. FAIL остаётся препятствием, а неизвестная полнота запрещает reuse.
Отметка роли как неприменимой не закрывает её прежний FAIL: он блокирует допуск, пока эта роль
не подтвердит исправление полным PASS. Промежуточный NOT RUN или частичный PASS его не закрывает.
Принятые исключения арбитража проверяются прежним путём приёмки и не заменяются отметкой N/A.

Продолжение старого сохранённого запуска не требует новой карты и не мигрирует его историю.
При явном `revise` оценка обязательна заново. Если все ответы уже получены или все роли
неприменимы, транспорт совета не запускается. Полный validate и остальные условия допуска сохраняются.

При восстановлении фрагментов AWJSON/архива применяется [ADR-0060](https://github.com/Krivega/agent-workflow/blob/main/docs/design/decisions/inherited/0060-preserve-reviews-after-dependency-restoration.md).
Хеш неизменного корневого документа связывает весь граф. Адаптер проверяет каждый достижимый
фрагмент, SHA-256 и разрешённый путь, включая вложенные архивы, при подготовке и актуализации.
Явное дублирование таких фрагментов во входах роли не меняет её логические материалы или
неизменяемый снимок выбора. Полный PASS сохраняет исходный ответ и native binding.
Независимый файл, изменённый корень/требование/discovery/scope требуют прежнего адресного
пересмотра; отсутствующий или повреждённый фрагмент запрещает reuse. FAIL, NOT RUN и частичный
PASS всегда возвращаются на проверку, включая planning. Граф хранения не заменяет предметный
анализ полноты источников.

## Низкоуровневое подключение профилей

Этот раздел предназначен вызывающему контроллеру. Участник читает обязанности и формат
заключения из [каталога ролей](../../roles/README.md#процедура-участника); сам себя он не запускает.

Предметная экспертиза — [каталог профилей](../../roles/README.md#экспертиза-ролей-совета). Для применимой роли включи
каталог и её собственный файл с текущими SHA-256 в `selection[role].requirements`,
`RunSpec.rules` и `RunSpec.sources`; сохрани предметные требования поручения.
Передай те же rules в нативный LOAD (`DataQuery.rules`), подтверди наблюдаемое чтение полных
текстов и запиши их в `LoadReceipt.rules` до содержательной работы. Сохрани исходную ссылку,
возвращённую `AppServerSessions.load` (либо `observeLoad` завершённого LOAD), в `LoadReceipt.native`; строка `observed_read` не доказывает
чтение. Подготовь `councilReviewRequest(council, role, run)` и начни содержательное поручение
точным результатом `councilReviewBrief(request)` из
`adapters/codex/councilReviewBrief.ts` от projectRoot. Передай его через нативный
send после LOAD: запрос связывает фазу, роль, run/session, assignment/sources, requirements,
входы роли, target и receipt LOAD. При изменении любого входа подготовь новое поручение.
В той же фазе и том же сеансе разрешено сохранить LOAD неизменных правил и процедур:
`reuseLoad` повторно сверяет receipt/hash, полное нативное чтение и отсутствие последующего
сжатия. Смена фазы, модели/effort, правил или процедур требует нового полного LOAD.
Изменение предметных входов требует свежего ответа, даже когда чтение правил сохраняется.
Профиль другой роли,
одна ссылка в тексте поручения и старое подтверждение чтения не заменяют эти входы.
При изменении профиля обнови требования, повтори LOAD и planning/acceptance затронутой роли;
общий файл затрагивает все применимые роли. Старые ответы сохраняются как история.
Для текущего чата запускай советников отдельным `AppServerSessions.create`/`thread/start`
с read-only, never, отключённой сетью и явной моделью/effort. Проверь свежую identity и пустую
историю через `confirmSession(..., true)`. До LOAD установи `councilAdviserName(role)`;
основной чат показывает роли и ссылки. Первый LOAD выполняй с объектом созданного сеанса
и сохрани его receipt также в `LoadReceipt.origin`. Он содержит первичный ответ `thread/start`
с пустыми turns. Приёмка проверяет identity/profile создания и что исходный LOAD — первый ход
нативной истории; resume с исключёнными turns и прежний чат не подтверждают создание.
Новые LOAD меняют `native`, сохраняя исходный `origin`; оба входят в точное поручение.
Логический parent_run сверяется с текущим запуском,
project/identity/parent_run включаются в точное нативное поручение. Штатный spawn_agent
с наследованными пишущими правами не заменяет этот маршрут.
Используй маршрут [council-chat](#советники-текущего-чата): отдельные identity, native
receipt, эффективные model/effort/read-only/network и полный scope/coverage. Адаптер проверяет
полный вывод чтения в нативной истории того же сеанса, порядок LOAD → answer, точное поручение
в userMessage и неизменность наблюдённого ответа. Он сам создаёт `ReviewAnswer.binding` версии 1
с первичным доказательством; binding из текста модели не принимается. Один answer turn нельзя
зачесть повторно. Старые записи без binding читаются как история и требуют нового review.
Перед проекцией completed и её повтором проверяются текущие профили planning и acceptance.
Общий outcome должен
совпадать с вложенным verdict. Все сеансы наблюдай без resume и изменения их sandbox;
наследованные права не объявляй read-only по тексту поручения. Проверяются первичные native
source, отсутствие parent/fork, независимая история и точное видимое имя роли. Контекст фактических прав относится к принимаемому
answer turn; более поздний безопасный ход не подтверждает прежний ответ. Старый самостоятельный сеанс
сохраняется как история и не получает текущий допуск автоматически.
