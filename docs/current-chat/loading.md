# Сравнительный запуск из исходников

Для штатного запуска задачи используйте [Temporal](../../CURRENT-CHAT.md#запуск-через-temporal).

## Команды и состояние запуска

Команды выполняются из рабочей копии Agent Workflow и подключают отдельное состояние
сравнительного запуска.
Пользователь ставит задачу в чате; предметную карточку и предложение готовит агент. Поддержаны компактная карточка
(`Цель`, `Границы`, `Критерии`) и полный ExecPlan (`Результат и не-цели`, `Критерии приёмки`).
Технические запросы, ID и хеши инструмент формирует сам. Агент составляет
[карту применимости совета](council.md#карта-применимости-совета); пользователь не готовит JSON или команды.
В записи критерия `- [ ] ID: описание` именем программной проверки служит ID; полное описание
остаётся в карточке и RunSpec. Без явного префикса сохраняется прежнее имя проверки.
`--human` по-прежнему использует точный текст критерия и сохраняет прежние человеческие gate.
Это позволяет исполнять подробные критерии без пробелов и пунктуации в техническом ID.

```sh
node --import tsx cli/main.ts task-chat start --state /absolute/external/run --card docs/exec-plans/active/task.md --plan proposal.md --council-selection roles.json
node --import tsx cli/main.ts task-chat load --state /absolute/external/run
node --import tsx cli/main.ts task-chat start --state /absolute/external/run
node --import tsx cli/main.ts task-chat continue --state /absolute/external/run
node --import tsx cli/main.ts task-chat revise --state /absolute/external/run --plan proposal-v2.md --affected criterion-id --council-selection roles-v2.json
```

`start` создаёт подключение выбранной карточки, отдельный Store и сохраняемые параметры.
`LOAD_REQUIRED` означает: вызывать `load`, пока он не перестанет выдавать файлы, затем повторить
исходное действие. Каждый вызов читает только ещё не подтверждённые файлы текущего marker.
Вывод LOAD сохраняй целиком в успешном нативном CommandExecution; достаточный лимит вывода
особенно нужен для большого файла правил. Внутреннее чтение и ответ команды до появления
этого события не дают READY. Новый turn/сжатие, revision и точный состав правил получают новый marker.
Изменение правил не принимает прежний обрезанный LOAD; новый marker требует полного свежего чтения.

`load --load-bytes 96000` увеличивает партию без дополнительных модельных переходов.
По умолчанию бюджет — 24000 байт UTF-8; допустимо 1000–512000. Бюджет включает JSON-экранирование,
метаданные и завершающий перевод строки, в том числе у первой строки. Размер части уменьшается
до выполнения бюджета; если не помещаются даже метаданные с одним символом, команда отказывает
с `chat-load-budget-too-small`, не подтверждая чтение. Большие файлы выдаются последовательными частями до 8000 символов с `offset` и
`length`, по одной части на вызов. LOAD подтверждает файл только после всех частей: совпадают
порядок, длина, точный текст и полный hash текущего источника. Старый полный вывод совместим. До вызова обеспечь достаточный лимит нативного вывода
и внешней обёртки: усечённый вывод не подтверждает LOAD. Увеличивай партию, только когда
можешь прочитать весь вывод; команда по-прежнему выдаёт отдельную строку для каждого файла.

После LOAD `start` сам создаёт независимые read-only сеансы, устанавливает имена, подтверждает
профили и первичный LOAD, отправляет и дожидается поручений, принимает planning и открывает
execution. Роли и ссылки выводятся при создании; повтор использует сохранённые сеансы.
`--binary` задаёт установленный Codex CLI, если `codex` отсутствует в PATH.
Новый `start` и `revise` требуют `--council-selection` с оценкой каждой роли; молчаливого
запуска всех ролей нет. Прежний явный `--skip-role role:предметное-основание` совместим:
он исключает указанные роли, остальные получают общий набор входов. Эти варианты не смешиваются.
Причина исключения сохраняется и не заменяет предметную оценку применимости.
В существующем запуске `start`, `continue` и `load` разрешают повторить прежнюю неизменную
карту или прежние исключения. Другой состав или путь карты требует `revise`; изменение байтов
прежней карты также блокирует продолжение с этой картой до пересмотра.
Перед советом служебный `prepare-chat` сохраняет principal в WAIT и привязку управления;
READY и реализация этим не разрешаются. Поэтому даже первоначальный FAIL planning допускает
штатный `revise`, сохраняя прежних советников и заключения.

`--source file` добавляет стабильное требование в RunSpec; `--target file` — изменяемый исходник
в manifest выполнения. Повторяемый `--human` задаёт точный текст критерия, требующего решения
человека. `validate` всегда остаётся обязательной программной проверкой. Ни роль, ни команда
не дают дополнительных прав реализации, публикации, установки или передачи другому чату.

`continue` читает актуальный Store, проверяет прежнего owner и pending effects, подтверждает
новый профиль/LOAD и выполняет существующий RESUME, включая восстановление истёкшего lease.
При действующем сроке каждый успешный `continue` продлевает его до 30 минут от вызова,
включая повтор неизменного RESUME без дублирования истории. Повтор проверяет текущий профиль,
owner, CAS и pending effects; сохранённый READY не заменяет эти проверки. При долгой работе
вызывай `continue` до истечения срока, например перед следующим этапом или после сжатия.
Автоматический ход без нового человеческого сообщения использует последний уже принятый
источник RESUME в том же активном чате. Он сохраняется как `previous_source_turn` и проверяется
по первичной истории: новый содержательный человеческий текст отзывает такой повтор,
paused/cancelled и новые REQUIREMENTS его не принимают. Свежий профиль/LOAD, завершение
прежнего хода, Store/CAS и известные исходы операций остаются обязательными.
При автоматическом продолжении без сжатия LOAD может повторно использовать принятые
первичные чтения: ссылки и хеши CommandExecution, тот же thread/workspace/профиль и текущие
байты каждого правила сверяются заново. Старые чтения до `compacted`, изменённые источники
и непригодные receipts не используются. Уведомление о завершении `SubAgentActivity` после
границы хода сохраняется в истории и не является поздней операцией записи; поздние starts,
команды, изменения файлов и MCP-операции по-прежнему блокируют продолжение.
Поздняя терминальная квитанция собственной фоновой команды допустима только при первичных
`started_at_ms` до границы хода и согласованном `completed_at_ms`, том же thread/turn/workspace,
уникальных command/process ID и точном совпадении команды и process ID с исходным нативным
code-mode вызовом и его результатом запуска. Порядок результатов связывается с отдельными
прямыми последовательными `text(await tools.exec_command(...))` и `text(await tools.write_stdin(...))`;
синтаксис разбирается установленным TypeScript, аргументы должны быть буквальными значениями.
Параллельная или иная неоднозначная форма не считается доказанной автоматически. Квитанция становится
источником continuation; исходная граница и история сохраняются. Все наблюдённые фоновые сеансы
требуют терминального результата. Новые поздние запуски, FileChange/MCP writers, неизвестные
квитанции, подмена, повтор и незавершённые операции по-прежнему блокируют продолжение.

При приёмке исходные ID, scope и condition замечания сохраняются. Неблокирующее подтверждение
его устранения от владельца с PASS остаётся в полной истории ответа; оно не заменяет определение
уже доказанно закрытого замечания. Само закрытие по-прежнему требует исходного condition,
истории исправления и текущего PASS владельца с точным evidence. Новый blocker, иной владелец,
FAIL и незакрытое условие этим правилом не исключаются.
Перед правкой связанной карточки в новом ходе сначала восстанови владельца через `continue`;
изменённые стабильные входы не обходят проверку прежнего scope. Пауза требует явного `continue`,
`start` и `revise` её не снимают.
`revise` сохраняет REQUIREMENTS с первичным человеческим источником, новой revision и REPLAN;
применимость ролей оценивается заново через `--council-selection` либо явный `--skip-role`.
Человеческие проверки неизменившихся критериев сохраняются; новые добавляются через `--human`.
После нового LOAD повторный `start` получает заключения затронутых прежних советников с сохранением origin
и истории; неизменные полные PASS сохраняются. Предыдущие требования и план сохраняй отдельными файлами; новую редакцию передавай
новым путём. Неизвестный исход create/send остаётся конкретным отказом без слепого повторения.
Если стабильный источник уже изменён и срок прежнего владельца истёк, `revise` проверяет
новый человеческий REQUIREMENTS, прежнюю завершённую границу, профиль, полный LOAD и исходы
операций до восстановления срока. REQUIREMENTS/REPLAN и RESUME сохраняются одним checkpoint;
до нового planning состояние остаётся WAIT. Обычный `continue` с изменённым источником
по-прежнему отклоняется; права, owner/generation и правила неизвестных эффектов не меняются.
Подготовленную редакцию planning до отправки нового LOAD/поручения можно заменить только при
точном совпадении сохранённого завершённого answer turn прежнего советника с его write-ahead
progress, при load_pending=false и проверенном доказательстве ответа. Начатая или неизвестная
доставка блокирует замену. Прежний PASS не принимается за новую редакцию.
Нативный `interrupted`/`failed` сохраняется отдельным доказательством; следующий вызов делает
одну новую попытку заключения в том же сеансе. Неизвестное состояние к такому повтору не допускается.

Параметры и намерения находятся во внешнем `--state`, принятый planning — в
`tmp/agent-workflow/chat-*/planning-*.json`. Store остаётся владельцем технического состояния.
Краткий результат содержит ссылку/hash полного доказательства и путь `request.json` для
совместимых низкоуровневых операций. Ранее созданные вручную запуски автоматически не
перепривязываются; прежние команды и адресные договоры сохраняются.

## Сообщения и полномочия

Агент понимает естественный текст и передаёт проверяемую операцию; инструмент не угадывает
полномочия по ключевому слову. Каждая операция содержит исходное сообщение/источник, task ID,
thread/turn, ожидаемые revision и generation, неизменный operation ID и проверяемый payload.

| Сообщение | Операция и условия | Отказ / отсутствие эффекта |
| --- | --- | --- |
| «Начни задачу через agent-workflow» | Выбор одной карточки, preview/apply; сохранить цель, границы и критерии | Неоднозначный выбор требует вопроса; информационный вопрос не подключает задачу |
| «Приступай» | Реализация только после принятого planning, действующего LOAD/READY и разрешения scope | Подключение и разрешение сами по себе не дают READY |
| «Учти …» | Новая revision требований; сохранить старые FAIL; отозвать только затронутые проверки через существующий REPLAN | Нельзя скрыть изменение под прежней приёмкой |
| «Статус» | Прочитать карточку, checkpoint, обязательные условия и ближайшее действие | Никаких create/resume/write при чтении |
| «Приостанови» | Сохранить paused и WAIT LocalRun; прекращение собственных writers подтвердить отдельно | Lease и отсутствие вывода не подтверждают остановку |
| Прерывание хоста | При следующем ходе сверить незавершённые операции и отметить interrupted | Не трактовать как отмену или успешную паузу |
| «Продолжай» | Та же session identity; новый подтверждённый turn/profile/LOAD, сверка входов и pending operations | Чужой сеанс или неизвестный эффект блокирует продолжение |
| «Отмени» | Отдельный cancelled, причина и невыполненный scope; проверенный stop receipt | Поздний ответ не возобновляет отменённое; возврат требует нового решения и запуска |
| «Да» / решение | Точный question ID, revision требований и разрешённая операция | Ответ старому/другому вопросу отвергается |

Разрешения задаются поручением, а не моделью, навыком или профилем хоста. Профиль фиксирует
наблюдаемую модель, effort и права; разрешённые RunAction задаются отдельно и не расширяются
при продолжении. Read-only поручение не создаёт подключение и не меняет код. Внешние действия,
координация и передача требуют соответствующего разрешения; сохраняется уже выданное.

## Выполнение и свидетельства

Planning готовится в чтении до READY и принимается существующим council; принятое evidence
переиспользуется execution. Результаты ролей проходят существующие проверки identity, scope,
профиля и источников. Арбитр, аудитор и координатор не заменяются самостоятельной проверкой.
Если обязательная роль недоступна, успешный Result запрещён.

Фактический процесс проверки сохраняет команду, exit code, полный журнал и manifest до/после;
изменение входов отзывает применимость даже при exit 0. Полноту manifest подтверждает владелец.
Проверка и текст роли — разные свидетельства. Execution владеет REVIEW/ACCEPT/CORRECT/RESULT/DONE;
LocalRun — READY/WAIT/CANCEL; projectLocalCard — проекцией и конфликтами revision.
DONE требует закрытия обязательных условий и успешной проекции.

## Загрузка процедур по действию

[ADR-0061](https://github.com/Krivega/agent-workflow/blob/main/docs/design/decisions/inherited/0061-load-workflow-procedures-by-action.md) задаёт режим
новых запусков `procedure_loading: by-action`. Полный каталог id/version/hash остаётся в RunSpec,
а LOAD подтверждает фактически прочитанное подмножество. Старый запуск без поля сохраняет
полную загрузку и прежний marker; автоматически его режим не меняется. Неизвестное значение
запрещено. Проектные правила по-прежнему читаются целиком.

База основного участника — bootstrap/task/evidence. Штатный start выполняет planning и открывает
реализацию, поэтому читает также council/data-roles/implementation/boundary-review: семь процедур
вместо двенадцати. Continue восстанавливает базу; новое действие требует свои процедуры.
LOAD выдаёт набор последнего ожидающего действия. Для расширения используй, например:

```sh
node --import tsx cli/main.ts task-chat load --state /absolute/external/run --procedure audit
```

Повторяемый `--procedure` допустим только для load и только для известного ID. Зависимости
добавляет core; чтение не выдаёт новых прав. Runtime сверяет текущие native receipts до действия
и сохраняет расширенный набор обычным LOAD. Без implementation/boundary-review запрещена
реализация, без coordination — координация; council, arbitration/audit, relay и finalization
проверяют собственные процедуры. Наличие процедуры только в каталоге не подтверждает чтение.

Смена правил или каталога меняет marker нового режима. Полнота текста, версии, профиль,
owner/generation, неизвестные исходы, FAIL и gates проверяются прежним путём. Сжатие отзывает
прежние чтения; повторное использование до сжатия требует точных первичных квитанций.
Клиенты, включая 0.164.0-alpha.11.1, проверяются точными версиями; неизвестные
версии не допускаются автоматически. Дополнительно разобраны точные версии `0.154.0`
(native participant прежней квалификации) и `0.165.0-alpha.1.2` (текущий desktop root).
Для `0.165` разные исходный `session.cwd` и текущий `turn.cwd` принимаются только для
непроизводного desktop/user чата с прежними session/turn/anchor IDs и подтверждённой
регистрацией обеих рабочих копий в одном физическом Git common directory. Проверяются
обратные `.git`/`commondir`/`gitdir` ссылки, отсутствие aliases, hardlinks и подмен.
Старые версии и `0.154` сохраняют строгое совпадение каталогов. Первичные записи не меняются.

Физическая проверка вынесена в один внутренний `src/adapters/codex/nativeWorkspace.ts`.
Её используют FileCurrentChatHost, NativeUserCommands.verify и Temporal Reader authority.
Для команды проверяется единственный `turn_context` её собственного первичного turn_id;
последующий ход не заменяет этот контекст. Прежние same-root входы, ID/hash/source/issuance,
target, owner/generation и редакции сохраняются. Нет переноса задачи или смены её workspace.

Эта совместимость проверяется метаданными, файловыми тестами и чтением протокольных полей.
Настоящие LOAD/READY и человеческое продолжение через рабочую копию требуют отдельной
квалификации и остаются открытыми. Для совета выбирай совместимый Codex через --binary
при первом start; наличие старого CLI в PATH не доказывает доступность выбранной модели.

## Подтверждение хоста

Продолжение выполняй через `continue-chat <agent-request.json>`: прежний базовый request,
текущие anchor/transcript и marker, `human_source` либо проверяемый `authorization`.
Для восстановления явной редакции `task-chat revise` передаёт в нём `message` типа REQUIREMENTS
с тем же текущим человеческим источником. Доставленное разрешение только на RESUME не даёт
права менять требования. Новые входы проверяются до восстановления; старая приёмка не переносится.
Команда сама строит RESUME с устойчивым ID и актуальной revision, проверяет входы и исходы,
продлевает lease либо восстанавливает истёкший срок прежнего owner/generation по ADR-0050.
Обычный `renew` после истечения запрещён. Для уже принятого активного READY того же
наблюдаемого нативного хода повторный `continue` заново проверяет identity/profile, первичный
человеческий источник, LOAD, входы и settled writers. Он сохраняет `live-owner-continuation`
и выполняет проверяемый `recover-owner` с прежними owner/generation/checkpoint и CAS.
Подтверждённое сжатие этого же хода также допустимо после нового полного LOAD, если до сжатия
уже был принят RESUME; проверка native origin, settlement и неизменности входов остаётся обязательной.
Первый допуск, новые требования, пауза и другой ход этим исключением не покрываются.
Frozen/released, чужой владелец, незавершённый старый ход, pending/unknown effect и неизвестная
writer-lock не обходятся.

Для доставки пользовательского поручения из другого чата источник вызывает
`authorize-chat <agent-request.json>` в текущем человеческом ходе. Request содержит обычные
root/transcript/anchor/human_source, внешний существующий `command_root` и точный
`target: {project_id, task_id, run_id, thread_id, generation, control_revision, requirements_revision}`.
Версии берутся из текущего состояния получателя; задержанная команда не отменяет позднюю
паузу, изменение требований или передачу владения. Вывод с `authorization: {locator, hash}`
сохраняется в нативной истории CommandExecution. Передача этой ссылки разрешена только
при наличии соответствующего пользовательского поручения; команда сама сообщений не посылает.
Получатель передаёт ссылку в `continue-chat`; приёмщик проверяет исходный human turn,
успешную нативную выдачу из `$CODEX_HOME/sessions`, неизменные байты и точный target.
Копия журнала, пересказ агента и обычное служебное сообщение разрешением не становятся.
Разрешено только RESUME прежнего владельца. Повтор доставки возвращает прежний результат.

Runtime-команды по умолчанию возвращают краткое состояние и `details: {locator, hash}`.
Для Store-команд `details` указывает на короткую квитанцию `purpose: operation-result`:
ID операции, итог и `state: {locator: <storage.root>#state, context}`. Это адрес текущего состояния,
которое читается через авторизованный Store; новая полная копия Store не создаётся.
Для `check-chat` ссылка ведёт на исходный proof проверки; для `council-chat` — на необходимое
текущее состояние Council для следующего вызова без Store. `status-chat` файлов не создаёт.
`status-chat` и `compact-context-chat` открывают Store только для чтения, без изменения режима
журнала. WAL-режим основной БД либо любой `-journal`, `-wal`, `-shm` дают
`chat-store-recovery-required` до чтения SQLite; это относится и к закрытой WAL-базе без
побочных файлов. Читающая команда не восстанавливает журнал и не переводит WAL в DELETE:
для этого нужна отдельная явно разрешённая пишущая операция. Обычный пишущий путь сохраняет
восстановление горячего rollback-журнала.
`--full` явно включает развёрнутый вывод, без сохранения дополнительного снимка.
`--brief` сохраняется как явное обозначение краткого формата;
`status-chat --brief` остаётся только читающим и показывает ownership, resume_required и blockers.
Он также показывает `checkpoint` (Store locator, техническую revision/generation, редакции
workflow/execution и ссылку на diff), `requirements_revision`, `last_result` и
`pending_operations`. Все разделы читаются из одного контрольного состояния; изменение revision
во время чтения даёт `chat-status-checkpoint-changed` вместо смешанной сводки. Pending/unknown
предлагают проверить исходную операцию и квитанцию. Locator указывает на текущий Store;
снимок статуса не является квитанцией допуска или разрешением повторить эффект.

Полный native LOAD роли поддерживает принятый
[ADR-0068](https://github.com/Krivega/agent-workflow/blob/main/docs/design/decisions/inherited/0068-confirm-native-role-reads-from-bounded-parts.md):
помимо прежней строки `{path,sha256,content}`, крупный источник передаётся строками
`{format:"aw-native-read-parts/1",path,sha256,content,offset,length}`. Смещения/длина — единицы
UTF-16, hash относится ко всему UTF-8-исходнику. Части непрерывны, не длиннее 8000 единиц,
каждая JSON-строка с переводом строки не больше 24 000 байт. Подтверждение появляется только
после полной длины и проверки общего SHA-256. Дубликат, пропуск, перестановка, смешение
форматов/версий, чужой hash и обрезанный вывод запрещают допуск. Пустой источник читается
старой полной строкой. `observeLoad`, `reuseLoad` и проверка ответа используют один decoder;
старые квитанции остаются совместимыми. Это полное чтение, отдельное от краткого режима К2/Р1.
Большие результаты сохраняются ссылками по [договору хранения](../../STORAGE.md#повторяющиеся-снимки-и-большие-артефакты);
`read-artifact ref.json` читает JSON конкретного артефакта с проверкой хешей.
Полные LOAD (`read-chat`) и notice `authorize-chat` не сокращаются.

Перед `execution-chat`, `check-chat`, `council-chat` и `project-chat` истёкший срок активного
владельца восстанавливается тем же проверяемым маршрутом `continue-chat`. Он требует уже
принятого RESUME и действительных входов; первый допуск, PAUSE и неизвестные эффекты
по-прежнему требуют своего разрешённого перехода. Это снимает необходимость угадывать
момент истечения между командами и не расширяет права текущего чата.

Версионный адаптер читает только локальный журнал выбранного CODEX_THREAD_ID; источник пути
выбирает агент по этому ID. Метаданные приложения сверяются с session_meta и turn_context.
Точные поддержанные версии перечисляет `isSupportedChatClientVersion` в
[адаптере хоста](../../adapters/codex/currentChatHost.ts); неизвестная версия, частичная запись,
чужой turn, неоднозначный источник и расхождение workspace/profile запрещают зависимую запись.
Метаданные выбираются по белому списку; инструкции, рассуждения и история других чатов
не сохраняются. Пути file URI нормализуются только для локальной authority.

LOAD подтверждается первичным успешным CommandExecution того же thread/turn/workspace:
маркер чтения, точные байты и hash всех выбранных процедур и правил совпадают с текущими файлами
и descriptor. Не считать готовым чтение части правил, старого turn или обрезанный вывод.
Технический run ID отличен от native session/turn ID. Адаптер не вызывает resume активного чата.

## Состояние и совместимость

Новый договор текущего чата имеет собственную `schema_version: 1` в расширении checkpoint.
LocalRun, Execution, TaskNotes и Store не повышают версии ради нового маршрута. Старые readers
игнорируют расширение, новый reader отказывает неизвестной версии до записи. Запись сохраняет
соседние поля; Store CAS, owner generation и неизменные operation IDs остаются обязательными.
Подключение использует прежние [preview/apply, backup и receipt](../../MIGRATION.md). Disabled не
включается от «продолжай»; новая задача не мигрирует соседние карточки.

Пауза — состояние управления чатом поверх существующего WAIT, а не новый LocalRun.status.
Перед эффектом сохраняется intent; подтверждение завершает тот же operation ID. Unknown
сначала восстанавливается по источнику эффекта, не повторяется с новым ID. Два владельца
отвергаются Store. Повтор после успеха возвращает прежнее доказательство; иной payload
с прежним ID — конфликт. Истечение lease не является разрешением смены владельца.

Восстановление той же identity после сжатия не является relay: требуются актуальный профиль,
LOAD, входы и сверка intent/receipt. Смена session сохраняет отдельный прежний маршрут
[stop/release/adopt/continue](../../RELAY.md), новую generation и явные полномочия. Пока нет живого
свидетельства остановки/сжатия/нативного аудита, соответствующая ветвь остаётся NOT RUN.
