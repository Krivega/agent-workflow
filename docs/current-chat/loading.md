# Загрузка и совместимость текущего чата

Подробный договор для соответствующего действия. Обычный рабочий цикл —
в [основном руководстве](../../CURRENT-CHAT.md#штатный-вход-без-json).

## Загрузка процедур по действию

[ADR-0061](https://github.com/Krivega/agent-workflow/blob/main/docs/design/decisions/inherited/0061-load-workflow-procedures-by-action.md) задаёт режим
новых запусков `procedure_loading: by-action`. Полный каталог id/version/hash остаётся в RunSpec,
а LOAD подтверждает фактически прочитанное подмножество. Старый запуск без поля сохраняет
полную загрузку и прежний marker; автоматически его режим не меняется. Неизвестное значение
запрещено. Проектные правила по-прежнему читаются целиком.

База основного участника — bootstrap/task/evidence. Штатный start выполняет planning и открывает
реализацию, поэтому читает также council/data-roles/implementation/boundary-review: семь процедур
вместо двенадцати. Continue восстанавливает базу; новое действие требует свои процедуры.
LOAD выдаёт набор последнего ожидающего действия. Для расширения используй, например:

```sh
yarn --silent agent-workflow task-chat load --state /absolute/external/run --procedure audit
```

Повторяемый `--procedure` допустим только для load и только для известного ID. Зависимости
добавляет core; чтение не выдаёт новых прав. Runtime сверяет текущие native receipts до действия
и сохраняет расширенный набор обычным LOAD. Без implementation/boundary-review запрещена
реализация, без coordination — координация; council, arbitration/audit, relay и finalization
проверяют собственные процедуры. Наличие процедуры только в каталоге не подтверждает чтение.

Смена правил или каталога меняет marker нового режима. Полнота текста, версии, профиль,
owner/generation, неизвестные исходы, FAIL и gates проверяются прежним путём. Сжатие отзывает
прежние чтения; повторное использование до сжатия требует точных первичных квитанций.
Клиенты, включая 0.164.0-alpha.11.1, проверяются точными версиями; неизвестные
версии не допускаются автоматически. Дополнительно разобраны точные версии `0.154.0`
(native participant прежней квалификации) и `0.165.0-alpha.1.2` (текущий desktop root).
Для `0.165` разные исходный `session.cwd` и текущий `turn.cwd` принимаются только для
непроизводного desktop/user чата с прежними session/turn/anchor IDs и подтверждённой
регистрацией обеих рабочих копий в одном физическом Git common directory. Проверяются
обратные `.git`/`commondir`/`gitdir` ссылки, отсутствие aliases, hardlinks и подмен.
Старые версии и `0.154` сохраняют строгое совпадение каталогов. Первичные записи не меняются.

Физическая проверка вынесена в один внутренний `src/adapters/codex/nativeWorkspace.ts`.
Её используют FileCurrentChatHost, NativeUserCommands.verify и Temporal Reader authority.
Для команды проверяется единственный `turn_context` её собственного первичного turn_id;
последующий ход не заменяет этот контекст. Прежние same-root входы, ID/hash/source/issuance,
target, owner/generation и редакции сохраняются. Нет переноса задачи или смены её workspace.

Эта совместимость проверяется метаданными, файловыми тестами и чтением протокольных полей.
Настоящие LOAD/READY и человеческое продолжение через рабочую копию требуют отдельной
квалификации и остаются открытыми. Для совета выбирай совместимый Codex через --binary
при первом start; наличие старого CLI в PATH не доказывает доступность выбранной модели.

## Подтверждение хоста

Продолжение выполняй через `continue-chat <agent-request.json>`: прежний базовый request,
текущие anchor/transcript и marker, `human_source` либо проверяемый `authorization`.
Для восстановления явной редакции `task-chat revise` передаёт в нём `message` типа REQUIREMENTS
с тем же текущим человеческим источником. Доставленное разрешение только на RESUME не даёт
права менять требования. Новые входы проверяются до восстановления; старая приёмка не переносится.
Команда сама строит RESUME с устойчивым ID и актуальной revision, проверяет входы и исходы,
продлевает lease либо восстанавливает истёкший срок прежнего owner/generation по ADR-0050.
Обычный `renew` после истечения запрещён. Для уже принятого активного READY того же
наблюдаемого нативного хода повторный `continue` заново проверяет identity/profile, первичный
человеческий источник, LOAD, входы и settled writers. Он сохраняет `live-owner-continuation`
и выполняет проверяемый `recover-owner` с прежними owner/generation/checkpoint и CAS.
Подтверждённое сжатие этого же хода также допустимо после нового полного LOAD, если до сжатия
уже был принят RESUME; проверка native origin, settlement и неизменности входов остаётся обязательной.
Первый допуск, новые требования, пауза и другой ход этим исключением не покрываются.
Frozen/released, чужой владелец, незавершённый старый ход, pending/unknown effect и неизвестная
writer-lock не обходятся.

Для доставки пользовательского поручения из другого чата источник вызывает
`authorize-chat <agent-request.json>` в текущем человеческом ходе. Request содержит обычные
root/transcript/anchor/human_source, внешний существующий `command_root` и точный
`target: {project_id, task_id, run_id, thread_id, generation, control_revision, requirements_revision}`.
Версии берутся из текущего состояния получателя; задержанная команда не отменяет позднюю
паузу, изменение требований или передачу владения. Вывод с `authorization: {locator, hash}`
сохраняется в нативной истории CommandExecution. Передача этой ссылки разрешена только
при наличии соответствующего пользовательского поручения; команда сама сообщений не посылает.
Получатель передаёт ссылку в `continue-chat`; приёмщик проверяет исходный human turn,
успешную нативную выдачу из `$CODEX_HOME/sessions`, неизменные байты и точный target.
Копия журнала, пересказ агента и обычное служебное сообщение разрешением не становятся.
Разрешено только RESUME прежнего владельца. Повтор доставки возвращает прежний результат.

Runtime-команды по умолчанию возвращают краткое состояние и `details: {locator, hash}`.
Для Store-команд `details` указывает на короткую квитанцию `purpose: operation-result`:
ID операции, итог и `state: {locator: <storage.root>#state, context}`. Это адрес текущего состояния,
которое читается через авторизованный Store; новая полная копия Store не создаётся.
Для `check-chat` ссылка ведёт на исходный proof проверки; для `council-chat` — на необходимое
текущее состояние Council для следующего вызова без Store. `status-chat` файлов не создаёт.
`status-chat` и `compact-context-chat` открывают Store только для чтения, без изменения режима
журнала. WAL-режим основной БД либо любой `-journal`, `-wal`, `-shm` дают
`chat-store-recovery-required` до чтения SQLite; это относится и к закрытой WAL-базе без
побочных файлов. Читающая команда не восстанавливает журнал и не переводит WAL в DELETE:
для этого нужна отдельная явно разрешённая пишущая операция. Обычный пишущий путь сохраняет
восстановление горячего rollback-журнала.
`--full` явно включает развёрнутый вывод, без сохранения дополнительного снимка.
`--brief` сохраняется как явное обозначение краткого формата;
`status-chat --brief` остаётся только читающим и показывает ownership, resume_required и blockers.
Он также показывает `checkpoint` (Store locator, техническую revision/generation, редакции
workflow/execution и ссылку на diff), `requirements_revision`, `last_result` и
`pending_operations`. Все разделы читаются из одного контрольного состояния; изменение revision
во время чтения даёт `chat-status-checkpoint-changed` вместо смешанной сводки. Pending/unknown
предлагают проверить исходную операцию и квитанцию. Locator указывает на текущий Store;
снимок статуса не является квитанцией допуска или разрешением повторить эффект.

Полный native LOAD роли поддерживает принятый
[ADR-0068](https://github.com/Krivega/agent-workflow/blob/main/docs/design/decisions/inherited/0068-confirm-native-role-reads-from-bounded-parts.md):
помимо прежней строки `{path,sha256,content}`, крупный источник передаётся строками
`{format:"aw-native-read-parts/1",path,sha256,content,offset,length}`. Смещения/длина — единицы
UTF-16, hash относится ко всему UTF-8-исходнику. Части непрерывны, не длиннее 8000 единиц,
каждая JSON-строка с переводом строки не больше 24 000 байт. Подтверждение появляется только
после полной длины и проверки общего SHA-256. Дубликат, пропуск, перестановка, смешение
форматов/версий, чужой hash и обрезанный вывод запрещают допуск. Пустой источник читается
старой полной строкой. `observeLoad`, `reuseLoad` и проверка ответа используют один decoder;
старые квитанции остаются совместимыми. Это полное чтение, отдельное от краткого режима К2/Р1.
Большие результаты сохраняются ссылками по [договору хранения](../../STORAGE.md#повторяющиеся-снимки-и-большие-артефакты);
`read-artifact ref.json` читает JSON конкретного артефакта с проверкой хешей.
Полные LOAD (`read-chat`) и notice `authorize-chat` не сокращаются.

Перед `execution-chat`, `check-chat`, `council-chat` и `project-chat` истёкший срок активного
владельца восстанавливается тем же проверяемым маршрутом `continue-chat`. Он требует уже
принятого RESUME и действительных входов; первый допуск, PAUSE и неизвестные эффекты
по-прежнему требуют своего разрешённого перехода. Это снимает необходимость угадывать
момент истечения между командами и не расширяет права текущего чата.

Версионный адаптер читает только локальный журнал выбранного CODEX_THREAD_ID; источник пути
выбирает агент по этому ID. Метаданные приложения сверяются с session_meta и turn_context.
Точные поддержанные версии перечисляет `isSupportedChatClientVersion` в
[адаптере хоста](../../adapters/codex/currentChatHost.ts); неизвестная версия, частичная запись,
чужой turn, неоднозначный источник и расхождение workspace/profile запрещают зависимую запись.
Метаданные выбираются по белому списку; инструкции, рассуждения и история других чатов
не сохраняются. Пути file URI нормализуются только для локальной authority.

LOAD подтверждается первичным успешным CommandExecution того же thread/turn/workspace:
маркер чтения, точные байты и hash всех выбранных процедур и правил совпадают с текущими файлами
и descriptor. Не считать готовым чтение части правил, старого turn или обрезанный вывод.
Технический run ID отличен от native session/turn ID. Адаптер не вызывает resume активного чата.

## Состояние и совместимость

Новый договор текущего чата имеет собственную `schema_version: 1` в расширении checkpoint.
LocalRun, Execution, TaskNotes и Store не повышают версии ради нового маршрута. Старые readers
игнорируют расширение, новый reader отказывает неизвестной версии до записи. Запись сохраняет
соседние поля; Store CAS, owner generation и неизменные operation IDs остаются обязательными.
Подключение использует прежние [preview/apply, backup и receipt](../../MIGRATION.md). Disabled не
включается от «продолжай»; новая задача не мигрирует соседние карточки.

Пауза — состояние управления чатом поверх существующего WAIT, а не новый LocalRun.status.
Перед эффектом сохраняется intent; подтверждение завершает тот же operation ID. Unknown
сначала восстанавливается по источнику эффекта, не повторяется с новым ID. Два владельца
отвергаются Store. Повтор после успеха возвращает прежнее доказательство; иной payload
с прежним ID — конфликт. Истечение lease не является разрешением смены владельца.

Восстановление той же identity после сжатия не является relay: требуются актуальный профиль,
LOAD, входы и сверка intent/receipt. Смена session сохраняет отдельный прежний маршрут
[stop/release/adopt/continue](../../RELAY.md), новую generation и явные полномочия. Пока нет живого
свидетельства остановки/сжатия/нативного аудита, соответствующая ветвь остаётся NOT RUN.
