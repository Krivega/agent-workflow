# Внутренние входы и исполнение текущего чата

Подробный договор для соответствующего действия. Обычный рабочий цикл —
в [основном руководстве](../../CURRENT-CHAT.md#штатный-вход-без-json).

## Локальная реализация по B1

[ADR-0063](https://github.com/Krivega/agent-workflow/blob/main/docs/design/decisions/inherited/0063-admit-local-implementation-with-executor-plan.md)
добавляет `--local-plan <plan.json>` вместо `--plan`. Это отдельный маршрут между механическим
применением принятого материала и существенным изменением. План готовит агент; пользователь
по-прежнему передаёт поручение. Обязательная карта `--council-selection` выбирает будущую
независимую acceptance; отдельные planning-сеансы для этого маршрута не создаются.

План версии 1 содержит `requirement`, непустые `basis`, `owner` и `consumers` как locator/hash,
`paths`, `consumers_complete: true`, `reason`, `checks`, `criterion` и объект `risks`.
Все восемь признаков `new_behavior`, `new_contract`, `architecture`, `storage`, `authority`,
`security`, `data_integrity`, `unknown_consumers` должны быть явно `false`. Неизвестность,
изменение договора или полномочий требуют обычного planning независимо от размера diff.
Владелец и все потребители входят в существенные входы; формальное заполнение полей не доказывает
полноту карты. Точную карту проверяет независимая приёмка.

READY сохраняет прежние native identity/profile/LOAD, owner/generation и проверку источников.
Admission и его исходные входы неизменяемы. При acceptance могут меняться только объявленные
пути реализации; требование, принятая основа и план остаются прежними. Изменившиеся требования,
потребители вне области или выход за пути возвращают задачу к обычному planning через `revise`.
Полный validate и независимая acceptance обязательны; self-PASS запрещён.

## Ограниченный coder по B2

[ADR-0064](https://github.com/Krivega/agent-workflow/blob/main/docs/design/decisions/inherited/0064-delegate-coder-in-isolated-copy.md) вводит отдельную
пишущую роль; советники, арбитр и аудитор сохраняют прежние права.
Операционный договор и восстановление — в [CODER.md](../../CODER.md).
Основной executor читает coordination в дополнение к implementation/boundary-review.
Команда `coder-chat <request.json> --brief` использует существующие request, Store и владельца
основного запуска. Coder не реализует механизм собственного допуска до его квалификации.

## Внутренний интерфейс агента

Пользователь ставит поручение текстом. Агент создаёт служебный request JSON версии 1 и вызывает
`yarn agent-workflow <операция> <request.json>`. Это внутренний интерфейс, не требование
обслуживать процесс пользователем. Общие поля: `schema_version: 1`, абсолютный `root`.

- `observe-chat`: `transcript` и `anchor` с thread_id/turn_id/workspace/host_id из приложения;
  thread сверяется с CODEX_THREAD_ID. Возвращаются только выбранные поля профиля и source/hash.
- `read-chat`: `descriptor`, уникальный `marker`, непустой `locators` из объявленных процедур
  и правил. Вывод содержит полные тексты/hash; агент читает небольшими порциями, чтобы первичный
  журнал клиента не обрезал доказательство. LOAD собирает все порции одного marker в том же turn.
- `connect-chat`: `descriptor`, внешний `journal`, одна запись в `cards` и `create: null` либо
  `cards: []` и `create` с title/goal/scope/criteria. Во внешнем selection intent сохраняются
  generated task ID и путь до записи карточки; повтор восстанавливает их, а не создаёт другую.
  Прежний ID существующей карточки сохраняется. Disabled, чужой journal, ручная правка и unknown
  version запрещают подключение; явное повторное включение остаётся прежней операцией миграции.

`selection.json`, backup и receipt остаются после отказа/отключения. Рабочая карточка не хранит
вторую копию технического журнала; соседние поля TaskNotes сохраняются прежним преобразованием.

### Готовность, исполнение и проверки

Следующие операции получают `descriptor`, `connection_journal`, `evidence_root`, `transcript`,
`anchor`, `generation`, `storage` с внешним root и grant. Для записи actor совпадает с native
thread; generation/owner, действующий lease, !frozen, manage, hash descriptor и включённое
подключение проверяются до эффекта. Стабильные входы сверяются повторно; pending-проекция
восстанавливает прежний plan/receipt без чтения уже перенесённого старого card locator. Поддержанный пишущий
профиль: never/danger-full-access/disabled; иной остаётся неподтверждённым.

- `bootstrap-chat`: агент сохраняет `planning_file` внутри workspace — объект версии 1 с task_id
  и принятым council; `spec.route.accepted_plan` указывает его точные байты. Передаёт `spec`,
  `marker`, `lease_until`. Новое хранилище создаётся с manage, первый владелец получает generation 1.
  Принятое planning, профиль, все процедуры/правила и источники проверяются до READY. Повтор
  сверяет прежний spec и LOAD; новая карточка индексируется один раз через сохраняемую проекцию.
- `execution-chat`: сначала `gates` и `code` переиспользуют принятое planning; далее агент передаёт
  существующий ExecutionEvent с ID/revision/generation. Процедуры исполнения, советов и надзора
  сохраняют свои договоры. `marker` подтверждает полный LOAD текущего native turn перед действием.
- `check-chat`: `check` содержит уникальный id операции, criterion (ID gate; по умолчанию id),
  command.file/args, discovery и attested_by.
  Запускается настоящий процесс, сохраняются intent, полный log, exit/signal, длительность и
  manifest до/после. Результат записывается также в LocalRun.results существующего Store.
  Переиспользование того же ID возвращает прежний proof; unknown не запускает новый процесс
  даже с новым ID того же criterion. Эксклюзивная блокировка criterion сохраняется при unknown
  и снимается после известного receipt только своим владельцем.
  Для критерия `validate` передай точные `file` и `args` из одной записи `validation_commands`
  доверенного дескриптора проекта. REVIEW проверяет receipts
  процессных gates; изменённые/неизвестные входы запрещают пригодный PASS.
- `project-chat`: после DONE и закрытых gates ещё раз проверяет актуальность Result и выполняет
  существующую проекцию. Pending/ручной конфликт остаётся открытым.
- `status-chat`: читает LocalRun/Execution и конкретные blockers; не создаёт Store/владельца,
  не посылает новый модельный ход и не меняет карточку.

Stable sources LocalRun содержат поручение и требования; изменяемые исходники входят в target
manifest Execution. После реализации не выдавай исходные hash изменённого кода за актуальные.
Артефакты проверок неизменны; коррекция использует новый ID операции с тем же criterion и сохранением прежнего FAIL.
Готовность этого связующего кода не означает живую квалификацию хоста: её сохраняют отдельно.

### Уточнения, решения и роли

`messages-chat` атомарно сохраняет `chat_messages` версии 1, LocalRun и WorkflowCheckpoint.
ASK/DECIDE связываются с task/thread/generation, question/action и revision требований; источник
решения — первичное сообщение пользователя именно текущего native turn. Повтор подтверждённого
события проверяет сохранённый источник, не требует повторного ответа. Новый вопрос по той же
операции приостанавливает применение прежнего решения; новый отказ заменяет прежнее согласие.
Уже связанная coordination запрещает REQUIREMENTS до изменения LocalRun: сперва завершить/отменить
дочернюю работу прежним маршрутом и выбрать отдельное поручение, не переназначать её скрыто.
REQUIREMENTS сохраняет исходное поручение и историю, увеличивает revision, переводит LocalRun в
WAIT, снимает LOAD и accepted_plan, открывает REPLAN с новым target/gates. Новое planning содержит
requirements_revision/assignment и ответы применимых ролей на текущие требования. Исторические
FAIL и receipts сохраняются; старые изменяемые исходники не проверяются как текущие требования.

## Пауза, отмена и восстановление

`control-chat` принимает событие управления с неизменным id, expected_revision/generation,
thread_id и первичным source. `chat_control` версии 1 сохраняется до первого READY; сбой этой
записи оставляет inbox. Старый READY без binding запрещает запись вместо тихого подключения.

PAUSE сохраняет paused/WAIT и снимает LOAD, не объявляет писателей остановленными. INTERRUPT
принимает только точную первичную границу прежнего turn (`compacted`, task_complete/task_aborted).
RESUME сохраняет identity/run/generation и разрешённые действия; требует текущего человеческого
поручения либо его подтверждённой доставки по ADR-0050, сверки intent/proof и входов, полного нового LOAD. Чтение до последнего turn_context
или compacted не подтверждает LOAD. Продолжение того же владельца в новом turn требует первичной
completed/aborted границы прежнего turn, полной истории его начатых вызовов и известных исходов
наблюдённых операций. Незавершённый вызов/item, неполная история и поздняя операция запрещают
продолжение. Неизменны thread/workspace/host/версия формата/эффективный профиль, run и generation;
Store отдельно проверяет owner, lease и CAS. Исходный профиль закреплён в origin; PAUSE/INTERRUPT
не меняют основание сравнения. unreconciled_turns сохраняет прежние активные и фактические
обрабатывающие turns, которые нельзя скрыть новой паузой. RESUME и STOP проверяют их закрытие
до READY или CANCEL. В checkpoint сохраняется continuation с прежним turn
и первичной границей. Это свидетельство продолжения, не writers-stopped receipt и не остановка
внутренних исполнителей приложения. Передача владения и финальный STOP требуют прежний полный
native stop proof. Переданный при RESUME stop receipt также проверяется, а не игнорируется.
Сжатие того же turn не считается остановкой писателей и не запускает relay.
Неизвестные check/lock/create/send блокируют продолжение; известное ожидание
читающей роли с session/load/turn можно продолжить опросом, без второго create/send.

Восстановление истёкшего срока выполняется после тех же проверок, до сохранения RESUME,
под общей writer-lock. Store сверяет checkpoint hash и CAS; доказательство продолжения
сохраняется отдельно. Активный CLI обновляет близкий к истечению срок до 30 минут,
а во время всех пишущих runtime-команд проверяет его каждые пять секунд без модельного вызова.
Проверка владельца, однажды завершившаяся ошибкой, блокирует последующие защищённые действия
этой команды даже после восстановления внешнего условия. Читающий status срок не продлевает.
Это не фоновая работа после завершения CLI и не доказательство остановки writers.

Каждая пишущая операция current-chat выполняется под одной эксклюзивной блокировкой
`agent-workflow-chat-writer.lock` в каноническом private parent Store: подготовка, effect и
сохранение исхода входят в один интервал. Другой Store в том же parent также ждёт завершения;
case/path alias не создаёт второго lock. Status остаётся читающим. Сбой процесса сохраняет lock
как unknown; lease, новый ID, другой evidence_root или поколение не разрешают его удаление.
Обычный известный выход освобождает только свой неизменённый lock. Повтор после unknown требует
отдельной подтверждённой сверки, а не автоматического повторного запуска.

Первый bootstrap до effects закрепляет evidence_root и физические dev/ino каталогов evidence
и Store в Store/chat-runtime.json версии 2. Пишущие вызовы сверяют binding до исполнения,
после подготовки непосредственно перед запуском процесса/записью карточки, перед сохранением
исхода и освобождением общего lock. Подмена binding или каталога сохраняет lock как unknown.
Legacy Store без binding либо с прежней версией доступен для чтения;
его успешные результаты не доказывают отсутствие неизвестного эффекта в другом каталоге.
Автоматическое подключение такого Store запрещено. Отдельный изолированный проверочный прогон
получает собственные task/run/Store/card/evidence без переноса прежних результатов; прежняя
попытка сохраняет свой PARTIAL и не становится восстановленной задним числом.

CANCEL сначала сохраняет cancelling/WAIT, причину и невыполненный scope. STOP отдельно сверяет
terminal boundary, остановку полного принадлежащего scope, реальные process identities и отсутствие
поздних записей в markers; затем LocalRun становится cancelled со следующим поколением. Поздние
ответы не возвращают active. `cancel-project-chat` выполняет только существующую cancelled-проекцию;
сохраняет конфликт pending, повторяет прежний operation и не выдаёт completed.

Stop receipt должен иметь абсолютный locator внутри разрешённого evidence_root. Его создаёт
внешний контроллер после реального AppServerWriters.stop, пока проверяемый чат остановлен. Пустая
выдача из неподтверждённого транспорта и текст модели не являются доказательством полноты writers.
Перед любыми действиями контроллер подтверждает target в `thread/loaded/list` того же соединения.
Неполная выдача или отсутствие target запрещают stop до сигналов/interrupt/terminate и receipt.
Чтение истории из другого App Server не подключает его к runtime приложения; `writer-runtime-unbound`
требует подключения к владельцу, а не автоматического `thread/resume` или запуска второго исполнителя.
Если видимость или остановка не подтверждены, финальный STOP и передача остаются NOT RUN.
Активный чат себя не resume/interrupt через native API; следующий ход использует проверяемый
договор same-owner continuation выше либо уже сохранённое внешнее stop-свидетельство.

Хеш контрольных файлов при создании и проверке receipt вычисляется по исходным байтам;
двоичные ресурсы не декодируются как UTF-8. Ограничения workspace и безопасного пути сохраняются.

Связанная coordination управляет собственной паузой UNAVAILABLE/RESUME/CANCEL, сохраняя исходный
LocalRun seed. Общий control не меняет её LocalRun и явно отказывает; status-chat показывает
состояние координации. Каждый следующий coordination-chat подтверждает identity/profile, owner
и свежий LOAD текущего turn без перепривязки исходного seed. Смена native session допускается
только отдельным внешним stop/release/adopt/continue; этот мост не создаёт successor и не
переписывает неизвестную привязку автоматически. Его native квалификация ведётся отдельно.

Настоящие REQUIREMENTS/ASK/DECIDE можно записать из нового human turn также при ещё не
подтверждённом восстановлении: это только новые требования/WAIT, без READY или права записи
целевого scope. Cancelling/cancelled отвергают такие события. После нового brief прежний reviewer
сохраняет identity; его активный Run/LOAD проверяется заново, исходные ответы остаются в истории.

## Проверка эффективности профиля

Не меняй квалифицированный model/effort ради предполагаемой экономии. Для сравнения обычной
реализации на medium и прежнего сильного профиля зафиксируй одинаковые входы, критерии,
инструменты и независимого проверяющего. Сравни время до принятого результата, число
запросов, вход без кэша, кэшированный вход, выход и пропущенные дефекты. Токены рассуждения
уже входят в выход; накопительные счётчики не суммируются между ответами.
Для сложных гонок и владения сохраняй сильный профиль до положительного сравнения.
Обновление профиля проходит штатную проверку requested/effective и новый LOAD; исторический
PASS не переносится на изменённый профиль. Размер файлов и процент кэша не доказывают
ускорения модели или денежной экономии. Новый эксперимент не запускает советы автоматически.
