# ADR-0061: загружать процедуры agent-workflow перед соответствующим действием

- **Status:** `accepted`
- **Date:** `2026-10-23`
- **Owner:** `agent-workflow`
- **Decision basis:** [явное поручение пользователя](../../exec-plans/completed/2026-10-23-workflow-procedure-loading.md#принятое-решение-пользователя) разрешает адресную загрузку с сохранением допуска и совместимости продолжения.

## Проблема

Штатный запуск загружает весь каталог процедур, включая арбитраж, аудит, координацию,
передачу и финализацию до возникновения соответствующего действия. Каталог нужен для
проверки версий, однако наличие записи в нём не требует заранее читать весь её текст.

## Факторы и ограничения

Подтверждаются первичные полные чтения, точные hash/version/locator, identity и профиль.
Изменение состава LOAD не выдаёт прав, не меняет owner/generation, FAIL, gates и приёмку.
Сохранённые запуски и история остаются читаемыми без миграции SQLite.

## Рассмотренные варианты

- **Выбрано:** явный режим загрузки по действию с проверкой необходимого набора перед эффектом.
- Сохранить полную предварительную загрузку: не сокращает контекст неприменимых процедур.
- Разрешить любое подмножество без проверки действия: допускает работу без обязательных правил.

## Решение

Новый штатный запуск сохраняет optional `RunSpec.procedure_loading: by-action` и полный каталог.
Отсутствие поля сохраняет прежний полный LOAD; неизвестный режим отклоняется.
Для основного участника базовый набор — bootstrap/task/evidence; роли сохраняют свой минимум.
Начальный start читает также процедуры планирования и открытия реализации, которые выполняет.
Дополнительные процедуры читаются перед соответствующим действием через штатный LOAD.

Чистая политика core определяет базу и зависимости. Реализация требует implementation и
boundary-review; координация — coordination; совет, надзор, relay и finalization проверяют
фактическое чтение своих процедур у низкоуровневых входов. READY не заменяет эти проверки.
Новый LOAD содержит только прочитанное допустимое подмножество с точными версиями и без дублей.
Проектные правила по-прежнему читаются полностью. Runtime проверяет актуальные native receipts
перед эффектом и сохраняет расширение существующим событием LOAD.

Каталог и правила входят в marker нового режима. Сжатие требует свежих чтений; прежнее
повторное использование native receipts разрешено только в установленной границе.
Формат legacy marker, прежние полные квитанции и история не переписываются.

## Обоснование

Версионный каталог, подтверждение чтения и разрешение действия имеют разные назначения.
Сокращение предварительного чтения безопасно при явной проверке зависимости до эффекта.

## Последствия

Обычный новый start читает семь процедур вместо двенадцати, а восстановление требует базу.
Дополнительное действие может потребовать ещё один LOAD. Цена — явный режим и проверки
при расширении; изменение процедур или прав по-прежнему запрещает прежний допуск.
Сокращение состава не является измерением экономии токенов, времени или денег.

## Проверка

Положительные и отрицательные сценарии core/CLI, точные native чтения, расширение и повторы,
сжатие, legacy продолжение, сохранение SQLite owner/generation/истории и полный yarn validate
с четырьмя метриками покрытия 100%. Живые советники проверяются отдельными первичными сеансами.
