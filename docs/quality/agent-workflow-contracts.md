# Договоры процесса агентов

Владелец — сопровождающий Agent Workflow. Договор задаёт границы процесса; реализация
и допуск конкретного сценария подтверждаются отдельно по [правилам качества](https://github.com/Krivega/agent-workflow/blob/main/docs/quality/README.md).
Процедуры, карточка и полномочия остаются у своих владельцев.

## Принятые правила

| Решение | Действующий выбор |
| --- | --- |
| DEC-01-B | Версионные локальные процедуры и явные договоры |
| DEC-02-B | Компактная карточка или полный ExecPlan по условиям PLANS |
| DEC-03-A | Отдельный статус cancelled; отмена не является завершением |
| DEC-04-A | Совет по условиям применимости; неприменимая роль имеет явную причину |
| DEC-05-B | Минимальный тест воспроизведения допустим до рабочего сценария; полный допуск обязателен |
| DEC-06-B | Управляемый постоянный сеанс App Server с проверенной связью с рабочей копией |
| DEC-07-A | `node:sqlite`, атомарные операции и внешние blobs по хешу |
| DEC-08-A | Ограничения отдельного поиска и оценка этапа; общего лимита проверок нет |
| DEC-09-A | Явный выбор модели и effort, подтверждение фактических прав; скрытых замен нет |
| DEC-10-A | Бессрочное сохранение до отдельной политики очистки |

## Принятый DEC-06-B

Для H2/R2 используются `project/create/read/list`, `thread/start/read/list/resume`,
`turn/start/interrupt` и события App Server. Реестр проектов принадлежит этому транспорту;
ID проекта приложения не подставляется вместо него. До записи проверяются project ID, точный
root/cwd и thread ID. Преемник — fresh persistent thread без fork, history и worktree;
resume сохраняет прежнюю identity и не считается relay. Видимость в приложении — дополнительное
наблюдение, без гарантии API приложения или передачи владения его активным сеансом.

Остановка состоит из interrupt хода, чтения принадлежащих сеансу background terminals,
явного terminate оставшихся процессов и наблюдения прекращения записей. Пустой список после
interrupt не требует выдуманного terminate; неизвестный writer запрещает release. Сам Ack
interrupt недостаточен. Защита от произвольных потомков и аварий проверяется в AW3/AW8.

Неизвестное создание сначала восстанавливается через сохранённую correlation, project/root,
lookup и чтение найденного thread. Отсутствие в неполной выдаче не разрешает второй create.
Idempotency проекта не переносится на создание сеанса. O6 использует тот же разрешённый
транспорт и scope: координатор подготавливает dispatch, внешний контроллер сверяет release
и выполняет его; запрет исходного действия не обходится. Отключение останавливает собственный
App Server и сохраняет evidence, не удаляя проекты/сеансы.

## Владельцы и bootstrap

Источники требований остаются в [карте проекта](https://github.com/Krivega/agent-workflow/blob/main/docs/README.md), [архитектуре](https://github.com/Krivega/agent-workflow/blob/main/docs/design/architecture.md),
[бизнес-правилах](https://github.com/Krivega/agent-workflow/blob/main/docs/design/business-rules.md),
[API](../design/api-contract.md) и [стратегии проверок](https://github.com/Krivega/agent-workflow/blob/main/docs/testing/strategy.md).
Карточка хранит delta, критерии, решения человека и ссылки, не копию этих требований.

Порядок определения типа: вызванный помощник → role; явно назначенный самостоятельный
координатор → orchestrator; прочий самостоятельный чат → executor. Создание помощника не меняет
тип родителя. Executor отвечает за реализацию, интеграцию и техническую приёмку; orchestrator —
за поручения, зависимости и продвижение. Координатор не пишет карточку чужого исполнителя.

Местный bootstrap: AGENTS → применимые строки маршрута → assignment/card → правило своего типа
в этом договоре → процедура предстоящего действия. У роли только собственный brief и явно
выбранные правила; у аудитора действует особое ограничение ниже. Неизменённый core повторно
не читается без причины. Отсутствующий обязательный источник блокирует зависимое действие.

Перед инструментом использовать существующий доступный native путь/адресное чтение; новый
helper требует конкретной неудовлетворённой потребности и сравнения в evidence. Отсутствующий
skill ищется по доступному каталогу, при разрешённом делегировании — ограниченным explorer;
эквивалент и его происхождение проверяются, обязательная процедура не заменяется догадкой.

Реестр `procedure_id/version/locator/content_hash` проверяется до действия. Run сохраняет
подтверждение чтения версии, а не только наличие файла. Путь к будущему SKILL.md не считается
загруженной процедурой. Исполняемые процедуры и режим явного подключения перечислены
в [каталоге](../../procedures/README.md); порядок подключения и отката — в [MIGRATION](../../MIGRATION.md).
Наличие файла не подключает задачу и не подтверждает живую квалификацию.

| Procedure ID | Когда загрузить | Связанный предметный договор |

## Карточка и проектный статус

Предлагаемая компактная карточка — один Markdown-файл в существующем каталоге ExecPlan,
одна строка его индекса; не отдельная очередь tasks. Минимум: стабильные project_id/task_id,
вид работы, owner/writer, ссылка на assignment и требования, scope/не-цели, критерии,
разрешённые действия, список этапов с результатом/оценкой/elapsed/evidence, blockers с resume
condition, текущий Result и решения человека. Для сложной работы используется весь
[нынешний шаблон](https://github.com/Krivega/agent-workflow/blob/main/docs/exec-plans/active/_template.md). task_id не выводится из cwd/chat/имени файла.

Предлагаемый раздел TaskNotes сохраняет неизвестные YAML-поля без потерь; формат исходного
TaskNotes не предоставлен, байтовая совместимость не заявлена. Местная версия содержит
schema_version, task_id и ссылки на state/evidence; данные неизвестной новой версии только
читаются без интерпретации, запись запрещена. Структура документа и ручные поля сохраняются.

Карточка — владелец цели, критериев, решения человека и проектного статуса. Store — владелец
технического состояния, событий, generation, elapsed, evidence head, запусков и операций.
Технический state содержит card locator/revision/hash и последний подтверждённый статус;
проектный статус — условно записываемая проекция. Это не распределённая транзакция с Markdown.
При конфликте ручной правки адаптер оставляет reconciliation pending и обе версии, не затирает
файл; dependent done запрещён. Перемещение карточки меняет locator, но не task_id.

| Техническое состояние | Проекция проекта после принятия DEC-03 | Условие |
| --- | --- | --- |
| inbox | active | Есть поручение, readiness ещё не выполнен |
| ready | active | Определены scope, критерии, источники, зависимости и применимость |
| in-progress | active | Есть полномочие и единственный writer |
| review | active либо verifying | verifying только когда реализация закончена, но собственная приёмка открыта |
| blocked | blocked | Сохранены причина, зависимый scope и точное условие возобновления |
| done рабочего пакета | Статус родителя не меняется автоматически | Остальные собственные критерии родителя всё ещё открыты |
| done всей задачи | completed | Все собственные критерии, человеческие решения и синхронизация подтверждены |
| cancelled | cancelled, предлагаемый `docs/exec-plans/cancelled/` | Только явная отмена; Result перечисляет невыполненное, без PASS |

До принятия и изменения PLANS строка cancelled — **не поддерживаемая проектная проекция**.
Адаптер не вправе подменить её completed/blocked без отдельного принятого варианта.
Finalization/archive ведутся отдельно от done и не отменяют завершённую приёмку.
Точные предлагаемые пути, компактный шаблон и порядок adoption старых карточек — в
матрице AW0b.
Непродуктовая работа без карточки хранит assignment/state/local evidence с assignment_id,
без фиктивного task_id и task-scoped вызовов Store; F2 создаёт карточку перед аудитом.

## Переходы и владение

[ADR-0050](https://github.com/Krivega/agent-workflow/blob/main/docs/design/decisions/inherited/0050-recover-workflow-owner-and-user-commands.md) добавляет
восстановление истёкшего срока прежнего владельца после подтверждения закрытых операций,
входов и прав под эксклюзивной writer-lock. Обычный renew после истечения остаётся запрещён.
RESUME может ссылаться на проверяемое исходное поручение пользователя из другого чата:
нативная выдача, точные project/task/run/target и неизменные байты обязательны.
Повтор команды сохраняет ID и прежний результат; служебный пересказ не создаёт полномочий.
Независимая приёмка, полный LOAD, обязательные проверки и STOP/release/claim не меняются.

Событие содержит event_id, project/task либо assignment context, run_id, expected_revision,
owner_generation, источник и payload. Повтор event_id с тем же payload возвращает прежний
результат; с иным — conflict. Время передаёт адаптер часов, core не читает системные часы.

| Переход | Необходимое основание | Сохраняемый результат |
| --- | --- | --- |
| inbox → ready | Источники, критерии, planning применимых ролей либо доказанный M1/прямой непродуктовый маршрут узла 07 | Readiness и версии входов |
| ready → in-progress | Authorization, scope без пересечения, CAS захвата | Writer, generation и исходная оценка |
| in-progress → review | Рабочий сценарий/baseline и обязательные применимые проверки | Точный diff/base, evidence и список reviewers |
| review → in-progress | Исправимый FAIL | Finding identity, один содержательный round, affected scope |
| review → done | Все gates PASS/обоснованно N/A, human gates закрыты, Result синхронизирован | Принятый scope и доказательства; NOT RUN запрещён |
| рабочее состояние → blocked | Подтверждённый blocker или отсутствие обязательных данных/возможности | Причина, сохранённое состояние возврата, resume condition |
| blocked → ready | Условие выполнено, нужное решение получено | Пересверка изменённых требований/входов, прежние FAIL сохранены |
| любое незавершённое → cancelled | Явная отмена | Остановка своих процессов, невыполненный scope, запрет поздней записи |
| передача владельца | Saved state → подтверждённая остановка → release → adoption | Новая generation, один преемник и наблюдаемое продолжение |

M1 не разрешает новую семантику: при её появлении вернуться к planning. Done/cancelled не
переоткрываются поздним событием; новая работа требует явного решения и новой ревизии scope.
Переход и намерение эффекта записываются одной транзакцией. Эффект имеет operation_id и состояния
not-started/confirmed/unknown. Unknown восстанавливается чтением receipt/состояния, не слепым retry.
Гарантия exactly-once внешнего API не заявляется.

Generation отклоняет старые технические записи, но не блокирует редактор/файловую систему.
До adoption проверить прекращение старых процессов по принадлежащим им IDs, доступ к workspace,
неизменность пересекающихся файлов и отсутствие внешней правки. Неизвестность блокирует только
пересечение; одинаковый путь в другом worktree не означает тождественный scope.
Отказ разрешения нельзя обходить через координатора, другой transport или новый процесс.

Этап имеет исходную положительную оценку ≤60 минут; это планирование, не таймер остановки.
Elapsed суммирует реализацию, проверки, review и внутренние ожидания; внешние/user waits отдельно.
Неизвестное время явно unknown; restart/relay/split не обнуляют учёт. Достижение 2× даёт событие
аудита, а не право пропустить проверку. Неприменимую оценку не выдумывать ради запуска F1.

## Ролевые поручения

Общий конверт запуска: run_id/parent_run_id, role, task или assignment locator, bounded scope,
критерий, разрешённые read/write/actions, procedure versions, requested model/effort и причина
выбора, client/host/workspace identity. Effective model/effort/permissions и политика истории
подтверждаются клиентом. Неподтверждённое значение — unknown, не совпадение по умолчанию.
Выбор пользователя приоритетен; неподдерживаемое сочетание требует решения без скрытой замены.

| Роль | Исходный профиль | Brief и результат |
| --- | --- | --- |
| Explorer | gpt-6.2-sol / medium | Вопрос, scope, entrypoints, критерий, формат → источники/revisions, находки, coverage и следующий адресный шаг |
| Raw-data-reader | gpt-6-luna / high | Source/ranges/revision, правила selection/classification → точные raw fragments без пересказа, пропуски, completeness и continuation |
| Evidence-explorer | gpt-6.2-sol / medium | Явный task_id, вопрос, scoped budget → metadata/выбранные IDs, revisions, coverage, continuation; известный ID не делегируется |
| Council adviser | В HTML не задан | Planning: предложение/требования; acceptance: точный diff/base/evidence → N/A либо scoped PASS/FAIL с findings и основаниями |
| Arbiter | gpt-6.2-astra / high | Trigger, подтверждённое противоречие/три rounds, точные источники, constraints → однозначный исход/compromise/нет решения, без реализации |
| Auditor | gpt-6.2-sol / xhigh | В содержательном brief **только ссылка карточки** → continue / сменить подход или исполнителя / пересмотреть ограничения, источники и checkpoint |

Для council предлагается наследовать выбор пользователя, фиксируя точные effective model/effort
каждого запуска в AW2; это местное заполнение отсутствующего исходного профиля, не «профиль v2».
Executor/orchestrator также не получают придуманной модели из схемы.

A1–A3 и независимые A5/A6: fork_turns=none, без истории родителя. Выбранные правила передаются
явно; роль не загружает bootstrap чужого типа. Для A6 технический конверт/профиль отделён от
содержательного brief: в нём нет диагноза, предыдущего обсуждения или выбранного решения.
Обязательные правила роли доступны отдельно и их загрузка подтверждена до действия.
Исходный F3 также задаёт agent_type=auditor: одно имя task_name не доказывает загрузку этого типа.
Именованный auditor квалифицирован дополнительным AW2.
DEC-09-A рекомендует этот проверенный путь. Если другой клиент не поддерживает тип,
эквивалентный профиль требует отдельного решения и проверки Q-02/Q-11; скрытой замены нет.

Follow-up A1–A3 направляется тому же agent identity; сохраняется счётчик созданий. Изменение
source revision требует пересверки ranges/selection до продолжения. Утрата identity — recovery
или явный новый запуск, не незаметное продолжение. Ролевой ответ сохраняет scope/revision,
источники, ограничения, PASS/FAIL/NOT RUN/N/A и непроверенное. Он не означает приёмку всей задачи.
Data roles, advisers, arbiter и auditor читают выделенный scope и возвращают результат;
у них нет прав реализации, захвата карточки, resolve или архива. Поручение не разрешает
дальнейшее делегирование само по себе. Нужная запись evidence остаётся у producer/main.

### Адресный поиск и продолжение

Известный файл, символ или evidence ID читай адресно. Для известной области используй `rg`,
владельца и его непосредственных потребителей. Неизвестные распределённые связи передавай
Explorer с ограниченным вопросом по прежнему договору A1; заданные ranges большого источника —
Raw-data-reader. Семантический инструмент IDE/LSP применяй, когда он доступен и нужна точная
связь типов/вызовов; его отсутствие указывай как ограничение. Текстовое совпадение не доказывает
такую связь. Новый сервер или индексатор для этого маршрута не требуется.

Ответ связывает вывод с владельцем, потребителями, путями/символами и revision; отмечает
покрытие и пропуски. Follow-up идёт тому же участнику. Изменённый источник требует пересверки
затронутого вывода; неизменный принятый результат повторно не исследуется без конкретного пробела.
Сводка карточки ссылается на цель, требования, текущее состояние Store, открытые FAIL и pending
операции. Она помогает продолжить работу, но не становится второй технической очередью.

## Применимость совета

В режиме текущего чата советники — отдельные read-only сеансы App Server по
[ADR-0049](https://github.com/Krivega/agent-workflow/blob/main/docs/design/decisions/inherited/0049-run-council-in-independent-read-only-sessions.md).
Связь с задачей подтверждается project/identity/parent_run/assignment/phase/target в точном
нативном поручении; логический parent_run сверяется с текущим запуском. Первичные transcript
и metadata подтверждают самостоятельную identity без parent/fork, название и реальные права.
Первый LOAD и первичный receipt `thread/start` подтверждают пустую историю при создании.
Ссылка `LoadReceipt.origin` входит в точное поручение и сохраняется при повторных LOAD того же
сеанса; приёмщик сверяет первый ход нативной истории. Старый чат или resume с пустым списком
исключённых turns не заменяет это доказательство.
Наблюдение не вызывает resume и не меняет права. [Договор текущего чата](../../CURRENT-CHAT.md#советники-текущего-чата)
владеет запуском, названиями и ссылками. Старые ответы без новой привязки остаются историей.

Предметную экспертизу проекта задают `council.catalog` и `council.profiles`
[дескриптора подключения](../design/api-contract.md#дескриптор-подключения-cli).
Для каждой объявленной роли указывается trigger либо предметное N/A.
Для применимой роли общий файл и собственный профиль с хешами входят в requirements,
sources, rules и подтверждённый LOAD. Приёмка сверяет нативное чтение полного текста в том же
сеансе до ответа и точный запрос с фазой, ролью, входами и receipt LOAD. Binding версии 1
создаёт адаптер из первичных наблюдений; слова модели и повтор прежнего answer turn не дают допуск.
Старые записи без binding остаются историей до новой проверки. Текущие версии профилей проверяются
при приёмке, переходах исполнения и перед проекцией completed, включая повтор;
изменение требует повторной проверки затронутой роли. Сам профиль не расширяет
полномочия. Порядок загрузки принадлежит [council](../../procedures/council.md).

Существенное изменение по узлу 07 требует planning до реализации и acceptance на фактическом
scope. Для механического применения уже принятого материала и полностью заданного простого
непродуктового текста совет не запускается. Открытая неизвестность о применимости решается
узким applicability-only запросом, а не произвольным N/A.

[ADR-0063](https://github.com/Krivega/agent-workflow/blob/main/docs/design/decisions/inherited/0063-admit-local-implementation-with-executor-plan.md) добавляет
узкий допуск однозначной локальной реализации принятого договора по сохраняемому плану
исполнителя. Проверяются требование, принятая основа, владелец, полная карта потребителей,
пути, риски и проверки. Новые поведение, договор, архитектура, хранение, полномочия,
безопасность, риск потери данных и неизвестность требуют planning. Независимая acceptance,
LOAD, owner/generation, FAIL и полный validate сохраняются. Точный формат и возврат к planning
при изменении входов принадлежат [CURRENT-CHAT](../../CURRENT-CHAT.md#локальная-реализация-по-b1).

[ADR-0064](https://github.com/Krivega/agent-workflow/blob/main/docs/design/decisions/inherited/0064-delegate-coder-in-isolated-copy.md) разрешает executor
поручить ограниченную реализацию coder в отдельной копии без общего coordinate. Coder не получает
историю родителя, карточку, Store, делегирование или самоприёмку. Основной executor владеет
исходными областями, интеграцией, общими проверками и передачей на независимую acceptance.
Проверяемые права, резервирование SOURCE root+paths, остановка и восстанавливаемый импорт
описаны в [операционном договоре](../../CODER.md).

Для ролей из [каталога поставки](../../roles/README.md) применяются следующие основания.
Собственные роли проекта используют основания, заданные его предметными профилями.

| Роль | Обязательный trigger в местном предложении | Владелец источника |

Две специализированные роли расширяют исходный состав A4 местного процесса. Для изменения
таймера мини-игры применим разработчик мобильных приложений и игр; при изменении учебного
смысла ограничения времени также применим методист — литературный редактор. Изменение подсказки
требует методической и литературной оценки, но само по себе не требует мобильной экспертизы.
Для серверного индекса без изменения игровых требований обе новые роли могут быть N/A
с обоснованием. Пересечение областей не отменяет другие применимые роли.

UI/UX-дизайнер возвращает отдельные `design.ui` и `design.ux` с verdict, coverage, reason и evidence
по [профилю](../../roles/ui-ux-designer.md#формат-и-обязательные-доказательства).
В planning положительный вывод требует `proposal`, в acceptance для UI — `screens`, для UX —
`interaction`. Артефакты с текущими SHA-256 входят в `target.inputs`; наблюдение описывает реальные
проверки. Отсутствие возможности просмотра/взаимодействия не становится N/A. Общий FAIL следует
из любого FAIL; иначе NOT RUN из любого NOT RUN или partial; только остальные полные проверки
дают PASS. Один N/A требует основания; обе N/A требуют переоценить применимость роли.
Продуктовые цели, корректность реализации и методическая экспертиза остаются у прежних ролей.

Старый selection без новых ролей, включая `ui-ux-designer`, не даёт текущего допуска (`missing-role-selection`).
Сохрани историю и явно составь полный selection по текущим требованиям; не дополняй его
автоматическими N/A. Для применимых ролей нужны актуальные профили, LOAD и проверка;
обновление общего профиля затрагивает все применимые роли.

Trigger создаёт обязанность выбрать роль, а не полномочие её запустить. Нет разрешения или
возможности — NOT RUN обязательного совета; не самостоятельный self-review под именем роли.
Для каждой роли сохраняются trigger/причина N/A и версия требований. Неприменимая роль
возвращает ровно N/A и прекращает работу; основание неприменимости хранится в selection.
Пропущенная обязательная роль не превращается в N/A. Planning оценивает предложение без
несуществующих будущих результатов; acceptance выбирает роли заново по реальному изменению.
Новая область после planning возвращает только затронутую роль.

## Реализация и приёмка

Executor находит entrypoint и ближайших потребителей, расширяет область по конкретному риску.
При принятом DEC-05-B сначала допустимо воспроизвести дефект минимальным тестом. Затем нужен
реальный работающий сценарий → измеренный baseline → затронутые проверки поведения/границ →
acceptance. Фикстура не доказывает интеграцию; новая инфраструктура не подменяет результат.
Все прежние обязательные проверки, включая полный validate для кода, сохраняются.

Finding: стабильный finding_id, owner/trigger, scope, источники/revisions, условие устранения,
раунд, original FAIL/dissent и disposition. Один цикл correction + affected review — один round;
голоса нескольких ролей и повторное чтение не добавляют rounds, смена HEAD не сбрасывает серию.
Re-review тому же adviser охватывает correction/open finding/new delta.

Принятый дочерний результат переиспользуется ссылкой по договору применимости в плане.
Неизменные существенные входы сохраняют reuse при другом HEAD; изменённая зависимость, грязный
вход, изменение discovery set, открытый дефект/риск требуют затронутой проверки. Неполный список
входов или недоступный вход дают unknown. Общий validate интеграции остаётся обязательным.

## Арбитраж и аудит

Подозрение E1 сначала проверяет применимая роль; подтверждённые blocker/contradiction сохраняют
источники и зависимый scope. Арбитр новый и независимый: trigger initial-contradiction либо третий
подряд содержательный FAIL одного finding. Он не реализует, не тестирует и не снимает gates.
Однозначный исход реализует main и проверяет affected reviewer. Initial compromise идёт человеку;
three-fail compromise может снять только спорный finding после рабочей проверки и сохранения
original FAIL, dissent, exact exception и остаточного риска. Обязательный дефект/проверка или
human gate так не снимаются. Сомнение/нет решения → blocked с resume condition.

F1 вызывается при 2×, сомнительном подходе или завершённой цепочке без подтверждённого прогресса.
F2 сохраняет исходную цель, выполненное, elapsed и ссылки в карточке; если карточки не было,
создаёт её без выдуманного времени и диагноза. F3 получает только её ссылку. Вывод/checkpoint
сохраняются один раз, технический owner остаётся прежним; координатор назначает следующий
результат. Уже обработанный порог не создаёт немедленно новый audit; нужен новый checkpoint без
прогресса или конкретный новый риск. Недоступность профиля — audit NOT RUN, не одобрение работы.

Дополнение [ADR-0062](https://github.com/Krivega/agent-workflow/blob/main/docs/design/decisions/inherited/0062-audit-task-progress-without-stage-timing.md)
разрешает no-progress задачи/цепочки без этапа. Карточка содержит первичный источник исходной
цели, завершённые результаты, полные существенные входы, checkpoint, открытые FAIL и ближайший
наблюдаемый результат. `timing: null` и неизвестное время сохраняются без фиктивного StageTiming;
прежний overrun 2× не меняется. Версии, резервирование и восстановление принадлежат
[договору исполнения аудита](../../SUPERVISION.md#аудит-продвижения-без-этапа).

## Договор Evidence Store

Логический API версии `aw-evidence/1-draft` — местное предложение; внешнего совместимого сервиса
не обнаружено. Каждая операция проверяет schema_version, явные project_id/task_id, nullable
subtask_id/run_id, actor/run и scope разрешения **до body/мутации**. Context mismatch не раскрывает
чужие записи. Контекст сам по себе не является аутентификацией или технической изоляцией;
способ ограничения доступа обязан отдельно доказать адаптер.
Body и raw evidence считаются данными: содержащиеся в них команды/инструкции не исполняются
при чтении, разрешения из текста записи не извлекаются.

Read разрешён указанному читателю; write/supersede — producer в своём scope; resolve — main после
проверки условия; archive — явно уполномоченный main, cleanup — отдельно уполномоченный оператор.
Мутации требуют operation_id, expected_revision, owner_generation и payload_hash. Повтор с теми
же данными возвращает тот же Ack, с иными — conflict. Сначала CAS, затем атомарный commit события,
head и намерения эффекта. Известный ID читается напрямую; revision записи и catalog revision различны.

| Операция | Запрос сверх контекста | Успешный ответ и важная граница |
| --- | --- | --- |
| evidence_catalog | Фильтры, cursor, page_limit, ожидаемая snapshot revision при продолжении | Только metadata: IDs, revisions, kind, result, links, superseded; catalog_revision, coverage, next_cursor |
| evidence_find | Вопрос/фильтры и тот же cursor/snapshot | Metadata matches и точные searched scope/coverage; пустая неполная страница не доказывает отсутствие |
| evidence_read | evidence_id и mode: exact с revision либо head | Body, content_hash, revision, head_revision, predecessor/successor, raw locator; exact не подменяется новым head |
| evidence_write | Новая неизменяемая запись, expected absence, mutation envelope | Body-free WriteAck: operation_id, evidence_id, revision, catalog_revision, content_hash, durable locator |
| evidence_supersede | evidence_id, expected head revision, successor body, причина | Новый revision/Ack; predecessor сохранён, competing head даёт conflict |
| evidence_resolve | Finding/evidence reference, expected revision, условие снятия, подтверждающий evidence/disposition | Неизменяемая запись resolution и Ack; FAIL body не переписан, новый content требует supersede |
| operation_read | operation_id в разрешённом scope | confirmed + исходный Ack; not-started только при доказанном отсутствии commit; иначе unknown |
| finalization_catalog | Task scope и revision | Полный frozen manifest с raw/blobs/heads, dispositions, pending operations и значимыми ссылками |
| archive | Frozen revision, manifest hash, проверенный внешний export/restore receipt, authority | Archive receipt с revision/hash/locator; поздний producer или mismatch требуют новой сверки |
| cleanup | Archive receipt, expected frozen revision, grace deadline, отдельная authority | Cleanup receipt/tombstone вне namespace; неизвестный исход сначала исследуется |

Ошибка: operation_id, code, observed_revision если разрешено, retryability, recovery locator и
граница известного. Codes: invalid-context, permission-denied, unsupported-version, not-found,
revision-conflict, stale-owner, budget-exhausted, unavailable, corrupt, unknown-outcome.
not-found допустим лишь для полного точного разрешённого поиска; нет права — permission-denied.
CAS conflict не повторяет запись автоматически и не перезаписывает ручной ввод.

Evidence содержит scope/criterion, run provenance, command/scenario, exit/result и ограничения,
полный raw locator/hash, manifest существенных входов и подтверждение его полноты владельцем.
Provenance неизменяем: HEAD/base, значимый dirty/untracked diff, версии правил/инструментов,
настройки и свойства окружения. Manifest отдельно включает прямые/влияющие транзитивные входы,
контент/ресурсы/манифесты/зависимости и discovery rule + состав набора. Reuse — отдельная запись
сравнения для целевого scope, не переписывание provenance или только сравнение HEAD.

Unknown-ID retrieval: до 5 metadata pages и 5 выбранных bodies, ответ до 2000 UTF-8 bytes;
расширение задаётся для конкретного вопроса с причиной, coverage и continuation. Изменение
snapshot revision инвалидирует старый cursor; чтение продолжается после пересверки. Эти числа
не ограничивают raw evidence и не обрывают обязательную проверку. Local fallback summary до
5000 UTF-8 bytes, а raw command/exit/input/output сохраняются без обрезания рядом с assignment
в разрешённом durable каталоге. Пользователь видит сбой; требуемый missing check остаётся NOT RUN.
Импорт fallback в Store — отдельная идемпотентная операция после восстановления; unknown write
сначала ищется по operation_id, чтобы не создать второй факт.

Восстановление неизменных фрагментов регулирует [ADR-0060](https://github.com/Krivega/agent-workflow/blob/main/docs/design/decisions/inherited/0060-preserve-reviews-after-dependency-restoration.md).
Логическая идентичность материалов роли задаётся корневыми документами; их SHA-256 связывают
транзитивный граф хранения. Проверка актуальности включает все достижимые фрагменты и архивы,
их хеши и разрешённые пути. Повторное явное перечисление этих фрагментов не меняет снимок роли.
Только полный PASS сохраняет исходный ответ и binding; FAIL, NOT RUN, частичное заключение,
изменённые материалы или непроверенный граф не дают reuse. Сохранённое состояние не мигрируется.

## Кандидаты хранения и восстановление

Общие входы, инструменты и архив следуют [ADR-0058](https://github.com/Krivega/agent-workflow/blob/main/docs/design/decisions/inherited/0058-share-workflow-facts-tools-and-archive.md).
Новые check proof/intent и первичные записи совета используют версионный кодек общих фрагментов.
Непустые списки `{locator, hash}` выносятся по SHA-256 даже при малом размере; повторные поля
`before`, `after`, `check.inputs` и поручения используют тот же фрагмент. Пул совета явно
подключается к пулу родительского namespace через `.workflow-pool.json`; разрешён только
непосредственный родитель. Прежний местный пул читается для совместимости.
Советник читает полное поручение через `request_reader` и неизменяемый ref-файл; проверка
исходного SHA, native LOAD/answer/origin и полного состава входов сохраняется.

Файлы, вынесенные из рабочего namespace, имеют обычные короткие указатели `AWLOCATION1` и
явный `.workflow-files.json`. Указатель без зарегистрированного файла остаётся буквальным текстом.
Индекс допускает только свой namespace и договорные соседние каталоги `archives/<root-hash>`
и `tool-cache/<bundle-hash>`. Чтение возвращает исходные байты с проверкой SHA-256; повреждённые
содержимое, индекс, пути и файловые ссылки запрещены. Общий набор инструментов сохраняет
относительную структуру. `resolve-tool` выдаёт проверенный исполняемый путь кэша;
check-команда разрешает инструменты и аргументы кэша, а архивный указатель запрещает исполнять.

`relocate-files` требует manage, revision/owner/generation, неактивного lease, отсутствия
незавершённых Store effects и check-операций. Рабочие Store, управление, connection, request,
managed state и текущие progress-файлы защищены от переноса. Копия проверяется до публикации
индекса и указателя; прерванный перенос повторяется с тем же запросом. Checkpoint не меняется.
`materialize-files` требует manage и спокойного Store, держит эксклюзивную транзакцию и
восстанавливает полный namespace в новый каталог, раскрывая внешние файлы. Store-only backup
по-прежнему копирует только Store; для всей задачи нужен namespace export/materialization.

Минимальное хранение следует [ADR-0057](https://github.com/Krivega/agent-workflow/blob/main/docs/design/decisions/inherited/0057-normalize-workflow-facts-and-events.md).
Сохраняются актуальное состояние, короткие квитанции повторов и необходимые доказательства
приёмки. Execution/ChatMessages записывают ID, SHA-256 и параметры идентичности вместо тела
команды; Council — значимые FAIL, последние необходимые оценки и индекс использованных turns.
Текущие полные ответы с bindings остаются для проверки допуска. Небольшие LOAD/RESUME receipts,
которые разбирает продолжение, остаются частью текущего состояния.

Индекс `review_turns` переносится при пересмотре planning вместе с историей: удаление старого
тела ответа не разрешает принять его native turn повторно, в том числе после смены требований.
Перед первым переводом legacy managed-файла в `AWRETAIN2` его точные байты и замыкание внешних
фрагментов сохраняются в `<file>.originals/<SHA-256>/` и проверяются по manifest. Повреждение,
отсутствующий фрагмент или изменение исходного файла запрещают замену. Повторная штатная запись
`AWRETAIN2` не создаёт ещё одну копию оригинала.
Для распознавания уже нового файла читаются только 10 байт заголовка; обычная запись проверяет
метаданные без чтения содержимого. Ссылки и нештатные файлы по-прежнему запрещены.
Полное чтение требуется только однократной защите legacy.

Диагностика App Server отделена от результатов доставки: `<journal>.diagnostics.json`
содержит не более 128 последних записей и 256 КиБ UTF-8. Это direction, ID, method, размер и hash;
только stderr имеет фрагмент до 512 символов. Полные RPC-ответы, история и тексты поручений
не записываются в диагностику и не переносятся из неё в отдельные большие blobs. Лимит позволяет
сопоставить последние вызовы и ошибки без второго архива нативной истории.
Прежний `<journal>` и его артефакты остаются неизменными.

Потребитель восстановления `rejectedSend` использует отдельную короткую квитанцию на
`{session, delivery}` в `<journal>.deliveries/`: hash запроса, попытки, ответы и наблюдаемый исход.
Текст поручения и полного ответа для этого не нужен. Только единственный однозначный
`-32602/input_too_large` разрешает прежний маршрут восстановления; повтор, коллизия со старым
журналом, потеря ответа или противоречие сохраняют unknown/no-retry. Эти квитанции и первичные
LOAD/origin/answer proofs не являются диагностикой и её лимитом не удаляются.

Краткий CLI-ответ Store-команд сохраняет ID операции, итог и адрес текущего состояния,
без неизменяемой копии всего Store на каждом вызове. `check-chat` ссылается на исходный proof
проверки, включая reuse. `council-chat` сохраняет необходимое текущее состояние для продолжения
без Store. `--full` явно читает полный доступный результат без побочной записи диагностического
снимка. Формат `details` описан в [маршруте текущего чата](../../CURRENT-CHAT.md).

`AWRETAIN1` обозначает минимальный Store checkpoint; `retention_version: 1` запрещает полные
исторические тела. Событие Store содержит хеш checkpoint и квитанцию, без вложенного снимка.
`AWRETAIN2` — переносимый управляемый артефакт с общими фрагментами внутри одного файла.
Неизменяемые текущие факты разделяются в памяти; изменяемые представления независимы.
Повтор сверяет отпечаток и не требует удалённого тела. Pending effects, CAS/owner/generation,
неизвестные исходы и все gates сохраняют прежние ограничения.

Явная операция `retain-store` требует manage, ожидаемых revision/owner/generation и истёкшего
lease либо release. Она проверяет внешнюю резервную копию, заменяет checkpoint, удаляет старые
снимки событий и недостижимые blobs. После включения очистки следующие записи удаляют свои
недостижимые фрагменты. Уже существующий namespace без разрешённой очистки автоматически не
теряет старые blobs. Восстановление старых тел — из проверенной копии при остановленных writers.

Совместимость прежнего архива следует
[ADR-0056](https://github.com/Krivega/agent-workflow/blob/main/docs/design/decisions/inherited/0056-separate-workflow-history-from-current-state.md).

Расследование роста данных установило генерацию
повторных manifests в полных вложенных событиях. Отделение архива этого не устраняет.
Прежний формат остаётся читаемым для перехода и восстановления:
Оболочка `AWARCHIVE1` обозначает компактный индекс Execution и исторических ответов Council.
События сохраняют исходный текст, включая UTF-16, а исторические ответы — исходное полное значение.
Рабочие записи содержат ссылки по хешу, verdict/coverage/findings/evidence, design и answer turn.
Текущие ответы и входы остаются доступны владельцам действующих проверок.

`state` без параметра сохраняет полное чтение; `archive: current` возвращает рабочий индекс,
`archive` по точному хешу читает отдельное значение. Журналы workflow/chat по умолчанию читают
рабочее состояние; `{ archive: true }` явно раскрывает историю. Повтор события читает нужный
оригинал и проверяет прежнее равенство; исторический ответ нельзя повторно принять по тому же turn.
Изменение checkpoint с `archive_version: 1` передаёт новые blobs, компактное состояние и effects.
CAS, владелец, поколение и lease проверяются до публикации. SQLite фиксирует состояние, событие
и квитанцию атомарно; повтор operation_id возвращает прежнюю квитанцию. Новая запись проверяет
новые архивные корни; старые тела проверяются при обращении и полном экспорте.

Большие общие фрагменты используют AWJSON1. Результат CLI переносит недостающие архивные
фрагменты в свой каталог и сохраняет возможность полного чтения после переноса. Backup/finalization
обходят все достижимые архивы, включая зависимости внутри событий. Старые JSON, AWJSON1 и
маркированные gzip-истории читаются без записи. Первый штатный commit владельца переносит
его рабочую историю; это не массовая миграция и не разрешение cleanup.

| Кандидат | Что нужно спроектировать и доказать в AW3 | Цена и критерий отказа |
| --- | --- | --- |
| SQLite через `node:sqlite` + content-addressed blobs, рекомендация AW0b | DatabaseSync/backup, DELETE/EXTRA, конкретные Node/SQLite/OS, transaction/CAS, два процесса, авария commit, публикация blob, согласованный backup/restore | API прочитан в текущем Node; совместимость всего диапазона и durability ещё не проверены. Рецепт и критерии; нельзя сужать поддерживаемые Node без решения |
| Файловый append-only журнал + snapshots | Единственный writer/IPC, process lock, fsync/rename по фактической ОС, checksums, оборванная запись, rebuild heads и compaction журнала | Нет драйвера БД, но больше собственной логики recovery; два параллельных автора без арбитража делают вариант неприемлемым |

Не выбирать JSON «последняя запись побеждает». Для обоих вариантов: canonical root, защита от
path traversal/symlink, несовместимой schema_version и поздней generation; разделение проектов;
согласованный export вне удаляемого namespace и restore в новый каталог с проверкой hash/IDs.
Отдельно SIGKILL до/после commit и до Ack, нехватка места, повреждение blob, повтор операции,
две конкурирующие записи, ручное изменение карточки. Rollback версии только с совместимой схемой
или проверенным restore; не открывать новую схему старым writer. Конкретный адаптер и рецепт
предложены в AW0b и ожидают принятия; фактическое доказательство адаптера — AW3, не эта таблица.

## Координация и relay

Координатор получает цель, scope/dependencies, card writer и полномочия на каждый dispatch.
Два независимых поручения допустимы только при разрешении; общая граница имеет одного executor
интеграции. Дочерние результаты закрывают свои этапы ссылками, изменённые связи проверяются
отдельно и затем общим validate. Наблюдение cursor/events дедуплицируется; ориентир 3–4 минуты
не задерживает доставленное событие и не отменяет короткие вызовы ожидания/обратную связь.

Единственный автоматический trigger relay — подтверждённый compaction executor/orchestrator;
resume не trigger. Состояние включает assignment, active stage/estimate/elapsed, next action,
audit checkpoint, FAIL/dissent/dispositions, gates, pending human decisions, child evidence,
ownership и, у координатора, mapping/dependencies. Без карточки это durable assignment/state.
Сначала сохранение и подтверждённое прекращение записей/release; затем одна попытка fresh
persistent thread/start в точном native project/root по принятому DEC-06-B без fork/history/worktree. Неизвестный исход — recovery по
operation/identity; второй чат вслепую не создаётся. clientThreadId не real threadId.

Преемник загружает свои текущие правила и версию relay, подтверждает identity/workspace/release,
принимает generation и сохраняет adoption. Потом наблюдается ближайшее действие по поручению.
Created, identity, adoption, continuation — четыре разных свидетельства. Старый исполнитель
после release только восстанавливает/координирует. O6 помогает лишь при допустимой технической
недоступности, не обходит отказ разрешения. Сообщения другим чатам требуют отдельной авторизации.
Невозможность получить нужное доказательство оставляет relay открытым; AW2
проверяет транспорт, AW8 — весь механизм инструмента.

## Финализация и архив

Done не запускает finalization. Явное начало 18 → отбор значимых проверок/решений/FAIL/dispositions
и raw источников → внешний durable export → restore → остановка producers → полная сверка
catalog revision/reconciliation → отдельно разрешённый archive → отдельно разрешённый cleanup.
Изменившаяся revision обнуляет готовность архива, но не стирает прежнее доказательство.

Предложение DEC-10-A сохраняет данные бессрочно до отдельного решения. DEC-10-B требует policy
version, оператора, точного grace_deadline и manifest; отсчёт предложенных 30 суток начинается
после подтверждённого archive receipt. Significant evidence и receipts живут вне namespace
бессрочно до отдельного решения. Cleanup не удаляет последнюю копию и не равен удалению чата.
При сбое/unknown сначала сверить receipt и состояние. Разрешённый одноразовый тест удаления
не является разрешением удалять реальные данные; после отключения инструмента архив читаем.
