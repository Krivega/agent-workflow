# Temporal SDK

Руководство по подключению проекта, запуску ролей, управлению задачей и восстановлению.
Текущие ограничения допуска — в [разделе качества](https://github.com/Krivega/agent-workflow/blob/main/docs/quality/README.md).

## Подключение проекта

`ProjectDescriptor` версии 1 задаёт логические project/workspace IDs, относительные пути правил,
корень карточек, роли с профилями и IDs проверок. Неизвестная версия, дополнительные поля,
повторы и выход пути из корня отвергаются. Descriptor не содержит shell-команд, секретов или
абсолютных путей. Примеры — `examples/neutral/project.json` и адаптер самого инструмента `project/temporal.json`.

Worker получает доверенную локальную регистрацию: тот же descriptor, host/owner/generation,
корни рабочей копии и артефактов, реестр executable/args. Совпадение имени очереди не заменяет
проверку регистрации. PreparationWorkflow проверяет наличие входов и регистрации команд;
команды проверок пока не исполняются. Несовпадение проекта, владельца, поколения или входов
останавливает маршрут до зависимого модельного действия.

Все команды SDK ниже выполняются из корня после `yarn build`.

После сборки клиент подготовки получает `PreparationInput`, адрес, очередь и JSON доверенной
регистрации (`project`, `workspaceRoot`, `hostId`, `owner`, `generation`):

```sh
yarn prepare-project INPUT.json localhost:7233 PROJECT_QUEUE REGISTRATION.json
```

Запуск Worker выполняет локальный хост через экспорт `./worker`; функция получает соединение,
очередь, путь неизменяемой сборки Workflow и регистрацию проекта. Этот клиент не включает
новые рабочие задачи и не подключает старые Store к Temporal.

SDK starts и control требуют предварительного `bindTaskBackendClient(client, registration)`
из `./task-backend`. Один Client поддерживает несколько project/workspace; повтор той же
регистрации допустим, смена root/owner/generation требует нового Client. Привязка не запускает
сервер и не выдаёт полномочия. Для рабочего T6 конфигурация Client и Worker сохраняет
`taskBackend: 'required'`: потеря деклараций или реестра после рестарта запрещает продолжение.
Изолированные qualification fixtures имеют собственный Git root и не включают рабочую политику.

## Локальная служба Worker на macOS

Установите версию пакета с комплектом T7 в стабильном каталоге хоста. Создайте каталог
для настроек, журналов и состояния с правами `700`. В нём сохраните `worker.json`
с правами `600` из [шаблона Worker](../examples/temporal-host/worker.example.json).
Укажите свои `codexHome`, путь регистрации и ID чата. Шаблон воспроизводит профиль
T7 на Mac, включая отключённые MCP-серверы стенда. Сверьте их список с настройками
выбранного Codex CLI. Начальный лимит ходов равен нулю. Использованные ходы хранятся
в состоянии хоста и сохраняются при перезапуске.

Перед выбором профиля выполните команды в каталоге хоста. Они читают путь и
`codexHome` из тех же настроек, что и LaunchAgent. Для вывода каталога нужен `jq`.

```sh
AW_CODEX=$(jq -er '.codexBinary' worker.json)
AW_CODEX_HOME=$(jq -er '.codexHome' worker.json)
"$AW_CODEX" --version
CODEX_HOME="$AW_CODEX_HOME" "$AW_CODEX" debug models |
  jq -r '.models[] | [.slug, ([.supported_reasoning_levels[].effort] | join(", "))] | @tsv'
```

На Mac со стендом T7 запрос `model/list` к CLI `0.171.0-alpha.13` подтвердил следующие
профили 22 ноября 2026 года. Worker проверяет выбранную пару при создании сеанса.

| Модель | Уровни рассуждения |
| --- | --- |
| `gpt-6.2-astra`, `gpt-6.2-sol`, `gpt-6.1-terra` | `low`, `medium`, `high`, `xhigh`, `max`, `ultra` |
| `gpt-6-luna` | `low`, `medium`, `high`, `xhigh`, `max` |

Для каждого проекта `file` — тот же приватный файл с правами `600`, который получает
`task-chat start --temporal-registration`. Его поля — `schemaVersion: 1`, `address`,
`namespace`, `taskQueue` и `registration`. Внутри `registration` укажите дескриптор
`project`, `hostId`, `owner`, `generation`, абсолютные `workspaceRoot` и `artifactRoot`,
словарь `commands` и `taskBackend: "required"`. Значение `threadId` связывает проверку
полномочий с выдавшим поручение чатом этого проекта. У проектов одной службы общие
адрес, namespace, очередь, хост и владелец. Для второго репозитория добавьте его файл
и ID в `projects`, проверьте настройки и перезапустите службу.

Выполняйте команды из каталога установки пакета под пользователем, которому принадлежат
рабочие копии и журналы Codex. Для реального запуска у проектов должна быть настроена
политика Temporal, а сервер должен отвечать. Команды `--check` и `--plist` работают офлайн.
Команда `--check-writer` запускает Codex через настроенный `codexBinary` во временном
каталоге внутри `artifactRoot/copies` каждого проекта. Она проверяет состояние входа
через `account/read` и полный реестр MCP по правилам Writer. Модельные ходы при этом
не расходуются. При ошибке входа выполните `codex login` для фактического `CODEX_HOME`
исполнителя. Состояние входа подтверждает наличие учётных данных. Доступ к модели
проверяется при обращении к провайдеру. Режим `--run` выполняет ту же проверку
до подключения к Temporal.

```sh
AW_HOST=/absolute/private/host
AW_WORKER="$PWD/node_modules/@krivega/agent-workflow/examples/temporal-host/worker.mjs"
AW_PLIST="$HOME/Library/LaunchAgents/com.krivega.agent-workflow.worker.plist"
node "$AW_WORKER" --check "$AW_HOST"
node "$AW_WORKER" --check-writer "$AW_HOST"
mkdir -p "$HOME/Library/LaunchAgents"
node "$AW_WORKER" --plist "$AW_HOST" > "$AW_HOST/worker.plist" &&
  plutil -lint "$AW_HOST/worker.plist" && install -m 600 "$AW_HOST/worker.plist" "$AW_PLIST"
launchctl bootstrap "gui/$(id -u)" "$AW_PLIST"
launchctl print "gui/$(id -u)/com.krivega.agent-workflow.worker"
```

Проверьте обе очереди командой `temporal task-queue describe --address 127.0.0.1:7233
--namespace NAMESPACE --task-queue QUEUE`: подставьте сначала основную очередь, затем
её имя с суффиксом `.control` и проверьте наличие Activity poller у каждой.
Журналы находятся в `worker.stdout.log`, `worker.stderr.log` и каталоге `rpc` хоста.
LaunchAgent запускается при входе пользователя и повторяет запуск при аварийном выходе.
Для остановки выполните `launchctl bootout "gui/$(id -u)" "$AW_PLIST"`.

Для существующего LaunchAgent TNAS в репозитории есть команда обновления на месте.
Запускайте её в Terminal на Mac из корня agent-workflow. Укажите путь к архиву и его
ранее проверенный SHA-256. Первый вызов показывает различия. Второй выполняйте в окно,
когда подача новых задач и локальных пишущих работ приостановлена. Для второго вызова
укажите в `RECEIPT` квитанцию завершённого запуска на целевом хосте, а в `ARTIFACTS` —
каталог артефактов того же запуска.

```sh
yarn worker:update "$ARCHIVE" "$SHA256"
yarn worker:update "$ARCHIVE" "$SHA256" --apply --receipt "$RECEIPT" --artifacts "$ARTIFACTS"
```

Команда берёт пути Node, пакета и хоста из установленного plist, проверяет Writer,
состояние Temporal и процессы. Сохраняет существующие зависимости при совпадающем
lock-файле и декларациях зависимостей. После замены сверяет пакет, прежние записи
state, регистрации, три типа обработчиков двух очередей и результат контрольного запуска по Run ID.
При совпадающем пакете `--apply` проверяет службу без перезапуска.
Параметры хоста, lock-файла, контрольной квитанции и каталога артефактов доступны
через `yarn worker:update --help`. Требуются macOS, Python 3.12+ и действующий
SSH-туннель TNAS. При сбое после остановки сначала сверьте состояние службы и
полноту установки с архивом. Для штатного запуска исправленной установки используйте
приведённые выше команды проверки и bootstrap. Резервная копия пакета не создаётся.

Изменения Worker сначала вносите в репозиторий. Соберите проект командой `yarn build`,
создайте архив через `npm pack` и сохраните его SHA-256. Распакуйте архив в отдельный
каталог, скопируйте в него `yarn.lock` той же рабочей копии рядом с `package.json`,
установите зависимости через `yarn install --production --frozen-lockfile --ignore-scripts`
и выполните `--check` из этой
копии с действующими настройками хоста. Для обновления используйте проверенную копию.
Перед переключением
дождитесь завершения задач и остановите службу. Сохраните `state`, артефакты и регистрации,
обновите пакет, повторите проверку и загрузку plist. Сохранившийся после аварии
`host-owner` требует штатной процедуры восстановления.

### Соединение Mac с сервером на TNAS

Если Compose работает на TNAS, порт 7233 слушает loopback самого TNAS.
На Mac установите SSH-туннель до проверки доступности Temporal. Скопируйте
[шаблон LaunchAgent](../examples/temporal-host/tnas-tunnel.example.plist) из выбранного
пакета в приватный каталог хоста под именем `tunnel.plist`. В копии замените
`user@nas.example`, порт SSH (на стенде `9222`) и абсолютный путь к журналу.
Заранее проверьте ключ хоста и вход по SSH без запроса пароля под пользователем службы.

```sh
AW_TUNNEL="$HOME/Library/LaunchAgents/com.krivega.agent-workflow.tnas-tunnel.plist"
mkdir -p "$HOME/Library/LaunchAgents"
plutil -lint "$AW_HOST/tunnel.plist" &&
  install -m 600 "$AW_HOST/tunnel.plist" "$AW_TUNNEL" &&
  launchctl bootstrap "gui/$(id -u)" "$AW_TUNNEL"
launchctl print "gui/$(id -u)/com.krivega.agent-workflow.tnas-tunnel"
temporal operator cluster health --address 127.0.0.1:7233
```

Туннель связывает `127.0.0.1:7233` на Mac с тем же адресом на TNAS.
Для обновления остановите Worker, затем выполните
`launchctl bootout "gui/$(id -u)" "$AW_TUNNEL"`, установите обновлённый шаблон
с параметрами хоста и повторите запуск туннеля и Worker.

При прямом вызове SDK последний аргумент `createReaderHost` задаёт namespace после
необязательного `resumeWritten`. Прежние вызовы без namespace используют `default`.

## Договоры и данные

- `PreparationInput` версии 1: taskId, descriptor, hostId, owner, generation, revision и путь карточки.
  Revision/generation — положительные безопасные целые. Карточка находится внутри cardRoot.
- Workflow ID подготовки кодирует пару projectId/taskId без коллизий. Повтор активного старта
  использует существующий Workflow и сверяет его вход; другой вход конфликтует. Повтор закрытого
  старта запрещён.
- Manifest подготовки закрепляет hashes входов. Temporal хранит короткие ссылки `{sha256, bytes}`,
  полные тела лежат отдельно. Чтение проверяет hash и длину; публикация не перезаписывает
  прежние байты. Символические ссылки и выходы путей отвергаются.
- Минимальный журнал эффектов хранит неизменяемый intent и ссылку на квитанцию. В нём нет стадий,
  решений совета, таймеров или расписания. Другой запрос с прежним ID конфликтует; intent без
  подтверждённого результата остаётся unknown и запрещает повтор эффекта, включая перезапуск.
  Для отправки допускается первичная сверка: ровно одно полное совпадение служебного ID и текста
  в пользовательском сообщении того же сеанса возвращает прежний turn ID. Ноль или несколько
  совпадений не разрешают новую отправку. Сверка и исходное завершение могут сохранить одну
  квитанцию одновременно; разные исходы дают конфликт без перезаписи.

## Читающая роль Codex

ReaderWorkflow вызывает четыре Activities: подготовка, создание сеанса, LOAD, ответ.
Activities получают узкий RPC-порт Codex от доверенного локального хоста; они не вызывают
прежние application-сценарии. Стенд этого репозитория пока использует существующий stdio
транспорт как внешний порт. Собственный переносимый запуск транспорта остаётся частью T2/T7.

Для задач поддерживаются CLI `0.154.0`, `0.169.1` и `0.171.0-alpha.13`.
Читающие роли также поддерживают `0.165.0-alpha.1.2`. На этой версии проверены
gpt-6.1-sol/medium, два независимых сеанса, четыре хода, полный адресный LOAD/ответ,
неизменный reuse и четыре replay. Сам аудит требует отдельно подтверждённых native auditor и gpt-6.2-sol/xhigh.
Перед созданием сеанса проверяются модель
и effort из первичного `model/list`; имя из ответа `thread/start` само по себе недостаточно.
Также проверяются эффективные cwd/model/effort, отсутствие fork/parent, режим только чтения,
отключённая сеть и запрет запросов разрешений. Недоступная модель не получает fallback.

Свежий сеанс до первого хода ещё не имеет rollout на диске. Первый LOAD допускается только
в создавшем его соединении после `thread/loaded/list`. После потери этого соединения новый
сеанс вместо него не создаётся. Для существующего rollout проверяются identity и отсутствие
незавершённых прежних ходов. Ответ привязан к исходной роли, подготовке, сеансу и LOAD.

LOAD подтверждается полными байтами из первичных успешных команд, включая части большого
источника. Общая чистая проверка частей сохраняет предел 8000 единиц UTF-16 и бюджет вывода
24000 байт UTF-8; её использует и прежний runtime. Само подтверждение модели не является LOAD.
Первичное наблюдение незавершённого/неуспешного хода сохраняется до отказа; ошибка содержит hash.

Инструкции LOAD сохраняют точные версии. Исторические v1/v2 не меняются;
отсутствие `promptVersion` означает v1. Writer и аудит сохраняют default v2.
Новые Reader Activity явно используют v3: отдельный прямой последовательный вызов
`exec_command` с буквальной JSON-строкой команды и неизменённым структурированным
результатом. Динамические eval/store и повторное представление результата голым текстом
не дают проверяемой связи вызова и возврата. Формат частей и оба предела сохраняются.

Когда RPC CommandExecution не содержит stdout, v3 может использовать только отдельное
первичное доказательство того же нативного сеанса CLI `0.154.0` и хода:
закреплённый неизменяемый
префикс журнала, единственный поддержанный прямой вызов, точную пару `call_id`,
однозначную команду и terminal return. Исходный RPC-снимок не изменяется и не выдаётся
за восстановленный вывод. Квитанция `commandOutputs` хранится отдельно и повторно
проверяется при ответе и историческом чтении. Неподдержанные, неоднозначные, чужие,
незавершённые и неуспешные возвраты отклоняются; старые v1/v2 этим путём не исправляются.
Неизвестная версия или понижение нового первичного сообщения до v1 отвергается.

Адресные и полные локальные проверки v3 не переносят прежнюю native-квалификацию
на новый runtime: она сохраняет свои профили и pins. Новый живой маршрут проверяется
отдельно под собственным допуском и бюджетом. В автономном H06 подтверждённый отказ
Reader текущей подготовки сохраняется как диагностическая квитанция и завершает стенд;
производственное ожидание явной сверки и ручной `/2` не меняются.

Живой стенд `node --import tsx tests/temporal/native-reader.mjs MODEL` требует отдельного разрешённого профиля
и бюджета. Он создаёт только читающую роль в отдельном временном проекте и делает два хода
(LOAD и экспертиза), сохраняет первичные квитанции, usage и историю, проверяет replay и
останавливает сервис. Его успех доказывает только обычный читающий маршрут.

`node --import tsx tests/temporal/native-recovery.mjs EVIDENCE_DIRECTORY` проверяет завершённый читающий сеанс
из собственного успешного прогона: в отдельных копиях квитанций моделируется потеря ответа
отправки и completion, неизвестное создание сохраняется без нового сеанса. Одноразовая рабочая
копия восстанавливается из уже подтверждённого LOAD только для этого теста; существующий
каталог не заменяется. Новый stdio транспорт читает прежние session/turn IDs, запуск любых
сеансов или ходов в этом стенде запрещён. Копия закрытой тестовой БД запускается повторно;
результат и replay должны совпасть. Исходные доказательства сохраняются. Это не общий backup/restore
и не восстановление незавершённой работы.

## Управляемая читающая роль

`ControlledReaderWorkflow` — отдельная версия маршрута; прежний ReaderWorkflow сохраняет
последовательность записанных команд. Экспорты `./reader` и `./reader-host` предоставляют клиент
и хост. Повтор старта сверяет нормализованный неизменяемый вход; закрытый ID не используется снова.

Update `readerControl` принимает команды версии 1: pause/resume/cancel, ID и SHA-256 полного
запроса, точный target (workflow/project/task/role/host/workspace/owner/generation/revision),
ожидаемая редакция управления, автор, номер попытки и ссылка на первичный источник полномочий.
Повтор возвращает ту же квитанцию; иной запрос с тем же ID и устаревшая редакция отвергаются.
Signal `readerReconcile` только будит первичную сверку. Query `readerStatus` показывает стадию,
редакцию и ошибку. Технический процесс хранится в Temporal.

Внутренняя запись полномочий версии 2 содержит список hashes отправок. Он публикуется
до запроса Codex; потеря, добавление или подмена intent запрещают следующий внешний запуск
и подтверждение остановки. Заморозить полномочия можно и при потере intent. Восстановление
точных исходных записей допускает первичную сверку без повторного create/send. Потеря самого
permission.json при сохранившихся записях не разрешает повторную выдачу полномочий; новый permit
после полной потери каталога не подходит ранее запущенному Workflow. Старый формат версии 1
отвергается: для прежних запусков нужна совместимая закреплённая сборка, автоматической миграции нет.

Хост обязан передать `ReaderAuthority.verify`: проверить подлинность первичного источника
и вернуть закреплённое доказательство. Разрешающей всё реализации по умолчанию нет.
RESUME требует origin `human`; исходное разрешение `initial-grant` допускает только pause/cancel.
Автор команды сам по себе не подтверждает полномочия. Тестовый источник SDK-стенда не разрешает
работу с настоящей задачей.

Один хост обслуживает все зарегистрированные проекты одним Worker с одним модельным слотом
и отдельным Worker с одним слотом управления. Эксклюзивный файл владельца не имеет автоматического
перехвата после тайм-аута. Общий неизменяемый предел `turn/start` проверяется до отправки;
повтор известной операции не тратит новый кредит, увеличение сохранённого предела запрещено.
Этот фиксированный профиль не включает фоновую работу.

Пауза/отмена сначала отзывают внешнее разрешение и отменяют ожидающую Activity, затем отдельно
проверяют native-остановку. Отмена Activity не считается остановкой модели. `turn/interrupt`
применяется к активным ходам исходного сеанса, затем проверяются первичные терминальные состояния.
Unknown create/send, неполная история или ошибка остановки оставляют `blocked`.
Статусы `paused`/`cancelled` появляются только с квитанцией остановки. Поздний результат
не применяется после смены редакции управления. Завершение хоста закрывает выдачу разрешений,
дожидается незавершённых выдач и останавливает все допущенные сеансы; unknown сохраняет владельца.

Внешний журнал содержит привязку/отзыв разрешений, запросы отправки и доказательства остановки;
стадий workflow и расписания там нет. Проверяются inode/dev рабочей копии и исходный hash
карточки. Подмена или смена цели запрещают новое действие; остановка доступна и после удаления
копии. Продолжение прерванного LOAD может явно увеличить номер попытки на один с прежней identity;
автоматического нового модельного хода нет.

`yarn test:control` запускает настоящий временный Temporal с имитацией
native Codex и человеческого источника: два проекта, занятый модельный слот, управление,
повтор/конфликт/устаревшая команда и replay. Модельных ходов нет.
`node --import tsx tests/temporal/native-cancel.mjs MODEL` требует разрешённых модели и бюджета; запускает
ровно один читающий ход и проверяет активную отмену по исходному допуску. Стенд сохраняет
первичные истории и останавливает сервис; он не подтверждает RESUME из другого чата.

### Native-источник человеческой команды

Экспорт `./reader-authority` предоставляет `nativeReaderAuthority` для доверенного выдающего
чата владельца: его threadId, workspaceRoot, owner и sessionsRoot задаёт хост. Это отдельная
регистрация выдающего чата; workspace читающей роли может находиться в другой копии.
`command.source` ссылается на неизменяемый JSON `NativeReaderSource` версии 1 с kind
`codex-user-command`, абсолютным transcript, threadId/turnId и номером/hash строки пользователя.

Проверяется исходный файл внутри доверенного sessionsRoot без символьных ссылок, целый UTF-8
с завершёнными строками, единственная native identity и cwd выдающего чата. Поддержан наблюдённый
формат источника Codex App `0.164.0-alpha.11.1`; это не версия CLI читающей роли `0.154.0`.
Незнакомый формат отвергается. Источник обязан быть пользовательским `input_text` в указанном
ходе; служебные обёртки, инструкции окружения и тексты агента не подходят.

Выдающий агент в пределах поручения строит команду обычным `makeReaderCommand`, вызывает
`authority.issue(command)` в исходном чате и выводит возвращённую строку без преобразования.
Только после завершения этой отдельной native-команды можно доставить ReaderCommand получателю.
Проверяющий модуль ищет точную строку ID/hash/source в успешном `CommandExecution` после исходного
сообщения, в том же чате/ходе/cwd. Между сообщением и выдачей не должно быть нового человеческого
поручения. Обычный вывод агента или ещё не завершившаяся выдача не заменяют native-квитанцию.
Hash связывает весь payload, target, редакции, попытку и источник. Действительная уже выданная
команда переживает последующий ход источника; повтор получателя использует прежнюю квитанцию.

Доказательство содержит выбранные первичные строки пользователя/выдачи, проверенные метаданные
и hash наблюдённого transcript. Полная история исходного чата в artifacts не копируется.
Получатель дополнительно выполняет свои проверки target/редакции/owner/generation и остановки;
этот модуль не выдаёт права смены scope или публикации.

`node --import tsx tests/temporal/native-resume.mjs MODEL GRANT_FILE` — отдельный квалификационный стенд с
настоящим источником. GRANT_FILE содержит разрешённый исходный контекст (`issuer`, `source`)
и границы текущего допуска (`previousStarts: 4`, `maxAdditionalStarts: 2`). Эти значения относятся
к данному ограниченному прогону; новый запуск требует собственного согласованного бюджета.
Стенд прерывает первый LOAD, сохраняет `paused-state.json` и ждёт команду из исходного чата.
Выдающий чат создаёт source artifact в указанном artifactRoot, строит RESUME с target/revision
из paused-state и attempt 1, сохраняет его artifact и отдельно печатает `issue(command)`.
После native-подтверждения выдачи ссылка на command artifact атомарно публикуется в
`resume-delivery.json`. Стенд проверяет человеческое происхождение, повтор доставки, второй LOAD
в прежней identity, отмену, первичные `interrupted` и replay. Максимум два новых `turn/start`;
при тайм-ауте или отказе стенд закрывается с безопасной остановкой и сохранением FAIL.
Это проверка RESUME при прерванном LOAD, не полный читающий результат или промышленный restore.

### Адресные пакеты и повторное использование заключений

При отказе одного дочернего Workflow родитель отменяет остальных и ждёт подтверждённого
завершения каждого перед возвратом ошибки. Parent Close Policy сама по себе этого ожидания
не заменяет. SDK-стенд задерживает физическую остановку имитированного хода и проверяет,
что родитель остаётся активным до её подтверждения.

Корневая команда `node tests/temporal/review.mjs --bounded` проверяет двух читающих
советников и неизменный reuse без моделей. После отдельного разрешения
`node --import tsx tests/temporal/review.mjs --native MODEL` использует настоящий Codex: максимум четыре
новых старта ходов, medium, до 45 минут, временный проект только для чтения и localhost.
Первичные доказательства, usage и истории сохраняются, сервисы останавливаются.
Это начальный native-допуск адресных пакетов; исправления, B1 и RESULT/DONE в него не входят.

Новый `ReviewWorkflow` сначала вызывает подготовку всего пакета, затем запускает только
нужные ControlledReaderWorkflow. Его клиент экспортирован как `./review`. Вход версии 1 содержит
preparation, reviewId и ссылку request на неизменяемый ReviewRequest: фазу planning/acceptance,
scope, sharedPaths и выбор для каждой объявленной проектом роли. Выбор содержит applies
(true/false/null), предметное reason, paths, полноту/автора/правило обнаружения зависимостей
и полную упорядоченную историю answer refs. Количество ролей/файлов произвольно не ограничивается.

Каждая новая читающая роль получает ReaderInput версии 2 с отдельным reviewId и review artifact.
LOAD включает общие правила, свою карточку/профиль, sharedPaths и только её предметные файлы.
История Temporal хранит ссылки; тела пакетов находятся в artifacts. Прежний ReaderInput и IDs
внешних операций сохраняются. Новые IDs зависят от логической проверки, роли, snapshot и явной
попытки, не от SDK retry/runId. Разрешение связано с полным новым входом.

Все необходимые файлы и зарегистрированные проверки проверяются до первичной сверки истории
и создания дочерних работ. Unknown applicability блокирует пакет. Каждая строка решения
содержит action и причины: not-applicable, review, reuse или blocked. Изменение общего файла
открывает все зависящие роли; локальное изменение — роли, чьи предметные inputs изменились.
Неизвестные полнота, история или discovery rule не разрешают reuse.

Для версии 2 первичный ответ имеет проверяемую JSON-форму ReviewReport: role/phase/scope/review,
verdict PASS/FAIL/NOT RUN, coverage complete/partial, findings и limitations. PASS с blocking
findings отвергается. Перед сохранением LOAD/ответа снова сверяются текущие байты. Старый
неструктурированный Reader answer не становится принятым заключением автоматически.

Reuse требует полного PASS, той же обязанности, требований, фазы/scope, профиля модели и
файлов. Проверяется вся объявленная история: source binding, подготовка, исходная независимая
identity, native LOAD/полный текст отправки, первичный завершённый ответ и непротиворечивый
report. История перечитывается через thread/read; новый сеанс/ход для сверки не создаётся.
Busy, недоступная/неоднозначная первичная история и повреждённый граф останавливают подготовку.
Новый пакет не может удалить предшественников, уже закреплённых в snapshot заключения.
Последний FAIL требует новой проверки даже при applies=false; лишь новый полный PASS закрывает
его применимость, исходный FAIL остаётся в истории.

Полнота предметных зависимостей и истории — явное утверждение владельца карты, а не свойство
SHA-256. Модуль не доказывает семантическую полноту списка по одним хешам и не обнаруживает
заведомо не переданное последующее заключение. В рабочем TaskWorkflow эту карту и актуальную
историю должен подавать её владелец; общий gateway и его допуск остаются частью T3–T6.

Перед возвратом результата `finishReview` проверяет точный пакет, независимость сеансов ролей,
первичные ответы и актуальность файлов ещё раз. Неуспешная/неполная/отменённая роль не даёт
complete=true. Это полнота данного набора ролей, не RESULT/DONE или общая приёмка задачи.
Дочерние workflows используют REQUEST_CANCEL и WAIT_CANCELLATION_COMPLETED; отмена родителя
не подменяет подтверждение остановки сеанса. Родитель не хранит второй технический checkpoint.

`yarn test:review` запускает временный настоящий Temporal с имитацией Codex:
два адресных пакета, неизменный reuse без новых ходов, локальная и общая правки, отсутствующий
вход, неизвестная применимость, отмена родителя/ребёнка и replay родительских/дочерних историй.
Реальных модельных ходов нет. Native-квалификация этого нового пакета требует отдельного бюджета.

## Подготовка локального плана B1

Экспорт `./local-admission` предоставляет `startLocalAdmission(client, input, taskQueue)`.
`LocalAdmissionInput` версии 1 содержит preparation, путь/hash сохранённого локального плана
и artifact ref карты будущей acceptance. Для сборки Worker используется
`dist/workflows/localAdmission.js`, экспортирующая также PreparationWorkflow; существующий
`createPreparationWorker` регистрирует обе операции подготовки.

При подготовке B1 проверяются восемь отрицательных рисков, полная
карта потребителей, точные bytes/hash requirement/basis/owner/consumers, обязательные
зарегистрированные команды и полная применимость независимой acceptance. План не разрешает
изменение собственной основы, правил, профилей ролей или карточки. Неполные/чужие/изменённые
входы отвергаются до зависимых действий. Результат `admitted` ссылается на immutable manifest;
проект, модели и команды проверок эта операция не запускает и не меняет.

`admitted` — только подготовка; полный путь описан ниже. Старые задачи/Store этой подготовкой
не мигрируются.

## Исполнение и независимое завершение B1

Экспорт `./local-task` предоставляет `startLocalTask(client, input, taskQueue)`.
Вход версии 1: `admission` из предыдущего раздела, `executor: { path, sha256 }` и ID
зарегистрированной исходной проверки `baseline`. Стабильный ID — `aw/task/PROJECT/TASK`;
повтор присоединяется только к тому же входу. Сборка Worker — `dist/workflows/localTask.js`.
`createReaderHost` принимает `localTasks: { profile, createRuntime, disabledServers }` у проекта.
Фабрика обязана создавать отдельный stdio runtime с известным PID, а все перечисленные MCP
должны быть фактически отключены. Модель, reasoning и CLI закрепляются до эффектов.

LocalTaskWorkflow выполняет подготовку, исходную проверку, writer, проверки копии, интеграцию,
проверки результата и независимый ReviewWorkflow. Все дорогие действия используют общее
место Activity; остановка имеет отдельный контрольный Worker. Query `localTaskStatus`
показывает этап, исходную ошибку и отдельную причину неопределённой остановки. Отмена запрещает
новые эффекты; Signal `localTaskReconcile` повторяет первичную сверку неопределённого stop.

Writer читает только объявленные материалы в отдельной копии без Git, зависимостей и секретов.
Перед реализацией проверяются primary thread, фактический native профиль записи только в копию,
отсутствие сети/MCP/помощников и полный LOAD по байтам/hash. Ответ остаётся кандидатом.
Хост прекращает весь принадлежащий runtime и его процессы, проверяет исчезновение и стабильность
копии. Команды запускаются по закреплённым executable/args/hash/timeout без подстановки shell;
сохраняются полные журналы, время, exit/signal и process stop proof. Повтор подтверждённой команды
возвращает квитанцию; потерянный исход не запускается повторно догадкой.

Интеграция закрепляет точный diff и сверяет исходные/конечные bytes и modes перед каждой
атомарной заменой. Повтор принимает уже перенесённые файлы, чужая третья версия запрещает запись.
Частичная отмена сохраняет резервирование. Первый B1 поддерживает обычные одиночные файлы,
добавление/удаление внутри существующих каталогов и modes файлов; изменение дерева каталогов,
symlink/hardlink и смена владельца после падения закрыты до отдельной квалификации T4.

ReviewRequest версии 2 добавляет immutable `evidence` и полный `expectedFiles` с bytes/hash.
Каждая роль читает свой пакет вместе с фактическим diff, журналами и доказательствами stop;
подмена входа и изменение evidence запрещают прежний reuse. Все применимые роли должны
независимо пройти приёмку. Перед RESULT повторно сверяются первичные ответы, сеансы и файлы.
Проекция карточки восстанавливается по закреплённому intent без второго DONE и без перезаписи
чужого текста; archive/cleanup не задерживают результат. Восстановление читающего host прямо
отвергает writer-enabled host, даже если список читающих допусков пуст.

`yarn test:local-task` проверяет нейтральный проект с настоящими Git, командами,
процессами, Temporal и replay, имитируя только Codex. `node --import tsx tests/temporal/b1.mjs --native MODEL` требует отдельного
конкретного бюджета: три хода writer (профиль/LOAD/реализация), два хода независимой роли.
Стенд сохраняет первичные artifacts, usage, измерения Activities/очереди/модели, объём данных
и состав исходников; сервисы останавливаются. Это не переключает рабочие задачи и не закрывает
остальные маршруты T3–T7.

### Подготовка Input12 для `task-chat start`

В текущем чате Codex подготовь `preparation`, закреплённый `plan` и отдельные строгие
запросы совета `planningRequest` и `acceptanceRequest` по дескриптору проекта. `registration`
должна совпадать с регистрацией Worker. `source` указывает на первичное поручение пользователя
в приватном журнале Codex (`transcript`, `turnId`, `user: { line, sha256 }`). Подготовка выполняется
из зарегистрированной рабочей копии с действующим `CODEX_THREAD_ID`. Для Desktop
`0.171.0-alpha.13` проверяются корневой ход, прямой ввод владельца и квитанция доставки.
Исходный журнал должен принадлежать текущему пользователю и быть доступен только ему
(обычно `0600`).

```js
import { prepareTaskStartAdmission } from '@krivega/agent-workflow/task-backend';
import { artifactStore, nativeTaskSource } from '@krivega/agent-workflow/task-execution';

const store = artifactStore(registration.artifactRoot, { existingOnly: true });
const observer = nativeTaskSource(store, {
  sessionsRoot,
  chatWorkspace: registration.workspaceRoot,
  threadId,
  owner: registration.owner,
});
const authority = { issue: () => observer.issue(source), verify: observer.verify };
const { ref: startAdmission } = await prepareTaskStartAdmission(registration, authority, {
  preparation,
  previous: null,
  human,
  inapplicable,
});
const publish = (request) => store.publish(Buffer.from(JSON.stringify(request)));
const input = {
  schemaVersion: 12,
  admission: {
    schemaVersion: 3,
    preparation,
    plan,
    planning: publish(planningRequest),
    acceptance: publish(acceptanceRequest),
  },
  executor,
  baseline,
  continuation: { attempt: 0, previous: null },
  startAdmission,
};
```

В `human` передаются точные тексты человеческих критериев карточки. `inapplicable` содержит
пары `{ criterion, reason }` для неприменимых критериев. `executor` содержит `{ path, sha256 }`,
`baseline` задаёт ID зарегистрированной исходной проверки. Подготовка пишет адресуемые артефакты.
Сериализованный `input` передаётся в [`task-chat preview` и `task-chat start`](../CURRENT-CHAT.md#запуск-через-temporal).
Для каждого критерия можно указать явные назначения в необязательном массиве
`criterion_checks` плана версии 2. Поле `criterion` содержит ID или полный текст критерия.
Для `baseline`, `candidate` и `integrated` указывают ID команды, а для `acceptance` —
`roleId` применимой роли и предмет проверки `subject`. Поля `evidence` и
`success` описывают ожидаемое доказательство и признак успеха.

```json
{
  "criterion_checks": [
    {
      "criterion": "K1",
      "stage": "candidate",
      "command": "validate",
      "evidence": "Журнал validate",
      "success": "Код выхода 0"
    }
  ]
}
```

В `createReaderHost` действующая конфигурация `localTasks` включает `startAdmissionAuthority`
для проверки начального допуска и `humanAuthority` для человеческого этапа. Экспорт
`nativeTaskHumanAuthority` принимает функцию проверки начала. `checkTaskStartAdmission` из
`./task-backend` позволяет собрать эту функцию с проверяющим методом `observer.verify`, ссылкой
из Input12, его `preparation` и закреплённым назначением задачи. После проекции карточки функция
проверяет сохранённые байты с параметром `{ card: 'retained' }`.

## Точное применение принятого материала M1

Тот же `./local-task` принимает вход версии 2: `baseline` и `admission` версии 2 с
`preparation`, `plan: { path, sha256 }`, `accepted` и `acceptance`. `plan` указывает на JSON
`mechanical-material` версии 1; `accepted` — hash/bytes полного результата ранее завершённого
planning ReviewWorkflow. `executor` отсутствует. Материал содержит `materialId`, requirement,
полные `links`, `linksComplete: true`, `semanticDelta: false`, обязательные `checks`, criterion
и непустой `files`: каждый путь задаёт точную исходную версию `{ content: { sha256, bytes }, mode }`
либо null и принятую конечную `{ source: { locator, hash }, mode }` либо null.

Хост повторно проверяет первичные planning-ответы, тот же project/task/revision и scope материала,
чтение manifest, исходных/принятых файлов и ссылок. Один `complete: true` не даёт допуска.
Перед копированием повторно сверяются все входы, правила, профили и modes исходных файлов.
Изменение собственной основы, профилей, правил и карточки запрещено. Неизвестные поля,
семантическая delta, неполные ссылки и несовпавший planning отвергаются до зависимых действий.

В стадии `applying-material` хост переносит точные принятые байты и modes в изолированную копию;
модель/процессы writer не создаются. Между файлами отмена может отозвать право следующей записи.
Квитанция `task-mechanical-stopped` не изображает native-сеанс: session null, processes пуст.
Затем работают прежние реальные команды, интеграция, отдельная acceptance и RESULT/DONE.
Ограничения файлов и восстановления те же, что у B1. M1 не принимает новый замысел или
произвольное преобразование; такой материал требует другого planning-маршрута.

`yarn test:mechanical-task` проверяет весь путь на реальных Temporal/FS/командах без модели;
`node --import tsx tests/temporal/b1.mjs --mechanical MODEL` требует конкретного бюджета четырёх читающих ходов: planning LOAD/ответ и
отдельная acceptance LOAD/ответ. Повторная проверка принятого planning не начинает новую модель.
Все временные сервисы останавливаются, usage и пять replay-историй сохраняются.

## Substantial с обязательным planning

Тот же клиент `./local-task` принимает вход версии 3: `baseline`, `executor: { path, sha256 }`
и `admission` версии 3 с `preparation`, `plan: { path, sha256 }`, `planning` и `acceptance`.
Две последние ссылки — immutable ReviewRequest; scope обоих равен `plan_id`. Проект перечисляет
все свои роли, для каждой явно задаются применимость, полнота входов и история.

План `schema_version: 2` сохраняет поля B1 и добавляет `plan_id`; все восемь рисков заданы
boolean, хотя бы один положителен, `unknown_consumers` false и карта потребителей полна.
Это отдельный договор: положительный риск по-прежнему запрещён в B1. Все source refs содержат
точные относительные пути и SHA-256. Scope может включать новые обычные файлы в существующих
каталогах; отсутствующие будущие acceptance-входы разрешены только как явно объявленные outputs.

`prepareSubstantialPlanning` проверяет proposal, sources, права scope, профиль исполнителя,
команды и полный пакет обеих фаз до зависимых ролей. Immutable preflight фиксирует исходные
bytes/modes, отсутствие будущих файлов и отдельное proposal evidence. Координатор запускает
planning ReviewWorkflow; незавершённый или отрицательный результат запрещает writer. После
первичной сверки принятого результата и всех входов используется прежний пишущий путь,
physical stop, checks, integration и отдельный acceptance ReviewWorkflow.

Запросы с `expectedFiles` сохраняют смысл: planning сверяет ожидания до моделей, acceptance —
до своих ролей на окончательных файлах. Принятый manifest повторно сверяется с первичными
ответами; одного `complete: true` недостаточно. Отмена ждёт дочерние поручения по прежней policy.
Подмена во время чтения оставляет диагностируемый blocked, решение о продолжении сохраняет
прежние полномочия. ReviewRequest/ReviewSnapshot версии 3 явно запрашивают структурированный ответ через
`turn/start.outputSchema` CLI 0.154.0. Enum закрепляют host-owned role/phase/scope/review;
выводы и ограничения выбирает роль. Хост сохраняет строгую сверку исходного primary ответа;
искажённый binding никогда не исправляется автоматически. Переход с формата 1/2 на структурированный формат 3 исключает reuse.
Запросы версий 1/2 и их operation hashes остаются прежними. Автоматических corrections/арбитража
этот обычный маршрут не добавляет.

`yarn test:substantial-task` проходит настоящий SDK-путь без модели; native-вариант
`node --import tsx tests/temporal/b1.mjs --substantial MODEL` требует конкретного бюджета: для двух применимых ролей это 11 ходов
(четыре planning, три writer, четыре acceptance). Стенд сохраняет usage, семь replay-историй
и teardown. `node tests/temporal/b1.mjs --substantial-fault=CASE` проверяет
`missing`, `planning`, `changed`, `cancel-planning`, `baseline`, `acceptance`, `cancel-writer`
или `cancel-check`, имитируя только модель. `changed` фиксирует blocked и отменяет дерево задач;
это не автоматическое переутверждение изменённого предложения.

## Конфигурация, диагностика и восстановление читающего хоста

Immutable permit версии 2 закрепляет schema/policy version и точные model/effort/clientVersion
до модельных действий. Подмена профиля Worker запрещает новые действия и RESUME. Freeze/stop
используют сохранённый профиль. Старый permit без конфигурации не обновляется догадкой.

После сборки `yarn reader-status WORKFLOW_ID ADDRESS` (`node dist/client/index.js --status` из корня)
однократно читает Describe, Query и ограниченный хвост первичной истории. Вывод содержит run,
очередь, известную версию Worker либо null, логическую операцию, попытки/пределы и следующий
разрешённый шаг. Он различает ожидание человека/Worker, неизвестный эффект, техническую ошибку
и ошибку Workflow Task. Недоступность или неизвестная причина названы явно. Команда не вызывает
модель, не ведёт вторую БД состояния и не выдаёт завершение Temporal за PASS.

Длительные Activities передают heartbeat; при потере процесса SDK повторяет прежнюю логическую
операцию не более двух раз. Обычный отказ договора/unknown не повторяется автоматически.
Эффект по-прежнему защищён внешним журналом, первичной сверкой и неизменным ID.
`./reader-recovery` экспортирует явный `recoverReaderHost(projects, directory, profile, assignments)`:
он принимает полный список прежних регистраций и входов, проверяет immutable admissions,
мёртвый PID и терминальные первичные истории. Неизвестный create/send, активный ход, чужой
сеанс, изменившийся журнал или неполный список запрещают освобождение прежнего host-owner.
Квитанция сохраняется до освобождения; разрешения frozen/released не активируются и RESUME
не выдаётся. Это восстановление мёртвого локального процесса при сохранённых данных и
доступном прежнем сеансе, не восстановление потерянного хоста или перенос между движками.

Хост с пишущими задачами сохраняет неизменяемые записи допуска отдельно для каждого
экземпляра в `task-admissions-v2/<instance>`. Восстановление читает полный список
попыток освобождаемого экземпляра. Каталоги первого формата также поддерживаются.
Повторное открытие в том же каталоге хоста сохраняет прежний журнал `turn-credits`
и лимит. Для RESUME сохранённой попытки хост под блокировкой повторно проверяет
остановку и неизменность прежней копии, затем принимает точную команду человека.
Следующая попытка получает собственную запись, а исходные допуск и остановка сохраняются.

На остановленном выделенном хосте после разрешения владельца вызовите
`extendTaskBudget(directory, store, expected, limit, runId)` из `./task-execution`.
Передайте исходный каталог `state/turn-credits`, хранилище задачи и последнюю квитанцию
бюджета из состояния ожидания. Первое увеличение сохраняется в `extension.json`,
последующие — в `extension-<предыдущий лимит>.json`. Каждая запись привязана к
предыдущей квитанции и тому же Run ID. Операция сверяет списания под блокировкой.
Повтор принятого запроса сохраняет действующий лимит. Перед запуском выделенного
хоста укажите последний подтверждённый лимит в `maxTurnStarts`.

### Замена Worker после подтверждённой записи B1

Для B1 (`LocalTaskInput` версии 1) в пространстве имён `default` новый процесс вызывает
обычный `createReaderHost` с прежней очередью, каталогом хоста, регистрацией проекта,
профилем и бюджетом. Последний необязательный аргумент — `{ workflowId, runId }` исходной
задачи. После создания Worker вызовите `host.runUntil(() => handle.result())` с handle
этого запуска. Очередь на время восстановления выделяют этой задаче.

Точка передачи — сервер уже подтвердил результат Activity `writeLocalTask`, следующая Activity
ещё не назначена. Сверяются смерть прежнего процесса, единственное задание, пустой реестр
читателей, полная история до записи, локальная квитанция той же Activity и Run ID, остановка
исполнителя, прежнее разрешение и обе копии файлов. После сверки новый процесс атомарно
занимает место владельца. Первичные квитанции и запись о передаче остаются в каталоге хоста.
У Codex состав дочерних процессов может измениться между запуском и остановкой. При чтении
квитанции завершившийся ранее дочерний процесс привязывается к дереву запуска по исходным
PID, родителю и времени старта. Проверка живых процессов охватывает обе описи. Если связь
потеряна, обнаружена подмена или остался живой процесс, передача блокируется.
Новый Worker продолжает с проверки кандидата. Повторное назначение исполнителя отклоняется.
Если запуск SDK завершился ошибкой до начала опроса очереди, восстанавливается прежняя запись
владельца. Более ранний сбой без завершённой записи или более поздний сбой во время переноса
требует сверки соответствующего состояния.

Чтобы защитить активную запись B1, в регистрации проекта задайте
`dispatchObservedWrite(job)`. Перед началом опроса подготовьте отдельный процесс
с собственной связью с Temporal и фабрикой Codex. Передавайте `job` этому процессу
один раз через закрытый IPC с поддержкой `Uint8Array`. В процессе вызовите
`observeLocalWrite(client, directory, project, maxTurnStarts, job)` из `./reader-host`
с исходными регистрацией, каталогом и бюджетом. Токен Activity передаётся только в памяти.
Наблюдатель владеет соединением с Codex, подтверждает активность в Temporal и завершает
исходную Activity по её токену после записи результата и квитанции остановки.
При потере Worker дождитесь подтверждения Activity сервером и выполните описанную выше
замену. Если завершение неизвестно, сохраните журнал и остановите передачу.

Для незапущенного исполнителя Input12 после смерти хоста оператор может вызвать
`recoverUnstartedBaseline(registration, directory, input, profile, expected)` из
`./reader-recovery`. Из первичной истории именно этого Run ID передайте в
`expected.snapshot` ссылку входа исходной проверки, а в `expected.baseline` —
ссылку на её результат FAIL. Восстановление проверяет владение попыткой,
отозванный допуск, остановку процессов проверки и совпадение дерева с её квитанцией.
Оно сохраняет первую квитанцию остановки под блокировкой. Повтор с теми же
доказательствами проверяет уже записанную квитанцию. Для доставки результата
используйте штатный `localTaskReconcile` и подтвердите по истории результат
`stopLocalTask`. У Worker должны быть зарегистрированы также
`captureTaskExecutionBudget` и `holdTaskExecution` из `executionControls`.

Нативный contextCompaction после LOAD запрещает ответ по старому контексту. Для продолжения
нужны подтверждённая пауза, человеческий RESUME с новой попыткой и полный LOAD в том же сеансе.
Сжатие внутри LOAD/ответа также отвергает результат. Неизвестная история не считается свежим LOAD.

Проверки без моделей: `test:replay` (неизменяемый синтетический корпус прежней версии),
`test:crash` (убийство процесса/потери ответов/повтор без эффекта), корневая `:context`
(новый LOAD после сжатия). Native-варианты требуют разрешённых конкретных бюджетов;
подробности и границы приведены в профиле проверок проекта.

## Адресные исправления в том же TaskWorkflow

LocalTaskInput версии 4 включает прежний B1 либо substantial admission, `executor`, `baseline`
и `corrections: { maxRounds: 1 | 2, checks: [{ roleId, commands }] }`. Для substantial сначала
обязателен planning всех применимых ролей; B1 сохраняет свой допуск. M1 применяет точный принятый
материал: произвольное исправление этого материала требует нового решения.

Полный первичный FAIL сохраняется, новая копия получает пересечение scope отказавших ролей с
одобренными writable paths. Исходные правила, критерий и потребители сохраняются. Обязательные
проверки повторяются на новых байтах, затем выполняются прежняя интеграция и проверка исходного
дерева. ReviewRequest/Snapshot версии 4 разделяют общий полный пакет и адресные доказательства:
неизменная роль сохраняет прежний квалифицированный PASS, затронутая роль получает свои новые
версии файлов/modes, diff, команды, исходные замечания и историю. Report версии 2 требует
`resolved` с исходными ID: открытые блокирующие замечания нельзя стереть новым PASS.

Советник возвращается через `thread/resume` с проверкой первичной истории и профиля. Старый
допуск отзывается и получает неизменяемую stop-квитанцию перед новым поручением. Поздний stop
старого Workflow не останавливает новую работу в том же сеансе. Одновременно у сеанса один
владелец. Неизвестность, смена профиля, неполная история и отказ остановки блокируют работу;
создание замены и автоматический takeover не разрешены. Отмена Task останавливает все его
раунды. Окончательные проверки, независимый PASS и единая проекция RESULT/DONE остаются прежними.

`yarn test:correction` выполняет сквозной SDK-стенд без моделей: 16 simulated
ходов и девять replay. `node --import tsx tests/temporal/b1.mjs --correction MODEL` использует записанный перед запуском бюджет.
Первоначальный дефект в этом стенде инъецируется после завершения реализации; реальные роли
независимо обнаруживают и проверяют его исправление. Сценарии `--correction-fault=CASE`:
`exhausted`, `third-fail`, `cancel-correction-writer`, `cancel-affected`. Арбитраж, изменение
требований и replanning остаются следующими маршрутами T3.

## Арбитраж после трёх отказов

Вход Task версии 5 сохраняет B1/substantial admission и требует `corrections.maxRounds: 2`.
Поле `arbitration` содержит `roleId`, точный `profile` и `compromiseFindings: [{roleId, findingId}]`.
Роль арбитра объявляется в ProjectAdapter и получает N/A в planning/acceptance; её профиль
входит в исходный снимок. `LocalTaskHost.arbiter` должен совпасть с входом до дорогих действий.
Обычный TaskWorkflow запускается на очереди q; второй читающий host с этим профилем обслуживает
q.arbitration. Оба используют тот же ReviewWorkflow/ControlledReaderWorkflow. По процедуре
профиль арбитра — gpt-6.2-astra/high, иной профиль требует явного выбора пользователя.
Canonical `procedures/arbitration.md` включена в самостоятельный пакет для проверяемого LOAD.

Три последовательных первичных содержательных FAIL одного finding готовят неизменяемый
пакет: связку snapshot/writer/review каждого раунда, исходные заключения, точные writablePaths,
текущие байты, исходные evidence и обязательные проверки. ReviewRequest/Snapshot 5 создаёт
свежий независимый сеанс, без history/reuse. Report 3 содержит `decision` с kind direction,
compromise либо no-decision; поля direction, mandatoryDefect, exception, residualRisk, dissent
и condition проверяются строго. `verdict: NOT RUN` и пустые findings обязательны: арбитр
не выполняет техническую приёмку и не закрывает замечания. Длинные основания не обрезаются.

Direction открывает одну дополнительную узкую correction. Compromise требует явно разрешённой
пары roleId/findingId и `mandatoryDefect: false`; обязательный дефект не может быть снят.
No-decision, partial и неразрешённое исключение сохраняются с условием продолжения, без нового
writer. После допустимого решения повторяются readiness, полные команды, интеграция и affected
review исходного советника; finding закрывает его первичный ответ. Peer PASS переиспользуется
при неизменности его входов. Повторный FAIL после арбитража останавливает Task, второго арбитра
этот бюджет не создаёт. RESULT сохраняет исходные три FAIL и решение с dissent/риском.

`yarn test:arbitration` проверяет SDK без моделей: 28 simulated / 15 replay.
`node --import tsx tests/temporal/b1.mjs --arbitration MODEL` требует записанного бюджета 28 ходов. Стенд явно инъецирует дефект
после первых трёх реализаций, до снимка кандидата; исходные FAIL и все решения настоящие при
native-вызове. Случаи `--arbitration-fault=CASE`: no-decision, compromise-held, compromise-ready,
post-fail, cancel-arbiter, cancel-post-writer. Начальный конфликт, аудит по времени, смена
требований, новые права/критерии и отдельная финализация остаются следующими маршрутами.

В текущем ограниченном входе no-decision/недопустимый compromise завершают Task со статусом
blocked и подтверждённой остановкой. Человеческое продолжение в том же Task, начальный конфликт
и replanning ещё не подключены; рабочее включение этого контура не выполнено.

## Первичное противоречие до реализации

Клиент `./local-task` принимает вход 6: substantial `admission`, `executor`, `baseline` и
`arbitration: { roleId, profile }` без `compromiseFindings`. Арбитр не участвует в planning
и acceptance; его профиль и каноническая процедура проверяются до модельных действий.
Первичный planning имеет request/snapshot 6 и report 4 с `conflicts`:
`{ findingId, sources: [{ path, sha256, bytes }, ...] }`. Подтверждение принадлежит применимой
роли, ссылается на её blocking finding и не менее двух различных точных источников её LOAD.
Сам FAIL не подтверждает противоречие. Неполный пакет, изменённые входы, отсутствие подтверждения
или несколько конфликтов закрывают допуск к зависимым действиям этого ограниченного маршрута.

Арбитраж request/snapshot 7 выполняется отдельно и возвращает прежний report 3. Его первичный
пакет сохраняет оригинальные reports, точные источники, процедуру и scope. Direction требует
повторного planning по report 2 у прежних советников с явным `resolved`; только затем разрешены
baseline, writer и обычная независимая acceptance. Хост учитывает владельца первоначального
planning-сеанса; перед повтором отзывается прежний допуск. Compromise без явного человеческого
решения, no-decision и partial остаются открытыми, writer не создаётся. Three-fail allowlist
сюда не переносится. Интерактивное человеческое продолжение ещё требует отдельного маршрута.

`yarn test:initial-conflict` проверяет полный SDK-путь без модели: 17 имитированных ходов и
12 replay с реальными командами, остановкой и RESULT/DONE. Корневой native-вариант требует
заранее записанного конкретного бюджета. Исторические входы 1–5 не меняются; 65 закреплённых
историй, включая четыре истории нового читающего клиента, проверяются через `yarn test:replay`
без новых модельных ходов.

## Пакет резервной копии и подготовка восстановления

`./backup` экспортирует `createBackup` и `stageRestore`; после сборки тот же вход доступен
как `yarn backup save INPUT.json` и `yarn backup restore INPUT.json`. Корневая команда
`node dist/client/index.js --backup save INPUT.json` использует собранный пакет.
Пути конфигурации локальные абсолютные; корни должны существовать, не иметь символьных ссылок
и не пересекаться друг с другом или местом новой копии.

Перед save оператор останавливает сервер/Workers и внешних writers, подтверждает их судьбу
по первичным данным и получает согласованный PostgreSQL custom export штатным `pg_dump`.
Инструмент проверяет сигнатуру формата, но не запускает сервер, не создаёт dump и не доказывает
его семантическую полноту. Незавершённые host-owner/source-reservation/permission-lock и
временные записи блокируют упаковку; отсутствие этих файлов само по себе не доказывает остановку.
Во время копирования источники остаются неизменными. Упаковка работающего PostgreSQL-каталога
вместо согласованного export запрещена.

Вход save версии 1:

```json
{
  "schemaVersion": 1,
  "persistence": "/absolute/stopped-export/temporal.pgdump",
  "roots": {
    "artifacts": "/absolute/snapshot/artifacts",
    "receipts": "/absolute/snapshot/receipts",
    "workspaces": "/absolute/snapshot/workspaces",
    "build": "/absolute/snapshot/pinned-build"
  },
  "destination": "/absolute/backups/new-backup"
}
```

В `receipts` входят все разрешения, внешние operation receipts, бюджеты и записи закрытых
задач; в `workspaces` — все зарегистрированные исходные деревья, копии и их Git-данные.
Сборка содержит исходный package/lock, dist, процедуры и необходимые для восстановления
версии зависимостей. Это подготовленные каталоги согласованного снимка, а не четыре
произвольных каталога, полноту которых инструмент мог бы угадать. Исходные абсолютные
bindings внутри квитанций сохраняются. Linked worktrees требуют сохранения общего Git-каталога;
один файл `.git` не заменяет его. Такой состав ещё требует эксплуатационной квалификации.

Save возвращает `status: saved` и hash/bytes manifest. Сохрани эту квитанцию отдельно от
пакета: при restore ожидаемый hash берётся из неё. Пакет содержит manifest и blobs по хешам;
manifest публикуется последним после тройной сверки исходников. Символьные/жёсткие ссылки,
специальные файлы, перемена байтов и ошибки диска не дают успешную квитанцию. Неполный каталог
не перезаписывается повтором; сохрани его для диагностики и выбери новый путь.

Вход restore версии 1: `{ "schemaVersion": 1, "backup": "/absolute/backups/new-backup",
"manifest": { "sha256": "HASH_FROM_SAVED_RECEIPT", "bytes": 123 },
"destination": "/absolute/recovery/new-staging-directory" }`. Число bytes и hash должны
точно совпасть с квитанцией save. До создания нового дерева проверяются весь manifest,
каждый blob и безопасная структура путей. Существующий каталог назначения не изменяется.
Файлы имеют права 0600, каталоги и исполняемые файлы — 0700. Исходные данные и пакет не удаляются.

Успех имеет **только статус staged**, `requiresReconciliation: true` и `RESTORE.json`;
`.restore-incomplete` должен отсутствовать. Ошибка записи сохраняет этот маркер и не разрешает
использовать частичные данные. Восстановление не меняет owner/generation/unknown, не выдаёт
новые разрешения и не запускает Worker. Затем нужны штатный PostgreSQL restore, совместимая
сборка, проверка Temporal history, привязок и всех внешних эффектов, особенно после отстающей
копии. Старая квитанция не подтверждает отсутствие более позднего живого Codex-хода.

`yarn test:backup` (`yarn test:backup` из корня) проверяет настоящий CLI
на временных файлах и восстановление после удаления исходников, без сервера и моделей.
Persistence этого стенда — явно синтетические байты с сигнатурой, а не настоящая база.
Проверка входит в standalone с запретом чтения исходного репозитория. Этот этап не подтверждает
промышленный backup/restore, RPO/RTO, ежедневное расписание или защиту от отказа основного диска.

## Отдельный нативный аудит Temporal

`./audit` экспортирует `startAudit(client, input, taskQueue)` с идемпотентным ключом
project/task/auditId. Другой неизменяемый input под тем же ключом отвергается. Это отдельный
AuditWorkflow; подключение к основной задаче задано входами 7–9 ниже.
Версии Task input 1–6 и их поведение сохраняются.

Для хоста требуется явный `ReaderProjectHost.auditor: true`, отдельная очередь аудита и её
очередь `.control`. Профиль родителя фиксирован: CLI 0.171.0-alpha.13, gpt-6.2-sol/medium.
Проект объявляет роль auditor и TOML-профиль native auditor/gpt-6.2-sol/xhigh; профиль и обе
процедуры audit/evidence входят в проверяемый полный LOAD. Preflight проверяет роли, файлы,
доступность обеих reasoning effort и полный MCP inventory без модельного старта; все
найденные MCP-серверы выключаются для нового родителя. Права проверяются по фактическим
native receipts, а не по инструкциям TOML. Встроенный поиск отдельно выключается через
`web_search=disabled` по [договору клиента](https://learn.chatgpt.com/docs/config-file/config-basic#web-search-mode).
Канонический профиль игры остаётся адаптером игры.

Audit input версии 1 содержит preparation, auditId, card и preflight — ссылки SHA-256/bytes
на неизменяемые артефакты. Карточка содержит первичную цель и полные версии источников,
критерии, выполненные доказательства, исходные замечания, checkpoint, следующий шаг и trigger.
Оценка сохраняется исходной; elapsed и внешнее ожидание раздельны и могут быть null.
Для no-progress без этапа timing=null: этап и время не придумываются. Политика `auditClaim`
отвергает ранние 2× и повтор уже обработанного порога даже после смены checkpoint. Новый
no-progress checkpoint либо конкретный риск имеет отдельный ключ. Claim и его применение
должны храниться у вызывающего Workflow; файловые refs не заменяют состояние Temporal.

Родитель создаёт ровно одного auditor с fork_turns=none, затем отдельно доставляет только
локатор неизменяемой карточки. Прямой turn/start ребёнку запрещён. Native тип, root/child
identity, модель/effort и parent turn проверяются по первичным данным. При скрытом userMessage
проверяются task_started/parent_turn_id и тот же encrypted_content у отправителя и получателя;
receipt явно отмечает attributed-encrypted, открытый текст не предполагается и не расшифровывается.
Полный LOAD процедур и карточки, отсутствие compaction и делегирования обязательны. Выбирается
ровно один final_answer со строгим JSON-отчётом; commentary сохраняется в первичной истории.

Только после повторного чтения первичного ответа и остановки обоих исполнителей Workflow
возвращает audited с manifest/report/stop. Полный или частичный отчёт и четыре направления
сохраняются явно; в Temporal возвращаются только coverage/direction и refs, полный текст
остаётся в артефакте. `acceptance: false` запрещает выдавать направление за техническую приёмку.
Отмена сначала закрывает разрешение на новые действия, затем проверяет родителя и всех
наблюдаемых детей. Потеря подтверждения регистрации не означает not-started. Неизвестная
остановка остаётся stop-unknown до auditReconcile; чтение результата не начинает новый модельный
ход. Наблюдение ограничено 20 минутами. Reader-only recovery отвергает host-owner с audits=true:
отдельное восстановление native children пока не квалифицировано, захват такого хоста запрещён.

`yarn test:audit` (из корня `yarn test:audit`) проверяет пять настоящих
SDK-историй с имитацией модели: complete/partial, отказ LOAD, отмену и stop-unknown/reconcile,
а затем replay. `node --import tsx tests/temporal/audit.mjs --native` требует заранее записанного бюджета; фиксированные модели не
подменяются параметром. Обычный путь стенда содержит четыре старта, резервный пятый допускается
только для safety interrupt. Исторические FAIL сохраняются; standalone и SDK не заменяют native
доказательства. Полный маршрут TaskWorkflow по времени, дальнейшие маршруты T3 и эксплуатация
T4–T7 этим отдельным аудитом не объявляются завершёнными.

`node --import tsx tests/temporal/audit.mjs --native-cancel` выполняет отдельную раннюю native-отмену при ожидании первого ответа LOAD:
два старта и резервный третий только на safety interrupt. Прогон подтверждает inProgress →
interrupted и primary stop; остановку уже исполняющейся команды чтения он не доказывает.

### Аудит планирования основной задачи

Явный Task input 7 добавляет к ordinary substantial поле
`audit: { planningEstimateMs }`. Исходная оценка обязательна до запуска совета, положительна
и не превышает часа. Схемы и команды Workflow старых входов 1–6 сохраняются; общий reader
stop до первого хода исправлен отдельно. Для основной очереди
нужен `LocalTaskHost.auditorRpc` — доступ только для первичной проверки; отдельный audit-host
обслуживает очередь `<main>.audit` с профилями родителя и native auditor, описанными выше.
В таблицах planning/acceptance роль auditor получает явное N/A: она не выдаёт приёмку.

Temporal запускает исходный совет и таймер 2×. При превышении фиксирует единственный
`planning:overrun`, создаёт неизменяемую карточку и вызывает AuditWorkflow. Полный исход
`continue` вместе с подтверждённой остановкой допускает ожидание того же совета. Новый
аудит по тому же превышению не запускается. Partial, другое направление или неизвестные
первичные данные останавливают допуск исполнителя; отмена дожидается остановки обоих детей.
Интервал надзора начинается после проверки входов и профиля аудита: он включает исходный
совет, создание сеансов, LOAD, ответы и внутренние ожидания. Полный wall задачи и подготовка
сохраняются отдельно в общем статусе и Activity timings. Оценка, время и refs сохраняются
в supervision artifact, снимке и RESULT. Перед допуском
и завершением заново проверяются native история, профиль, LOAD, карточка, отчёт и остановка.
Изменяемые исходники при завершении сверяются с закреплённым planning, а текущие байты
реализации проходят самостоятельные checks/acceptance. Неизвестное время остаётся null.

`yarn test:supervised-task` и `yarn test:supervised-cancel` проверяют полный SDK-маршрут
и отмену без моделей; из корня доступен `yarn test:supervised-task`.
Временный стенд явно задерживает внутреннее наблюдение planning LOAD до первого запуска
аудитора, максимум на 120 секунд. Это управляемая проба таймера, а не измерение замедления
модели; внешнее ожидание здесь равно нулю. Для этих проверок задайте в `AW_MAIN_MODEL` разрешённую основную модель из каталога CLI стенда `0.154.0`. Профиль отдельного аудитора закреплён в его договоре.

Native-команда `node --import tsx tests/temporal/b1.mjs --supervised "${AW_MAIN_MODEL:?}"`
требует заранее записанного отдельного бюджета: до 11 основных и четырёх audit-стартов.
Дальнейшие этапы, no-progress/doubt основной задачи, correction/arbitration и native recovery
аудита остаются последующими маршрутами T3; постоянный режим этим входом не включается.

Вход версии 8 добавляет обязательный `audit.stages` с оценками в миллисекундах для `baseline`,
`writing`, `candidate-checks`, `integration`, `integrated-checks`, `acceptance`. Оценки задаются
до старта; каждая положительна и не превышает часа. Те же правила 2×, одного claim, полного
continue и stop действуют во время каждой исходной операции. Шесть неизменяемых записей и
свежая проверка всех аудитов обязательны до RESULT/DONE. Порядок и привязка записей к входу
и снимку проверяются; аудит не заменяет результат операции и техническую приёмку.
Изменяемые файлы передаются через неизменяемые blobs и снимок путей, неизменяемые входы —
через обычные проверяемые sources. Неполученный результат и ненаблюдаемый прогресс остаются
неизвестными. Прежние входы 1–7 и replay-корпус сохраняются.

`yarn test:stage-supervised-task` проверяет полный SDK-путь с таймером writing;
`yarn test:stage-supervised-cancel` — отмену при активном LOAD аудитора и остановку writer.
Самостоятельный допуск запускает оба стенда. Из корня доступны команды
`yarn test:stage-supervised-task`, `yarn test:stage-supervised-cancel` и отдельно разрешаемая
`node --import tsx tests/temporal/b1.mjs --stage-supervised "${AW_MAIN_MODEL:?}"`. Стенд задерживает наблюдение завершения writer до
первого аудита, максимум 120 секунд; это внутреннее ожидание, не сравнение скорости модели.

Вход версии 9 сохраняет поля входа 8 и добавляет `progress: {checkpoint, trigger}`. Trigger
имеет kind `no-progress` либо `doubt` и ArtifactRef `evidence`. Контрольная точка одна:
после baseline и до первого writer. Это явный запрос независимой оценки, не автоматический
диагноз отсутствия прогресса. Доставка нового запроса во время исполнения и человеческое
продолжение остаются последующими маршрутами. Повтор того же start использует ту же задачу;
иной payload конфликтует.

Evidence — неизменяемый `task-progress-request` версии 1: preparation, checkpoint, trigger-kind,
goal `{path, sha256, bytes}`, непустой список первичных evidence и краткий reason. Подмена цели,
редакции или контрольной точки, отсутствующие blobs и неполный запрос отвергаются ещё до
planning-моделей. Производный `progress-<checkpoint>` должен помещаться в обычный identifier.
Карточка содержит исходную цель, завершённый planning с первичными ответами, baseline и
входные байты. Timing равен null; stage/estimate/stage elapsed не придумываются. Наблюдаемое
время всей задачи передаётся отдельно как taskElapsedMs, неизвестное — null.
Первый writer и DONE требуют полного continue, подтверждённого stop и свежей проверки
квитанции. Этот аудит не заменяет техническую приёмку и не закрывает исходные FAIL.

`test:progress-task` и `test:progress-doubt` выполняют полные SDK-пути; `test:progress-cancel`,
`test:progress-held`, `test:progress-partial` проверяют остановку до первого writer. Эти команды
входят в standalone. Искусственной задержки модели в этих сценариях нет. Для живой проверки
из корня доступны `node --import tsx tests/temporal/b1.mjs --progress-no-progress "${AW_MAIN_MODEL:?}"` и
`node --import tsx tests/temporal/b1.mjs --progress-doubt "${AW_MAIN_MODEL:?}"` с заранее записанными бюджетами.

CLI 0.154.0 не поддерживает историю до первого сохранённого хода. Progress сохраняет
проверенный native header и явную неизвестность истории/LOAD; `idle` не выдаётся за пустую
историю. Общая остановка допускает отдельное подтверждение только для закрытого журнала с
единственным успешным fresh thread/start и без модельных отправок/resume/unknown create:
два проверенных idle headers и повторная сверка журнала. Все прочие случаи остаются unknown.
`node --import tsx tests/temporal/unstartedReader.mjs` проверяет этот путь на настоящем CLI,
поздний LOAD и остановку процессов, гарантируя ноль отправок `turn/start`. Проверка не требует
модельного бюджета и не возобновляет прежние неизвестные сеансы. Исторические отказы сохраняются.

## Человеческое продолжение и отдельный архив

Вход Task версии 10 — ordinary substantial с `continuation: {attempt: 0, previous: null}`.
Он сохраняет исходный planning FAIL, подтверждает остановку читающих ролей и ожидает человека
до первого writer. Update `taskPlanningControl` принимает только отдельный RESUME версии 2,
привязанный к held-артефакту и admission через payload ref. Дубликат возвращает прежний ответ;
иной payload, stale revision, чужой target или расширение paths отвергаются. Новая редакция
требует полного перепланирования и новых зависимых проверок. Входы 1–9 сохраняются.
`./task-continuation` экспортирует `makeTaskPlanningCommand` и `controlTaskPlanning`.

`./task-execution` экспортирует `makeTaskExecutionCommand` и `controlTaskExecution`
для Update `taskExecutionControl` входа Task версии 11. Этот вход управляет прерыванием
и продолжением полного маршрута planning/writer/checks/integration/acceptance. Held требует
подтверждённой остановки и ожидания незавершённых действий; отдельный RESUME закрепляет
held и admission для продолжения через payload `task-execution-resume`, сохраняя owner/generation
и не расширяя прежний writable scope. Публичный export и его импорт сами не запускают задачу, Worker
или модель.

Для команды `resume` задачи из Codex Desktop `0.169.1` владелец отправляет точный JSON
отдельным сообщением в исходном чате проекта. Проверка сверяет байты команды, происхождение
сообщения, рабочую копию и запись доставки. Затем она проверяет квитанцию выполнения команды
в том же чате. Ответ через форму подтверждения для этой версии не даёт допуска.

Для Task версии 12 после подтверждённого `FAIL` на шаге `integrated-checks`
оператор может отправить `resume` с **текущим** номером попытки через
`controlTaskExecution`, закрепив Run ID. Payload версии 2 указывает исходные
`held`, `admission` и `startAdmission`. Worker сверяет остановку, квитанцию
переноса и версии файлов, заново выполняет зарегистрированные проверки и передаёт
результат независимой приёмке. Исходный FAIL сохраняется. Изменённые файлы,
неопределённый перенос или неполное подтверждение проверки блокируют приёмку.
Номер попытки, увеличенный на один, по-прежнему означает полное перепланирование.

Для новых команд 2/3 первичное пользовательское сообщение после trim должно точно совпадать
с `nativeHumanAuthorizationText(command)` из `./reader-authority`: schemaVersion, commandId,
author, action, target, expectedRevision, attempt и payload. Поля source/hash исключены из
текста намерения, чтобы не создавать цикл хеширования. Обычная фраза RESUME не разрешает
новый payload или архив; отдельный native notice дополнительно подтверждает выдачу.
Исторические байты/поведение команды 1 сохранены. Поддерживаются точные версии источника
0.164.0-alpha.11.1 и наблюдённая 0.165.0-alpha.1.2; новая версия требует source=vscode,
forked_from_id=null и id=session_id. Это поддержка формата, не квалификация живого grant.

`./finalization` запускает независимый `FinalizationWorkflow`, `./finalization-host` создаёт
его отдельный Worker. Вход содержит `operation: archive`, исходный RESULT/DONE и отдельную
ArchiveCommand версии 3 с action archive. Payload закрепляет result, файловые roots/destination
и inventory. Authority, payload и receipts хранятся вне архивируемых roots. Перед копированием
и публикацией каждого blob проверяется принятый manifest. Потерянный ответ сверяет готовую
копию; partial/unknown ждёт `finalizationReconcile` и не создаёт вторую. Основной TaskWorkflow
не запускает и не ждёт этот архив; RESULT/DONE не меняются. Cleanup не реализован.

`test:continuation`, `test:requirements` и `test:finalization` — подготовленные SDK-стенды
без моделей, включённые в standalone. Последний теряет ответ архивной Activity и сверяет
тот же результат; сохраняются незавершённые истории ожидания человека и сверки архива.
Проверка живого продолжения и восстановления требует отдельных первичных доказательств.

Архивная Activity явно использует WAIT_CANCELLATION_COMPLETED, heartbeat и guards отмены
до/после authority и перед началом эффекта. Отмена до copy не создаёт архив; начатая copy
сохраняет фактический исход. Timeout/потеря ответа переводят финализатор в nonCancellable
unknown: `reconcileFinalizedTask` только читает существующие intent/receipt и проверяет копию,
не вызывает authority и не начинает новую copy. Утрата самой первичной квитанции требует
восстановления подлинных данных; готовой копии недостаточно для выдумывания receipt.
SDK-команды `test:finalization-cancel-before`, `test:finalization-cancel-after` и
`test:finalization-timeout-cancel` проверяют эти границы. Последняя использует явно отмеченный
test-only interceptor с timeout 1 с; production timeout не сокращён. Принудительное завершение
используется только для очистки теста после наблюдаемого выхода Activity и не считается
успешным архивом. Для replay такого случая обязателен тот же fixture-профиль.
