# Подготовка сопоставимого сравнения с Temporal

Исполнение и результаты TEMP-17–18 ведутся в [плане сравнения](exec-plans/active/2026-11-21-legacy-temporal-comparison.md). Существующий
[`comparison/README.md`](../comparison/README.md) описывает прежний исполнитель;
его формат или ранее выданный бюджет не разрешают новую Temporal-серию.
Квалификационные B1/M1/substantial/native результаты подтверждают свои маршруты и не являются
сравнением скорости или стоимости.

## Одна задача, два исполнения

До первого модельного RPC зафиксировать manifest серии и SHA-256 каждого элемента:

| Элемент | Что должно совпадать / как учитывать различие |
| --- | --- |
| Задача | Одинаковые исходное поручение, все требования, критерии и разрешённые пути результата; неизменяемый проверяющий сценарий |
| Исходники задачи | Один snapshot/hash и Git revision либо явный null; два независимых checkout с одинаковыми байтами. Runtime baseline/candidate закрепляются отдельно |
| Модель | Одинаковые бинарник/hash, фактическая версия клиента, model, effort, права, правила и отсутствие посторонней истории у сопоставимых ролей |
| Приёмка | Одинаковые дефекты/ожидаемое поведение, команды, независимые критерии и порядок оценки качества. Полный обязательный совет каждой реализации включён в её затраты |
| Среда | Node/Yarn/lock, ОС/архитектура, cache policy, CPU/места Workers, версии SDK/server, оборудование, фоновые процессы и сетевые условия закреплены |
| Жизненный цикл | Начало до подготовки копии, конец после результата, проверок, независимой приёмки и подтверждённой остановки. Общая подготовка учитывается отдельно и в полном времени серии |

Нельзя назвать задачи одинаковыми только по имени. Исправление harness, несовместимого baseline,
критерия, исходников, модели или прав после старта требует новой серии и нового manifest;
расходы и исходные отказы прежней серии остаются в отчёте. Изменения приложения между вариантами
не допускаются. Доказательство от одного сеанса не передаётся другому как готовое решение.

Отдельный H01 уже содержит общий проверяющий сценарий и два узких адаптера для одного
варианта одной попытки. Полной серии ещё нужны оркестрация и квалификация обоих путей.
Нынешний `cli/comparisonSeries.ts` не является Temporal-клиентом. Для серии сначала без моделей
проверяются равенство входов, независимость копий, полнота учёта, штатный stop и отказ при unknown,
затем отдельно квалифицируется настоящий клиент. Новая схема серии требует явной версии;
старые отчёты остаются читаемыми и не получают выдуманные поля.

## Офлайн-проверка manifest подготовки

`tests/comparisonReadiness.ts` — отдельный контур репозитория, вне `src`, `dist` и runtime
поставки. Он переиспользует `parseComparisonSuite`, `parseComparisonMaterials`,
`comparisonSchedule`, canonical и SHA-256; прежние CLI/runner не меняются. Команды только
читают файлы, без exec, установки, копирования, служб или моделей:

```sh
yarn --silent comparison:prepare --plan
yarn --silent comparison:prepare --check /absolute/manifest.json
```

`--plan` выводит JSON-черновик, который до заполнения неизвестных полей отвергается проверкой.
Формат manifest — `schema_version:1`, `kind:"temporal-comparison-readiness"`, непустой
`seriesId`, строго `allowedModelStarts:0` и `authorization:null`, два `variants` и точный `order`.
Иные поля бюджета и прежние лимиты suite не принимаются как новый допуск.

Каждый вариант содержит:

- `runtime:{engine,artifact}`: baseline объявлен `legacy`, candidate — `temporal`; artifact —
  локальный `{locator,hash}`. Это намерение выбора пути, не доказательство его исполнения.
  Один закреплённый артефакт может содержать оба пути, равенство его SHA допустимо.
- `taskSource:{locator,hash}`: точные байты текущего `comparison/materials.json` с поручениями,
  файлами и scope **только шести прежних H-01–H-06**; `criteria` так же закрепляет текущий
  `suite.json`. Замена даже с пересчитанным hash отвергается. Произвольный полный исходник игры
  этот формат не принимает и не закрепляет. `sourceRevision` — одинаковая заявленная Git SHA
  из 40 символов либо явный null; Git без exec независимо не проверяется.
- `profile`: model, effort, clientVersion, непустой уникальный список roles и локальные pins
  client/rules/permissions. Проверяются bytes/hash и совпадение схемы/значений; permission pin
  описывает вход, не выдаёт права. Разные locators одинаковых байтов допустимы.
- `environment`: node/yarn/os/architecture, cold либо warm cachePolicy, sdk/server, положительные
  целые workerSlots и pins lock/hardware/background/network. Это равенство закреплённых
  деклараций, не измерение действующей среды или подтверждение effective runtime.

`order` фиксирует все 24 выполнения: по каждой задаче baseline/candidate, затем
candidate/baseline. PASS возвращает refs/hash, canonicalManifestHash, хеши профиля/среды и
расписание без содержимого файлов. FAIL также не раскрывает байты или текст исключения парсера.
Любой результат сохраняет `mayRun:false`, `qualification:false`, `allowedModelStarts:0` и
`authorization:null`. Проверка не создаёт разрешения или готовой серии. Будущие независимые
копии, полнота участников, actual client/stop/native accounting и full-game qualification
остаются непроверенными. H01 ниже даёт отдельные адаптеры одной попытки; для живой полной
серии нужны её оркестрация, квалификация этих путей и собственный действующий бюджет.

## Файлы выполняемого сценария

Существующий `comparisonSeries` перед checker вызывает общий `verifyComparisonMaterial`.
Каждый объявленный файл, включая mutable, должен существовать как обычный файл своей
канонической case-копии: ссылки, hardlink, специальные файлы и alias родителя отвергаются.
`projectPath` и `safeDirectory` проверяют путь; чтение физических bytes использует
`O_NOFOLLOW`/`O_NONBLOCK`, сверку дескриптора/пути до и после и закрытие fd при отказе.
Неизменяемые материалы сравниваются с точными UTF-8 bytes, без разыменования file-location
pointers; mutable может менять содержимое. Вложенные обычные файлы и дополнительные
`evidence/` допустимы. Это наблюдаемая файловая граница, без атомарной ABA-гарантии.
Исправление не превращает прежний runner в Temporal adapter и не квалифицирует native-серию.

## Равенство предоставленных деревьев исходников

Тот же `--check` принимает отдельный manifest `schema_version:2`: все поля schema1
сохраняются, добавляется обязательный `sourceSnapshot`. Schema1 и обычный `--plan` не меняются
и не включают это поле. У источника и двух уже подготовленных копий проверяется весь предоставленный
namespace, без исключений для `.git`, `node_modules` или иных путей:

```json
"sourceSnapshot": {
  "inventory": {"locator": "/absolute/source-inventory.json", "hash": "SHA-256"},
  "roots": {
    "source": "/absolute/prepared-source",
    "baseline": "/absolute/baseline-inputs",
    "candidate": "/absolute/candidate-inputs"
  }
}
```

Inventory использует существующий формат `inventory(root)` из installed-consumer:
массив `{path,mode,kind:"directory"}` и `{path,mode,kind:"file",sha256,bytes}`, включая
корень с `path:""`; каталоги и файлы перечислены в порядке рекурсивного обхода с сортировкой имён.
Закреплённый inventory должен находиться вне трёх деревьев и содержать хотя бы один обычный файл.
Три абсолютных канонических корня различны и не вложены друг в друга.

Проверка самостоятельно читает деревья и требует точного совпадения с inventory: отсутствие,
добавление, повтор записи, неверный путь, изменение mode или физических bytes отвергаются,
даже если декларация inventory переподписана новым hash. Ссылки, hardlink и специальные файлы
не принимаются. Read-only walker проверяет родительские каталоги и identity, открывает обычные
файлы с `O_NOFOLLOW`, сверяет дескриптор и путь до/после чтения, затем повторяет полный обход
и проверку привязки корней. File-location pointers считаются физическими байтами и не разрешаются
во внешнее содержимое. Проверка не создаёт inventory или копии и ничего не исполняет.

PASS schema2 добавляет `sourceSnapshot` с refs, корнями, `treeHash` и `observedEquality:true`,
без содержимого файлов. Он доказывает равенство namespace/mode/bytes предоставленных деревьев
при этих наблюдениях. Это **не** доказательство происхождения полного game snapshot или Git revision,
не атомарный снимок filesystem при произвольных ABA-гонках и не гарантия будущей неизменности копий.
`full-game-source`, `git-revision`, `future-isolated-copies` и прочие `unproven` остаются в отчёте.
`mayRun:false`, `qualification:false`, `allowedModelStarts:0`, `authorization:null` сохраняются;
executor и два runtime adapter этим контуром не появляются.

## Офлайн-журнал последовательности серии

Тот же читающий контур проверяет отдельный версионированный журнал наблюдений:

```sh
yarn --silent comparison:prepare --series-check /absolute/series-record.json
```

Владелец — `checkComparisonTemporalSeries` в `tests/comparisonReadiness.ts`; прежние
`--plan`, `--check`, CLI-исполнитель и отчёты schema1 сохраняют свой договор. Журнал имеет
строго следующие поля:

- `schema_version:1`, `kind:"temporal-comparison-series-record"`, `allowedModelStarts:0`,
  `authorization:null`;
- `readiness:{locator,hash}` — закреплённый manifest подготовки версии 1 или 2;
  `canonicalManifestHash` — его канонический SHA-256. Manifest и все его pins проверяются
  заново; скопированный прежний PASS не используется;
- `elapsed_ms` — объявленное полное время, целое неотрицательное число;
- `preparation:{participants,receipts,timing,stopConfirmed}` — общая подготовка;
- `attempts` — упорядоченные блоки `{participants,receipts,result,stopConfirmed}`.

`participants` содержит уникальные непустые ID; для попытки список непустой. Каждый заявленный
участник имеет хотя бы одну квитанцию своего блока. Квитанции используют существующий
`ComparisonReceipt`, с `run:null` для подготовки и точным ID выполнения для попытки;
их IDs уникальны во всём журнале. Неизвестные показатели записываются явным `null`, не нулём.
`result` содержит существующие поля `run`, `attempt`, `outcome`, `checks`, `evidence`,
обязательный `timing` и только при сверке неизвестного исхода — `reconciles`.

Время использует существующие `start/end:{wall_ms,monotonic_ms,clock_id}` либо явный `null`.
Неполные, противоречивые или разорванные часы блокируют следующий шаг. Объявленное полное
время покрывает подготовку, разрывы и конец последнего результата; времена участников
не складываются. `stopConfirmed` — обязательное логическое объявление, а не проверенная
первичная квитанция остановки.

Проверка требует точного порядка 24 выполнений. Следующий слот допустим в журнале только
после accepted со всеми checks, известного учёта/времени и объявленной остановки предыдущего.
Пропуск, перестановка, повтор accepted и продолжение после FAIL отвергаются. Версия 1 не
поддерживает повтор FAIL; он остаётся предметом отдельного решения. UNKNOWN допускает только
сверку того же run/attempt с новым evidence; исходная запись и затраты сохраняются.
Пределы старого suite проверяются как дополнительные ограничения записанного порядка,
включая время подготовки и разрыв перед стартом, и не становятся новым разрешённым бюджетом.

Структурный PASS возвращает totals, число принятых наблюдений, `observationsComplete` и
`next:{action,run}`. Неизвестный расход, UNKNOWN, неподтверждённая остановка, отсутствующее время
или предел дают блокирующее действие; `prepare-run` лишь называет следующий слот подготовки.
Отчёт всегда сохраняет `mayRun:false`, `qualification:false`, `allowedModelStarts:0`,
`authorization:null`. Полнота фактических участников, первичные результаты/STOP, runtime,
исполнитель серии и её действующее разрешение остаются непроверенными. Этот шаг не закрывает
TEMP-17/18 и не доказывает экономию.

### Сверка первичного расхода журнала версии 2

`--series-check` также принимает `schema_version:2`. Договор версии 1 сохраняется;
в версии 2 у каждого блока подготовки/попытки обязателен `usageSources`. Каждый источник
содержит `session`, `transcript:{locator,hash}`, `run`, `stage`, обязательный `through`
и необязательный `after`. Границы — `{locator,hash}` точной строки `transcript#L<N>`.
Весь файл журнала закреплён отдельно; hash проверяется до и после чтения сборщиком.

Для каждого заявленного участника нужен источник его блока. Квитанции используют
`NativeComparisonReceipt`: прежние поля и обязательный `source:{locator,hash}`.
Существующий `readComparisonUsage(...,false)` пересчитывает перечисленные диапазоны
без второго парсера; IDs, привязка, стадии, все четыре показателя и первичные ссылки
должны точно совпадать с объявленными квитанциями независимо от порядка массива.

Один `session` во всей серии имеет один закреплённый файл журнала. Два экспорта одного
сеанса, в том числе в разных форматах, отвергаются до чтения конфликтующего источника:
различные алгоритмы ID не должны превращать один расход в два. Непересекающиеся диапазоны
одного pin допустимы; повторный учёт той же квитанции запрещён общим реестром IDs.
Неизвестные первичные показатели сохраняют `null` и блокируют следующий шаг.

PASS добавляет `primaryUsageVerified:true`, `usageVerificationScope:"listed-ranges"`.
Это соответствие перечисленным диапазонам закреплённых файлов, а не обнаружение всех
участников и затрат. Записи вне диапазонов, происхождение журнала, фактический профиль,
STOP и действующее разрешение серии не подтверждаются. Все запреты запуска сохраняются;
полное исполнение 24 попыток и критерии TEMP-17/18 остаются открытыми.

## Исполняемый срез H01 общего сравнения

`tests/comparisonH01Series.ts` связывает первые четыре H01-позиции полного расписания
из 24 выполнений с существующим `runH01Operator`. Порядок — baseline/candidate, затем
candidate/baseline. Каждый шаг использует собственный точный допуск H01; общий лимит
манифеста является дополнительным ограничением, а не разрешением других запусков.

```sh
yarn comparison:series --plan /absolute/manifest.json
yarn comparison:series --status /absolute/series/state.json
```

Эти команды только читают входы. Отдельная команда
`yarn comparison:series --step /absolute/step.json` выполняет один шаг после проверки
его допуска прежним оператором H01. Разрешение на локальный `yarn validate` не разрешает
такой модельный запуск.

Манифест содержит `kind:"comparison-h01-series"`, `schemaVersion:1`, pin `readiness`
версии 2, отдельный `outputRoot`, начало общего интервала `startedAtMs`, общий `cap` и
ровно четыре `steps:{runId,spec,request}`. `cap` задаёт положительные целые
`maxElapsedMs`, `reserveMs`, `maxManagedStarts`, `maxInputUncached`, `maxOutput`.
Время подготовки, промежутки и остановка входят в общий интервал; новые шаги не обнуляют
его начало. Между командами сохраняется монотонная отметка; несогласованность часов
или потеря применимости временной границы блокирует следующий шаг.
Закреплённый бюджет H01 целиком должен помещаться в оставшийся общий лимит
с резервом; менять бюджет H01 под существующим допуском нельзя.

`spec` и `request` — pins существующих H01 operator spec и draft request. Для реального
сбора нужны две пары `prepareH01Drafts` с одинаковыми исходниками/сборкой и независимыми
opId/корнями. До получения допусков candidate inventories закрепляются на одном общем
buildRef с теми же байтами. `readiness.variants.*.runtime.artifact` закрепляет общий H01
runtime inventory `{engine,root,files}` без шагового operator spec; каждый шаговый
runtime содержит в точности общий список и собственный `spec`. Произвольные добавочные
файлы не допускаются; проверка полной closure `verifyH01Runtime` сохраняется.
Полные профили H01, включая executor/reviewer и отключённые MCP, совпадают у всех шагов.

Запрос шага имеет `kind:"comparison-h01-series-step"`, `schemaVersion:1`, `manifest`
и `request` pins, `runId`, `previousState` — pin прежнего `state.json` либо null для
первого шага. Его `request` закрепляет уже заполненный точным допуском H01 запрос.
Сравнение штатного `h01RequestHash` разрешает отличаться от draft только полям источника
допуска, его hash и текущего turn, которые исключает владелец этого hash. Параметры задачи,
профиль, корни, бюджет и остальные полномочия остаются закреплёнными.

До вызова оператора сохраняется durable pending; отдельный writer и проверка привязки
каталогов защищают серию от параллельного шага. Неизменные завершённые команды возвращают
сохранённый результат. Pending, UNKNOWN, FAIL, неполные расходы или неподтверждённая
остановка блокируют повтор и следующий шаг. Ошибка записи результата после эффекта
оставляет pending. История проверяется по сохранённым первичным отчётам, а не по одной
суммарной отметке accepted.

`comparisonH01SeriesEvidence.ts` сверяет цепочку operator → owned → child, первичные
квитанции расхода, ответ независимого советника и STOP. Неизвестные общие суммы остаются
null; `knownSubtotal` сохраняет только подтверждённую нижнюю границу и не разрешает
продолжение при неизвестности. Время оператора берётся из его первичного отчёта;
неполное время child не выдаётся за полный интервал.

Это отдельный операционный журнал. Он не является экспортом в офлайн-формат `--series-check`.
После четырёх H01-позиций состояние `adapter-required` указывает на следующий H02.
Все результаты сохраняют `partialScope:true`, `qualification:false`; общий исполнитель
остальных сценариев, единый допуск автономной серии и живая квалификация остаются открытыми.

## Технический адаптер H02

`comparison:h02` выполняет один H02 case для Legacy council и Temporal Activities
с настоящими файлами и фиксированными локальными RPC-ответами:

```sh
yarn comparison:h02 --plan
yarn comparison:h02 --self-test /absolute/new-output-directory
```

`--plan` ничего не создаёт. `--self-test` требует нового каталога, сохраняет исходные
материалы, первичные квитанции технического порта, пробы и общий отчёт. Собственные ответы
моделей и Temporal-службы не запускаются. Фикстуры не зависят от Vitest; программные
`runH02LegacyCase`/`runH02TemporalCase` принимают существующие порты и контексты владельцев.

В основном маршруте требование ставки 7 действует сразу: исходный pricing=5 имеет FAIL,
а logging/storage — полные PASS своих областей. После изменения только pricing на 7
повторяется его обзор; первичные ответы/evidence/turn остальных ролей сохраняются.
Четыре обзора различаются с LOAD: Legacy использует три сеанса и восемь локальных
`turn/start`, Temporal — четыре сеанса и восемь `turn/start`. Эти числа описывают технический
порт, а не модельный расход или экономию.

Отдельные пробы проверяют неизменный PASS, изменение зависимости после принятого pricing
7→8 с восстановлением 7, новую зависимость, общий scope, основание роли, сохранение
исходного FAIL, отсутствующую роль и неполную карту. Пробы планирования не создают новых
сеансов или ходов; ожидаемые отказы проверяются по конкретному правилу владельца.

Legacy использует реальные council/refresh/observe и `AppServerSessions`; Temporal —
`prepareReviewPlan`, scoped LOAD/answer, boundary/control STOP и `finishReview`.
Правила reuse не дублируются. Фиксированный pricing-ответ опирается на исходный
`checks.mjs`; неизменяемые материалы проверяются перед каждым обращением, результат
чекера при прежних байтах может использовать кеш. Поздняя отмена, включая cleanup,
оставляет unknown; STOP остаётся доступен. Остановка читателя не доказывает остановку
физического native-процесса.

Отчёт всегда содержит `nativeUsage:null`, `nativeAcceptance:false`, `qualification:false`,
`partialScope:true`. Прямой вызов Activities не квалифицирует `ReviewWorkflow`, SDK/replay
или реальный Codex. Результат не записывается как принятый H02-слот native-серии.
Отдельный [оператор H02](#оператор-h02-и-восемь-позиций-серии) имеет собственный допуск и
подключение к общему исполнителю; технический CLI и прежний H01 grant его не разрешают.

## Оператор H02 и восемь позиций серии

H02 имеет отдельные `comparison-h02-preparation`, `comparison-h02-operator` и
`comparison-h02-execution` документы. Запрос и первичный grant используют `executionVersion:2`;
H01-запрос, grant или guard не разрешают H02. Поля бюджета, профиля, корней и первичного
источника имеют те же строгие правила, что H01. Подготовка закрепляет настоящий source/build
inventory, пишет только новые draft JSON и не выдаёт разрешение.

```sh
yarn comparison:h02:operator --plan-preparation /absolute/preparation.json
yarn comparison:h02:operator --prepare /absolute/preparation.json
yarn comparison:h02:operator --plan /absolute/spec.json /absolute/request.json
```

Подготовка использует прежний формат закреплённой сборки `h01-workflow-build-artifacts`:
тот же `workflows/localTask.js` экспортирует `ReviewWorkflow` и `ControlledReaderWorkflow`.
H02 inventory дополнительно включает все `comparisonH02*.ts`. Команда
`yarn comparison:h02:operator --run SPEC.json REQUEST.json` требует собственного точного
H02-поручения из первичного чата. Разрешение локальной проверки его не заменяет.

Одна попытка использует общий с H01 внешний интервал, keeper и native guard: единую границу
времени с резервом, первичные квитанции каждого старта, проверку профиля/инструментов,
наблюдаемый расход и подтверждённую остановку процессов. Нового контроллера повторов нет.
H01-команды по умолчанию принимают только H01. Исторические документы и grants не меняются.

Legacy вызывает настоящий council через три отдельных `AppServerSessions`; исправленный
pricing использует свой прежний сеанс. Temporal выполняет два `ReviewWorkflow` через SDK
и существующий reader host: сначала три читателя, затем один pricing. Общая ведомость
резервирования ходов не обнуляется между обзорами. Обоим вариантам подаются одинаковые
материалы, правила, профили ролей и пять исходных процедур. STOP включает физическую
остановку каждого принадлежащего попытке native-порта; поздняя отмена остаётся UNKNOWN.

Манифест, запрос шага и состояние серии сохраняют прежние `comparison-h01-series*` kinds.
Версия 1 исполняет четыре H01-позиции. `schemaVersion:2` исполняет первые восемь позиций
того же расписания 24: четыре H01, затем четыре H02 с симметричным порядком вариантов.
Каждому шагу нужны свой scenario-bound spec/request и отдельный точный grant. Общий cap,
время, pending, writer lock, неизменность входов и запрет продолжения после FAIL/UNKNOWN
действуют на все восемь шагов. После H02 статус `adapter-required` указывает H03.

Первичная сверка H02 проверяет начальный pricing FAIL, logging/storage PASS, единственный
новый pricing-обзор, сохранённые ответы остальных ролей, содержимое отрицательных проб,
цепочку operator → owned → child, фактический расход и STOP. Temporal дополнительно
связывает SDK-истории обоих обзоров и дочерних читателей с закреплёнными входами/результатами.
Восемь `turn/start` не приравниваются к восьми модельным ответам: ответы и токены читаются
из первичных журналов. Неизвестные суммы остаются null, подтверждённая нижняя граница сохраняется.

Реализация и unit-проверки не являются живой квалификацией Codex/SDK или полной серией.
Результаты сохраняют `partialScope:true`, `qualification:false`; native-серия требует
своих ещё не выданных допусков. Установочная приёмка остаётся в конце T5 перед T6.

## Оператор H03 и двенадцать позиций серии

H03 продолжает незавершённую задачу после настоящего `thread/compact/start` в том же
native-сеансе. У него отдельные `comparison-h03-preparation`, `comparison-h03-operator`,
`comparison-h03-execution` и точный H03 grant версии исполнения 2; H01/H02 разрешения
не применяются. Общие interval, keeper, guard, caps и физический STOP сохраняются.

```sh
yarn comparison:h03:operator --plan-preparation /absolute/preparation.json
yarn comparison:h03:operator --prepare /absolute/preparation.json
yarn comparison:h03:operator --plan /absolute/spec.json /absolute/request.json
```

До исполнения candidate из текущего первичного чата с точным H03 grant требуется отдельно
завершить `yarn comparison:h03:operator --issue-recovery REQUEST.json`. Команда использует
существующий native authority и печатает notices для паузы и возобновления; они получают
силу только как настоящий завершённый tool result того же root-чата. Она не пишет transcript,
не запускает модель и не разрешает другие действия. Сам `--run SPEC.json REQUEST.json`
перечитывает первичные notices: начальный `initial-grant` не подменяет человеческое resume.

Legacy сохраняет настоящий SQLite checkpoint с открытым F-01 и pending, проверяет четыре
непригодных кратких контекста и возвращается к полному наблюдаемому LOAD. Temporal исполняет
существующий `ControlledReaderWorkflow`: первый LOAD, compact, отказ прежнего LOAD, пауза
ревизии 0, возобновление ревизии 1/attempt 1, свежий LOAD и ответ в прежнем session.
Его pending принадлежит настоящему effect journal. UNKNOWN по-прежнему запрещает зависимое
product-действие; успешное восстановление чтения этого запрета не снимает.

Оба LOAD читают обязательный `evidence/initial-context.json` с точными первичными байтами,
ссылками и хешами исходных FAIL/pending. Отдельные пробы проверяют пропущенное правило,
устаревший источник, неверную роль и новое действие через существующих владельцев допуска.
Проверяющий код сверяет их основания и ошибки, полный состав правил, наблюдаемое чтение,
первичные SDK-истории и неизменность исходного незавершённого состояния.

Сжатие имеет отдельное резервирование в общем `maxManagedStarts`. Его ACK не является
`turn.id` или модельным ответом. Перед reservation требуется native accounting barrier:
предыдущий ход завершён, его первичный расход уже записан. Новый `compacted` и отдельные
`token_usage_record` связываются с диапазоном до следующего `task_started`; отсутствие
стоимости оставляет UNKNOWN. Неподдерживаемая операция остаётся NOT RUN. Потеря ответа
не создаёт разрешения на второй compact. Один владелец диапазона используется guard и
первичной сверкой серии, без второго алгоритма стоимости.

Версия 3 прежних manifest/state/step kinds `comparison-h01-series*` поддерживает первые
двенадцать позиций расписания 24: H01/H02/H03, по четыре позиции каждого. Версии 1 и 2
сохраняют строгие срезы четырёх и восьми шагов. После H03 требуется адаптер H04; pending,
UNKNOWN, неполные расходы или STOP блокируют следующий шаг. Локальные unit-подмены не
засчитываются как настоящий compact или принятый слот живой серии. Установочная приёмка
остаётся в конце T5 перед T6; `partialScope:true`, `qualification:false` сохраняются.

## Оператор H04 и шестнадцать позиций серии

H04 проверяет ожидание длительной операции внутри одного native-хода. Операция длится
не менее 35000 мс, сохраняет шесть промежуточных записей и первичный результат; применение
выполняется ровно один раз. Прежний `comparison:h04` остаётся отдельным model-free helper:
его успешный результат не доказывает ожидание моделью.

Отдельный оператор использует общий interval, guard, keeper, расходы и STOP:

```sh
yarn comparison:h04:operator --plan-preparation INPUT.json
yarn comparison:h04:operator --prepare INPUT.json
yarn comparison:h04:operator --plan SPEC.json REQUEST.json
yarn comparison:h04:operator --run SPEC.json REQUEST.json
```

Планирование и подготовка не запускают модели или службу. Исполнение требует собственного
точного H04-поручения; H01/H02/H03 grants не подходят. Новые запросы и отчёты используют
`comparison-h04-*`, `executionVersion:2` и закреплённые источники. Общий предел времени
включает подготовку, ожидание и остановку; внутри операции он не начинается заново.

Модель сохраняет права только на чтение. Она запускает закреплённый Node waiter с быстрым
возвратом идентификатора процесса и делает ровно один блокирующий `write_stdin` этого
процесса. Waiter только читает запрос и первичный результат; он не запускает операцию,
не применяет эффект и не требует TSX или записи кеша. Операция остаётся у host owner
и начинается после первичного события запуска точной команды ожидания. Legacy использует
существующий `waitCouncilProgress`, Temporal — Workflow/Activity на уже принадлежащей
оператору службе. Второй сервер для операции не создаётся.

Первичная сверка связывает исходный native-ход, вызовы и ответы инструментов, идентификатор
процесса, terminal output и квитанции операции/применения. Применение разрешается только
после подтверждения полного native-ожидания и STOP. Самодекларация `waitCalls:1`
или ответ модели не заменяют эту цепочку. Повторный опрос, другой ход, чужой результат,
неподтверждённые расходы или STOP оставляют попытку заблокированной. Недоступная операция
остаётся NOT RUN; UNKNOWN не разрешает повтор.

Версия 4 прежних `comparison-h01-series*` kinds исполняет первые шестнадцать позиций
неизменного расписания 24: H01/H02/H03/H04, по четыре позиции каждого. Версии 1–3 сохраняют
свои прежние границы. Следующий требуемый адаптер — H05. Все шаги имеют собственные grants;
общие caps, pending и запрет продолжения после FAIL/UNKNOWN сохраняются. Unit-подмены
не являются живой квалификацией. Полная серия и установленная приёмка остаются открытыми;
установочная приёмка выполняется в конце T5 перед T6.

## Оператор H05 и двадцать позиций серии

H05 проверяет ожидание уже известного native-хода: завершение до подписки, потерянное,
дублированное и переставленное уведомление, восстановление после перезапуска, смену
поколения владельца и отказ позднему результату после отмены. Один исходный `create/send`
создаёт ход; восстановление читает его первичный результат без нового модельного старта.
Исходный F-01 сохраняется во всех пробах.

```sh
yarn comparison:h05:operator --plan-preparation PREPARATION.json
yarn comparison:h05:operator --prepare PREPARATION.json
yarn comparison:h05:operator --plan SPEC.json REQUEST.json
yarn comparison:h05:operator --run SPEC.json REQUEST.json
```

Подготовка не запускает модели или службу. Исполнение требует отдельного точного H05 grant
и `comparison-h05-*` входов с `executionVersion:2`; допуски H01–H04 не подходят.
Для H05 исходное `identity.generation` должно быть не меньше 2: проба старого поколения
использует допустимое значение на единицу меньше. При перезапуске поколение не меняется;
отмена проходит через действующего владельца состояния и блокирует позднее применение.

Legacy и Temporal используют общего владельца семантики ожидания и существующие переходы
`AssignmentLocalRuns`. Это локальный checkpoint сценария, без переноса полномочий живых задач.
Temporal запускает Workflow/Activity на службе внешнего оператора; восстановление получает
тот же Workflow/run, останавливает прежний Worker и создаёт новый. Дополнительный сервер
и повторный native `create/send` не требуются. Общий срок включает подготовку и очистку.

Native transport сохраняет первичные отправленные и принятые строки в отдельный неизменяемый
журнал. Пробы доставки ссылаются на исходные строки и ведут собственные квитанции вмешательств;
нативная история не переписывается. Перезапуск подтверждает остановку старого процесса,
точный префикс истории и исходного незакрытого участника. Итоговый STOP сохраняет обе
физические остановки. Неизвестные расходы или STOP запрещают восстановление.

Перед сохранением ответа повторно проверяются отмена, срок, закреплённые входы, первичные
результаты и точные task/owner/generation. Первичная сверка серии проверяет те же доказательства
и дополнительно связывает их с внешним запросом, профилем и обязательными процедурами.

Версия 5 прежних `comparison-h01-series*` kinds исполняет первые двадцать позиций расписания
24: H01–H05, по четыре позиции каждого сценария. Версии 1–4, общие caps, pending/lock
и блокировка после FAIL/UNKNOWN сохраняются.
Unit-подмены SDK/native не подтверждают живое восстановление или сравнительную экономию;
`partialScope:true`, `qualification:false` сохраняются. Установочная приёмка остаётся
в конце T5 перед T6.

## Оператор H06 и двадцать четыре позиции серии

Версия 6 `comparison:series` добавляет четыре слота H06 в том же порядке пар. Слоты
закрепляют замороженную редакцию H06/2 с критерием сохранения владельца при долгом этапе.
В Legacy проверяется renew до исходного срока аренды. В Temporal проверяются сохраняемое
состояние той же логической задачи и отложенный эффект при замене Worker. Исторический
критерий `lease-renewed` остаётся в исходном расписании readiness и прежнем офлайн-журнале.

Живая приёмка H06 проходит в этих четырёх позициях: по два исполнения Legacy и Temporal
в установленном порядке. Запрос каждого исполнения заранее закрепляет критерии приёмки,
источники и пределы. Восстановление, физический STOP и сверка полного расхода проверяются
по тем же первичным квитанциям, по которым считаются сравнительные показатели.

```sh
yarn comparison:h06:operator --plan SPEC.json REQUEST.json
yarn comparison:h06:operator --run SPEC.json REQUEST.json
yarn comparison:series --plan MANIFEST.json
yarn comparison:series --step STEP.json
```

Spec `comparison-h06-operator` версии `schemaVersion:1` содержит pin `package` готового
манифеста H06 и отдельный новый `evidenceRoot` оператора. Запрос `comparison-h06-execution`
той же версии закрепляет `material`, `criteria`, `profile` и `runtime`. Оба используют
пары `{locator,hash}`. ID операции, стимул, пределы и native-корни определяет закреплённый
пакет. Все четыре H06-слота используют одинаковую длительность долгого этапа и общее
расписание. Каждый слот выделяет собственные корни и отдельный одноразовый допуск.
Native runtime закрепляет общий инвентарь серии, исполняемые модули `comparisonH06*`
и `comparisonH04Contract.ts`.

Оператор использует пакет `h06-autonomous-recovery/3` в Legacy и
`h06-autonomous-temporal/3` в Temporal. Legacy ожидает настоящие делегированные доставки
из исходного чата. Temporal использует исходный допуск для стадий восстановления и
общих абсолютных сроков службы и Worker. Подготовка не принимает допуск и не запускает
сценарий. Шаг серии сохраняет `pending` до вызова оператора и занимает часть общего лимита.

Сразу после H06 журнал сохраняет исходный `UNKNOWN`, пока корневой ход и внешние участники
не закрыли свои первичные журналы. Затем `yarn comparison:series --reconcile COMMAND.json`
сверяет расходы без повторного исполнения H06. `COMMAND.json` содержит
`{kind:"comparison-h01-series-reconcile",schemaVersion:6,manifest,runId,previousState,record,settlement}`.
`manifest`, `previousState`, `record` и `settlement` — pins манифеста, текущего `state.json`,
исходного `record-<index>.json` и пакета сверки.

Пакет сверки имеет форму `{kind:"comparison-h06-series-accounting/1",operator,through}`.
`operator` — pin `record.operator.receipt`. Каждый элемент `through` содержит `session`,
`turn` и `source:{locator,hash}` точной terminal-строки либо последней строки первичного
расхода того же хода после terminal. Locator оканчивается на `#L<N>`. Конечные границы
нужны для исходного хода координатора, связанных повторов после нехватки мощности и всех
подтверждённых делегированных ходов Legacy. Состав участников выводится из допуска,
журнала стартов и фактических доставок. Поздний расход за пределами pin, чужой профиль,
повтор участника в серии и незакрытый ход оставляют исход `UNKNOWN`.

Для положительной сверки нативный журнал должен подтверждать запуск закреплённой команды
шага и исчерпывающий список внешних действий. H06-координатор запускает закреплённый Node
с `--import`, закреплённым загрузчиком `tsx`, `tests/comparisonH01Series.ts`, `--step` и
абсолютным путём `STEP.json`. Аргументы заключаются по одному в одинарные кавычки. В
Codex команда записывается как один вызов `text(await tools.exec_command({...}));` с JSON
параметрами `cmd`, `workdir`, `shell:"/bin/sh"` и `login:false`. Тот же формат применяется
для точных команд Legacy `--admit` и `--settle`, делегированных команд и их `read-chat`
из пакета. Чтение абсолютного файла через `/bin/cat`, ожидание существующих ходов и опрос
терминала без ввода допустимы. Дополнительный запуск, неизвестный инструмент или команда
в произвольном скрипте оставляют полноту расходов неподтверждённой. После записи исходного
`UNKNOWN` команда H06 завершается со статусом `blocked` и кодом 1. Первичное наблюдение
связывает этот выход с короткой строкой `comparison-h06-step-record:<hash>`.
Сверка опирается на закреплённую хостовую установку и её нативный журнал.

Успешная сверка включает F-01, сохранение владельца, восстановление, физические STOP
управляемых процессов, первичный расход и фактические профили. Внешние ходы входят в
предел стартов H06 и серии. Полное время серии включает ожидание сверки. Результат
сохраняется отдельным неизменяемым `reconciliation-<index>.json`; исходный `UNKNOWN` и
известный расход остаются в записи попытки. При подтверждённом перерасходе сохраняется
`FAIL`. После успешной сверки в пределах общего бюджета `--status` возвращает следующий
слот. `partialScope:true` и `qualification:false` сохраняются для всех локальных результатов.

## Порядок и бюджет до серии

Выбранные задачи и число повторов определяются до старта. Для двух пар порядок симметричный:
baseline/candidate, затем candidate/baseline; фактический порядок и причины отклонений сохраняются.
Холодный и прогретый cache не смешиваются. Повторные проверки запускаются из-за изменения,
ошибки или новой неизвестности и входят в затраты. Параллельная посторонняя нагрузка исключается
либо отмечается как ограничение, запрещающее вывод о скорости.

Перед первым RPC обязательны отдельное действующее поручение и заполненные значения:

- series ID, manifest/hash, источник человеческого поручения и срок действия;
- разрешённые model/effort, число задач/пар, все основные/советующие/проверяющие роли;
- общий предел модельных стартов, токенов, полного времени и денег, если есть подтверждённый тариф;
  пределы отдельных запусков и доля резерва на остановку/сверку;
- правило предупреждения/остановки до исчерпания и запрет автоматического повторного старта;
- какие действия разрешены при известном FAIL, unknown, потере usage или изменении исходников;
- кто принимает качество и кто вправе принять компромисс времени/стоимости.

**Текущий бюджет Temporal comparison: не выделен; разрешённых стартов серии — 0.**
Нельзя переносить остаток квалификационных пакетов, бюджет другого чата или старой comparison-серии.
Подготовка материалов не создаёт финансовых полномочий и не включает фоновую работу.

## Подготовка H06 и порядок проверок

Для H06 используется один версионируемый вход подготовки:

```sh
yarn comparison:h06:package --prepare /absolute/spec.json
yarn comparison:h06:package --check /absolute/manifest.json
```

`--prepare` и `--check` выводят результат, не запускают сценарий и не принимают живой допуск.
Подготовка закрепляет источники, runtime и разрешённые действия пакета; сверка обнаруживает
изменённые входы до дорогого исполнения. Действия `start`, `warm`, `cold`, `deliver` и
делегирование Temporal принадлежат закреплённому runtime, а не новой произвольной команде
оператора. Передача первичного допуска остаётся отдельным действием: подготовка не потребляет
и не расширяет его, использованный допуск не переносится на изменившийся пакет.

Пакет поддерживает три явно различающихся профиля: `h06-autonomous-recovery/3` для Legacy,
`h06-native-temporal/2` для ручного Temporal и `h06-autonomous-temporal/3` для автономного
Temporal. Последний выдаёт одно предложение `comparison-h06-temporal-autonomous-grant/3`:
общий таймер и резерв остановки включают сервер, оба восстановления и завершение. Его
производные команды используют `origin: initial-grant`; пользовательские сообщения этапов
не имитируются. [Отдельное решение и границы](../comparison/revisions/autonomous-recovery-v3/README.md#автономный-temporal-с-отдельным-допуском)
не меняют ручную приёмку или общий источник полномочий рабочих задач.

Для автономного Temporal spec содержит `{kind,profile,run}`, где `kind` равен
`comparison-h06-package/1`, `profile` — `h06-autonomous-temporal/3`, а `run` — pin JSON
`comparison-h06-temporal-autonomous-run/3`. Этот JSON закрепляет `authority` и канонические
Worker `node/tsx/entry`. Файл authority имеет вид
`{kind:"comparison-h06-temporal-autonomous/3",attempt,budget}`: `attempt` — pin исходного
запроса, `budget` — проверяемый предел старой обвязки сервера. Он входит в setup hash;
действующие общие часы и лимиты всегда берутся из `attempt.budget`, без нового отсчёта
при старте Worker. Команда `--run` в manifest выбирает маршрут по закреплённой версии.

Сквозной `comparisonH06TemporalAutonomous.integration.test.ts` использует настоящий тестовый

## Первичный учёт

Сохранять общий wall/monotonic interval и все попытки: подготовку, planning, LOAD, writer,
проверки, приёмку, исправления, арбитраж, аудит, восстановление и shutdown. Длительности
параллельных участников не складываются вместо полного времени. Используются реальные
монотонные часы; иной clock ID после перезапуска или потеря границы оставляет время unknown.

Для каждого model/session/turn хранить первичный источник, точные границы/hash журнала,
подтверждённые effective model/effort, operation ID, исход и usage. Уникальные первичные
квитанции учитываются один раз. Input без кэша, cached input и output показываются отдельно;
reasoning повторно не добавляется к output. Сжатие, child-аудиторы, вспомогательные роли,
неудачные create/send, retry и проверки полноты включаются. Неизвестное значение — null,
оно не заменяется нулём или оценкой размера файлов.

Бюджет проверяется до каждой операции и в ожидании. Unknown запрещает новые действия до
первичной сверки; Ack interrupt не доказывает stop. Ошибочный ответ модели и ошибка стенда
различаются, сохраняются вместе с последующими исправлениями. Нельзя очищать исходный FAIL
после удачного повторного исполнения. Денежная стоимость вычисляется только по подтверждённому
применимому тарифу; иначе публикуются токены и неизвестная денежная сумма.

## Приёмка результата

Сначала оценить обнаруженные и пропущенные дефекты, сохранность данных, соблюдение scope,
корректность RESULT/DONE, остановку writers и полноту доказательств. Регрессия качества
запрещает положительный вывод об эффективности. Необнаруженный обязательный дефект сохраняется
в оценке даже после исправления.

Только для сопоставимых принятых задач с полными часами и расходами вычислять разницу полного
времени и затрат, показывая каждую пару и разброс. Нулевая/неизвестная база не даёт процентного
снижения. Два повтора не доказывают универсальной эффективности. Если скорость не улучшена,
включение требует отдельного решения пользователя о допустимом компромиссе; выбор Temporal
сам по себе не доказывает экономию.

Отчёт содержит manifest, начальный бюджет и фактическое потребление, все исходы/попытки,
первичные evidence/usage refs, качество, время, расходы, неизвестности и итоговый вывод.
Принятие методики, installed-consumer smoke и проверка структуры отчёта не закрывают T5.

Полный installed-consumer SDK-стенд из `installed-full-consumers.mjs` также не является
comparison-серией: он выполняет конкретные M1 с намеренной инъекцией дефекта, детерминированными
ролями и реальными проверками приложения. Два игровых validate принадлежат candidate/integrated
одной задачи; их разница не доказывает ускорение runtime. Все расходы установки, SDK, checker,
остановки и replay входят в его собственный журнал. Бюджет модельного сравнения остаётся 0,
а его будущий manifest должен отдельно фиксировать источники приложения, runtime tarball,
exact overlay, доверенный checker и одинаковую cache policy обоих сравниваемых вариантов.

## Одна попытка H-01 через настоящий адаптер

Новый контур репозитория `tests/comparisonH01.ts` готовит и исполняет один вариант одной
попытки. `executionVersion:2`, `kind:"comparison-h01-execution"`: baseline использует
`comparisonSession` прежнего движка, candidate — native Temporal assembly. Это отдельная
версия исполнения; прежние v1 suite/session/report и команда readiness сохраняются.
Полная парная серия, H-03–H-06 и окончательная квалификация T5 остаются следующими этапами.

Для отдельного живого восстановления Legacy пользователь выбрал
[автономную приёмку H06/3](../comparison/revisions/autonomous-recovery-v3/README.md).
Прямой первичный `/3` допуск связывает бюджет, автономный профиль и текущий пакет.
Для переноса прежнего `/2` сохраняется отдельное человеческое решение о новом режиме.
Оператор самостоятельно доставляет LOAD, PAUSE и RESUME; их подлинные
квитанции проверяются отдельно от человеческого происхождения исходного разрешения.
Профиль `/3` требует физических STOP, тёплого и холодного восстановления и интегрированного
завершающего Writer. Он сохраняет ручной `/2` без переинтерпретации и не расширяет полномочия
общего runtime. Ни отдельная успешная фаза, ни тесты не закрывают живую приёмку.

```sh
yarn --silent comparison:h01 --plan /absolute/request.json
```

`--plan` только читает закреплённые входы и показывает точный первичный JSON-допуск для
requestHash, opId, variant и численного бюджета. Для будущего `--run REQUEST` нужен
отдельный прямой пользовательский допуск в текущем чате с сохранённой первичной строкой
и hash. Продолжение работы, цитата JSON, ответ с обёрткой карточки вопроса, произвольный
файл `author:user` и разрешение neutral не дают права запускать H-01. Delivery source/hash
и текущий turnId исключены из самоссылки requestHash; scope, входы и бюджет закреплены.
Оператор не создаёт пользовательское разрешение вместо человека.

Request закрепляет material, criteria, profile, bootstrap, фактические runtime inputs и
пять непересекающихся новых корней: workspace, evidence, artifacts, host и state. Общий
`hostRoot/turn-credits` и `maxManagedStarts` действуют для обоих путей и независимого совета.
Legacy snapshot получает заранее закреплённый instrumentation overlay; три существующих
CLI callsite проверяются до замены. Temporal подтверждает уже выданный host credit без
повторного списания. Пропущенный stage и неподдерживаемая команда останавливаются до
dispatch; старый legacy маршрут без optional controls сохраняет прежнее поведение.

`maxManagedStarts` ограничивает управляемые starts, а не весь аккаунт провайдера.
Native builtins и неуправляемые участники запрещены профилем; их обнаружение оставляет
unknown. `maxInputUncached` и `maxOutput` — отсечки по наблюдённому расходу завершённых
ответов, не гарантированная верхняя граница токенов или денег внутри активного ответа.
Подтверждённый активный родитель может создавать разрешённые вложенные роли без ожидания
своего завершения; его ещё неизвестный расход остаётся null. Потерянное подтверждение,
осиротевшая резервация и неизвестный итоговый расход запрещают дальнейшие эффекты.

Один монотонный срок начинается до подготовки попытки и включает проверки, общий
независимый совет, остановку и экспорт. Часть срока резервируется для остановки.
Граница измерения стоит после содержательного экспорта и перед записью завершающей
квитанции часов. Её ввод-вывод, вывод CLI и доставка оператору следуют после этой границы
и указаны как неподтверждённая часть полного внешнего измерения. Сохранённый отчёт и возвращаемое тело
имеют одинаковые outcome/timing/elapsed. Это ещё не полное операторское время серии.
Отдельный Keeper владеет дочерним процессом и его потомками; зависший SDK/shutdown,
поздний результат или принудительная остановка не превращаются в подтверждённый успех.
Предоставленный оператором Server не принадлежит Keeper. Общая подготовка и внешний
предварительно запущенный Server учитываются отдельно как ещё неподтверждённые условия.

Оба пути проходят общий checker и независимый читающий совет. Старый путь дополнительно
требует собственные первичные task/run/RESULT/DONE: ответ внешней модели или прямая правка
файла не подтверждают исполнение прежним движком. Внутренняя Temporal-приёмка
сохраняется дополнительно: один `handle.result()` не заменяет общий verdict. Сохраняются
исходные FAIL, unknown, сырые журналы, расходы и подтверждения остановки. Отчёт остаётся
`partialScope:true`, `qualification:false`; неизвестные расходы и время — null.

Контур не устанавливает зависимости и не запускает Temporal Server. Для настоящего
исполнения нужны закреплённый native binary/profile, доступный localhost Server, проверенные
pins и собственный операторский допуск с бюджетом. Текущие проверки с подставным провайдером
и файловыми фикстурами не являются модельным сравнением или доказательством эффективности.
Бюджет настоящего H-01 сейчас не выделен; разрешённых модельных стартов — 0.

## Закреплённая подготовка и внешний оператор H-01

```sh
yarn --silent comparison:h01:prepare --plan /absolute/preparation.json
yarn --silent comparison:h01:prepare --prepare /absolute/preparation.json
yarn --silent comparison:h01:operator --plan /absolute/operator.json /absolute/draft-request.json
```

Подготовитель использует один общий сборщик runtime inventory с исполнителем H-01.
`--plan` только читает; `--prepare` создаёт новый каталог JSON-снимков. Рабочие каталоги,
модель, бинарник, Worker, сервер и разрешение не создаются. Подготовка всегда имеет
`mayRun:false`, `qualification:false`, `authorizationIssued:false`, `allowedModelStarts:0`.
Числа `budget` — предложенные пределы, пока нет первичного человеческого согласия.

Вход задаёт точный текущий runtime root, primary root текущего чата, новый output root,
одинаковый профиль, текущий Node с hash, identity, численный бюджет и два разных opId/runBase.
Candidate дополнительно закрепляет cached Temporal CLI, три отдельных `127.0.0.1` endpoints,
namespace `default`, taskQueue и build-manifest. Свежая стандартная сборка экспортирует только
JS-замыкание Workflow; каждый модуль закреплён в runtime.files. `workflowsPath` — его JS-entry,
а CJS webpack bundle служит доказательством сборки и не подставляется вместо CLI или entry.
Это source assembly с имеющимися зависимостями, не установленный v6 или новый standalone.

Static operator spec не содержит requestRef/hash или author. Сначала spec входит по точной
ссылке в runtime.files, затем считаются runtime/requestHash и текст предполагаемого согласия.
Этим исключается самоссылка. Оба варианта имеют одинаковые material/criteria/profile/budget;
это две подготовленные попытки, без автоматического запуска пары или серии.

Для выполнения выбранного варианта нужен точный первичный JSON из плана в обычном сообщении
пользователя текущего чата. Цитата, JSON в файле, ответ с обёрткой карточки или generic continue
его не заменяют. Допустим только канонический текст либо он же с одним нативным LF в конце;
trim и снятие обёрток не выполняются, raw source/hash остаются исходными. После такого сообщения можно привязать только delivery-поля
`authorization.source`, `anchor.turn_id` и `authorization.requestHash` к фактическому источнику,
сохранить новый bound request и независимо сверить неизменный requestHash. Разрешение не
пишется от имени пользователя. `--run` отклоняет незаполненный черновик до внешних действий.

Будущий интерфейс после конкретного допуска:

```sh
yarn --silent comparison:h01:operator --run /absolute/operator.json /absolute/bound-request.json
```

Оператор сверяет primary source, Node identity, все pins, полный runtime namespace и свежие
пути до exec. Node запускает только фиксированный `--import tsx` и прежний Common CLI;
произвольных команд и preload нет. В PATH присутствует каталог именно закреплённого Node
и фиксированные системные каталоги; произвольный PATH родителя не наследуется. RunBase — новый общий контейнер, в нём пять корней H-01
и отдельный шестой корень оператора. После согласия создаются только принадлежащие контейнеру
родители; пять корней H-01 создаёт сам Common CLI. Старые данные не используются как запуск.

Baseline не поднимает Temporal. Candidate запускает один закреплённый CLI `start-dev` без UI
с новым SQLite. Три public endpoints заданы явно; внутренние RPC могут использовать временные
порты того же loopback. Metrics и внутренний RPC используют FrontendIP в
[исходнике CLI v1.9.1](https://github.com/temporalio/cli/blob/v1.9.1/internal/devserver/server.go).
Подготовка не подтверждает фактическую доступность портов или службу. До H-01 проверяются
свободные endpoints и принадлежность frontend listener процессу оператора.

Внешний монотонный interval начинается до authority/preparation/server и включает H-01,
его результат, известные остановки и содержательный экспорт. Из исходных maxElapsedMs
выделяется stop reserve, срок не расширяется после задержек. Финальная clock receipt и
доставка CLI находятся вне измеренной границы; физическое прерывание зависшего синхронного
FS-ввода остаётся неподтверждённым. Late/cancel/forced stop, неизвестные listeners, повреждённый
экспорт или неизвестные итоговые метрики не становятся accepted. Исходные FAIL и расходы
сохраняются. Все корни остаются для разбора; копируется inner evidence, а не всё хранилище.
Пара, серия, физический runtime/stop и окончательная T5 требуют настоящих отдельных прогонов.
