# Agent Workflow

`@krivega/agent-workflow` подключает проект к процессу работы агентов через Codex и Temporal.
Пакет содержит CLI, SDK, общие навыки, процедуры и базовые профили совета. Проект хранит
собственные правила, роли, карточки и команды проверки в Git.

## Установка и проверки

- **Первый хост.** Владелец [готовит сервер и службу Worker](#3-подготовьте-рабочий-хост).
  Для регистрации первой рабочей копии понадобится её дескриптор из шага 2.
- **Новый репозиторий на действующем хосте.** Выполните шаги 1 и 2, передайте владельцу
  дескриптор и ID чата проекта. Владелец добавляет регистрацию и перезапускает только Worker.
  Для всех репозиториев остаются общими сервер Temporal и том PostgreSQL.

### 1. Подготовьте репозиторий

Откройте терминал в корне Git-репозитория. Для приведённых команд нужны npm и Node.js
22 начиная с 22.22.2, 24 начиная с 24.15.0 либо 26 и выше. Проверьте версии:

```sh
node --version
npm --version
```

В корневом `package.json` должны быть имя проекта и рабочая команда `validate` или
`test`. Если есть обе, `init` выберет `validate`. Язык приложения может быть любым.
Например, в Python-репозитории без `package.json` создайте такой файл и выполните
`npm test`, чтобы убедиться, что команда находит и запускает ваши тесты:

```json
{
  "name": "my-python-project",
  "private": true,
  "scripts": { "test": "python3 -m unittest discover" }
}
```

Если в проекте уже есть манифест и рабочая проверка, используйте их. Примеры далее
даны для npm. В репозитории с Yarn используйте его для установки и обновления зависимостей.

### 2. Установите пакет и проверьте настройки

Пример для опубликованной предварительной версии:

```sh
npm install --save-dev --save-exact @krivega/agent-workflow@0.1.3-rc.2
npm exec -- agent-workflow init
npm exec -- agent-workflow doctor
git status --short
```

При первом подключении проверьте созданные файлы:

| Путь                                         | Что настроить                                                                                   |
| -------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `AGENTS.md`                                  | Правила работы в этом репозитории. Существующий файл сохраняется.                               |
| `tools/agent-workflow/project/temporal.json` | Идентификаторы проекта и рабочей копии, расположение карточек, роли и имена команд проверки.    |
| `tasks/`                                     | Каталог карточек по умолчанию. Добавьте сюда первую карточку с целью и проверяемым результатом. |
| `tools/agent-workflow/roles/architect.md`    | Начальный профиль рецензента. Адаптируйте его к проекту.                                        |
| `.agents/skills/agent-workflow/SKILL.md`     | Инструкция для Codex, связывающая проект с навыком установленного пакета.                       |

Повторный `init` сохраняет проектные изменения. После правок снова выполните `doctor`.
При успехе он выведет JSON с полями `version`, `descriptor`, `skill` и `projectId`.
Сохраните в Git проверенные файлы проекта, `package.json` и lock-файл. Если `init`
просит команду проверки, добавьте в `scripts` реальную команду и повторите запуск.
На этом подключение репозитория завершено. Доступность сервера и Worker проверяется отдельно.

### 3. Подготовьте рабочий хост

Этот раздел предназначен для человека, который обслуживает исполнение задач. В первом
профиле проекта один доверенный хост macOS обслуживает несколько репозиториев. Владелец один раз
готовит сервер и пользовательскую службу Worker, затем добавляет регистрации проектов.

1. **Один раз подготовьте каталог хоста.** В версии с комплектом T7 скопируйте
   [compose.yaml](examples/temporal-host/compose.yaml) из установленного пакета
   (`node_modules/@krivega/agent-workflow/examples/temporal-host/`) в приватный каталог
   вне рабочих копий. Здесь и далее запускайте Compose из этого каталога. Создайте
   файл `.env` с правами `600`, сохраните в нём `POSTGRES_PASSWORD` со случайным
   значением (например, выводом `openssl rand -hex 32`). Для другого namespace добавьте
   `TEMPORAL_NAMESPACE`; по умолчанию используется `agent-workflow`.
2. **Запустите и проверьте сервер.** Команда `docker compose up -d --wait` поднимает
   PostgreSQL во внутренней сети и Temporal на `127.0.0.1:7233`. Образ Temporal готовит
   базы `temporal` и `temporal_visibility`, затем регистрирует namespace. Проверка
   готовности ожидает ответа на запрос об этом namespace. Для сервера на TNAS сначала
   настройте [SSH-туннель на Mac](docs/temporal-sdk.md#соединение-mac-с-сервером-на-tnas). С Mac проверьте доступность
   командой `temporal operator cluster health --address 127.0.0.1:7233`.
   Для остановки используйте `docker compose down`, для повторного запуска —
   `docker compose up -d --wait` с тем же именем проекта Compose. Именованный том
   сохраняет PostgreSQL между запусками. Перед обновлением сделайте независимую копию,
   проверьте допустимый путь обновления обеих служб и замените файл Compose версией
   из выбранного пакета. Для второго репозитория используйте уже работающий сервер.
3. **Зарегистрируйте репозиторий.** В приватной регистрации клиента укажите адрес
   `127.0.0.1:7233`, namespace из Compose (по умолчанию `agent-workflow`) и основную очередь.
   Владелец связывает дескриптор проекта с рабочей копией, каталогом артефактов,
   владельцем и разрешёнными командами. Каждому репозиторию нужны свой `projectId`,
   абсолютные пути рабочей копии и каталога артефактов. Добавьте в массив `projects`
   файла `worker.json` запись с путём `file` к регистрации и `threadId` чата этого проекта.
   Сохраните прежние записи. На действующем хосте дождитесь окончания задач, проверьте
   настройки и перезапустите службу по инструкции ниже. Сверьте число проектов в ответе
   `--check` и PID новой службы с обработчиками очередей.
4. **Подготовьте пользовательскую службу macOS.** Закрепите установку пакета на Mac,
   заполните `worker.json` в приватном каталоге хоста и создайте LaunchAgent по
   [инструкции запуска Worker](docs/temporal-sdk.md#локальная-служба-worker-на-macos).
   Для T7 укажите в `worker.json` CLI из приложения версии `0.171.0-alpha.13` и профиль
   `gpt-6.2-sol/high`. Каталог зависит от исполняемого файла в `codexBinary`.
   Служба обслуживает основную очередь и очередь с суффиксом `.control`.
5. **Подготовьте независимую копию** перед обновлением и проверьте её восстановлением
   по [порядку резервного копирования](#резервная-копия-и-проверка-восстановления).

### 4. Проведите первую задачу

После подготовки хоста откройте рабочую копию в Codex. Укажите карточку явно, например:
«Выполни карточку `tasks/first-task.md` через agent-workflow». Для первой проверки
выберите небольшую задачу с однозначным результатом и короткой командой проверки.

В текущей реализации маршрута Temporal владелец хоста включает для проекта политику
назначения версии 2. В чате подготавливается вход версии 12 с планом, проверками и
допуском, привязанным к исходному поручению. Команда запуска из корня репозитория
использует этот вход и приватную регистрацию Worker. Когда вход сохранён как
`input12.json`, а переменная `AW_REGISTRATION` содержит выданный владельцем абсолютный
путь к файлу регистрации, выполните:

```sh
npm exec -- agent-workflow task-chat start --temporal-input input12.json --temporal-registration "$AW_REGISTRATION"
```

Оба файла должен читать только их владелец. Подготовка допуска и формат регистрации
описаны в [инструкции запуска](CURRENT-CHAT.md#запуск-через-temporal).

Ответ `accepted` с `workflowId` означает, что Temporal принял задачу. Для сквозной
проверки дождитесь `DONE` и сверьте результат в рабочей копии. При неизвестном исходе
сохраните идентификатор и квитанцию для проверки текущего запуска. Новый идентификатор
может привести к повторному исполнению.

### 5. Обновляйте проект и хост отдельно

В отдельной ветке обновите зависимость до выбранной точной версии и её lock-файл.
Выполните `doctor` и ту же команду `validate` или `test`, что использует проект.
Проверьте изменения правил, профилей и карточек перед слиянием. Владелец хоста
проверяет совместимость новой сборки Worker с сохранённой историей задач.
На время обслуживания закройте приём новых задач, дождитесь завершения активных
и остановите LaunchAgent Worker. Сохраните согласованную копию и прежние версии
пакета, plist и Compose. Если обновляются контейнеры, примените совместимые версии
из нового Compose командой `docker compose up -d --wait` в прежнем каталоге проекта
с тем же именованным томом. Для обновления только Worker оставьте сервер запущенным.

Установите закреплённую сборку Worker в отдельном каталоге. Передайте ей прежний каталог
хоста с регистрациями и `state`. Выполните `--check` и, для сборки с этой командой,
`--check-writer`. Создайте plist из новой установки и загрузите его через `launchctl`.
Проверьте namespace, обработчики Workflow и Activity на основной очереди и Activity
на очереди `.control`. По сохранённым Workflow ID и Run ID прочитайте прежний результат
и сверьте его SHA-256 перед открытием приёма задач.
[Команды проверки и переключения Worker](docs/temporal-sdk.md#локальная-служба-worker-на-macos).

### Резервная копия и проверка восстановления

1. Выберите независимое хранилище с ограниченным доступом. Пока запись остановлена,
   зафиксируйте время среза, версии PostgreSQL, Temporal и сборки Worker, namespace,
   Workflow ID, Run ID и SHA-256 контрольного результата. Для холодной копии остановите
   Worker и обе службы Compose, затем сделайте снимок именованного тома PostgreSQL.
   В комплекте T7 этот том содержит обе базы — `temporal` и `temporal_visibility`.
2. Для того же среза скопируйте конфигурацию Compose и служб, приватные регистрации,
   каталог `state` со списаниями, каталоги артефактов и квитанций, первичные журналы
   команд и рабочие копии с незакоммиченными файлами. Для каждого Git worktree включите
   также каталог метаданных из `git rev-parse --path-format=absolute --git-common-dir`.
   Сохраните права доступа и манифест с размерами и SHA-256 файлов. Секреты из `.env`
   и другие необходимые учётные данные храните в защищённой части копии.
3. Восстановите копию в отдельные том и каталоги с изолированным сервером Temporal.
   До подключения какого-либо Worker сверьте манифест, доступность namespace, историю и
   результат по исходному Run ID, SHA-256 артефакта и контрольных файлов. Запишите итог
   проверки и время восстановления. Перезапуск на прежнем томе проверяет сохранность
   данных при замене контейнеров; для проверки резервной копии нужен восстановленный том.

## Вход и договоры

Работу в чате описывает [руководство Codex](CURRENT-CHAT.md). Для настройки Temporal
используйте [руководство SDK](docs/temporal-sdk.md). Общие [процедуры](procedures/README.md)
и [профили совета](roles/README.md) соответствуют версии установленного runtime.
