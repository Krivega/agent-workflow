# Ревью локальных изменений

Следуй [корневым маршрутам](https://github.com/Krivega/agent-workflow/blob/main/AGENTS.md) для затронутых договоров и
[стратегии проверок](https://github.com/Krivega/agent-workflow/blob/main/docs/testing/strategy.md). Цель — подтвердить дефект или риск
на фактической границе. Правка кода, коммит и публикация комментариев требуют отдельного запроса.

## Область Git

1. Зафиксируй `git status --short --branch`, текущую ветку и локальные ссылки. Выполни именно
   запрошенный вид ревью: диапазон коммитов, ветку либо рабочее дерево.
2. Для ветки выбирай цель интеграции: явный ref пользователя, `refs/remotes/origin/HEAD`, затем
   существующий `origin/main` или `origin/master`. Проверь обе ссылки и общего предка.
   Не используй автоматически `@{upstream}`: он может указывать на ту же проверяемую ветку.
   При неизвестной базе сообщи ограничение и уточни только зависимую область ревью.
3. Изучи список путей, полные изменения `<target>...<branch>` и нужные коммиты. Для текущей
   проверяемой ветки отдельно включи `git diff --cached`, `git diff` и относящиеся к задаче
   неотслеживаемые файлы. Рабочее дерево другой ветки к диапазону не добавляй.
4. Не получай данные из сети, не переключай ветку, не меняй файлы, индекс, refs или историю.
   Диагностику запускай по подтверждаемой гипотезе, не исправляй найденное в процессе ревью.

## Предметные проверки

Проверяй только затронутые области через договор, вызывающий код и доказательства:

- CLI и SDK: явные входы, совместимость форматов, установленные потребители и файлы поставки.
- Движок: единственный владелец состояния, повторяемость переходов, исходные доказательства.
- Сохранение и внешние эффекты: идентичность задачи и владельца, повтор запроса, отказ до записи,
  восстановление после остановки и сохранение неизвестного исхода.
- Адаптеры проектов: регистрация, правила и команды, корни и проверка разрешённых путей.
- Проверки: актуальные исходники и профиль, синтетический или настоящий SDK, область доказательства.

Сверь каждый кандидат с полным относящимся к нему изменением. Не выдавай предпочтение оформления,
необязательную переработку, нетронутый старый долг или теоретическое предположение за дефект.
Недостаток доказательств отделяй от подтверждённой ошибки.

## Результат

Сначала находки по убыванию `P0`–`P3`: русский заголовок, точный файл и строка, условие проявления,
неверный результат и влияние, направление исправления и нужная регрессия. Затем назови проверенные
refs, включённое состояние рабочего дерева, выполненные команды и ограничения. Если находок нет,
скажи это прямо. Укажи, какое исполнение, внешний сервис или установленная поставка действительно проверялись.
Сравни итоговое состояние Git с исходным и сообщи неожиданное изменение.
